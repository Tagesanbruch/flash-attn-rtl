## 2. 本轮修复项（报错已处理）

### 2.1 Clocked SDC 约束不完整（已修复）
问题：`fa_online_softmax_update` 早期出现 `output port ... is not constrained`。

修复：更新 `syn/sdc/default_clocked.sdc`，加入：
- `set_input_delay`
- `set_output_delay`
- `set_input_transition`

并做 iEDA 兼容：去除不支持的集合命令，采用 `[all_inputs]` / `[all_outputs]` 约束。

结果：`fa_online_softmax_update` 复跑后 unconstrained 报错归零。

### 2.2 top 依赖缺失（已修复）
问题：`fa_attention_ip_top` STA 合成时提示：
- `Module \fa_attention_core ... is not part of the design`

根因：`cfg/sta_modules.mk` 中 `STA_RTL_fa_attention_ip_top` 依赖列表不完整。

修复：补齐依赖到完整顶层链路：
- `rtl/common/fa_mul_sat_q8_8.sv`
- `rtl/softmax/fa_exp_pwl_8seg_q1_15.sv`
- `rtl/softmax/fa_recip_nr_q16_16.sv`
- `rtl/bus/fa_axi_lite_regs.sv`
- `rtl/bus/fa_dma_reader.sv`
- `rtl/bus/fa_dma_writer.sv`
- `rtl/core/fa_attention_core.sv`
- `rtl/top/fa_attention_ip_top.sv`

### 2.3 Yosys 解析 `automatic` 语法失败（已修复）
问题：top 继续推进后，在 `rtl/core/fa_attention_core.sv` 报：
- `syntax error, unexpected TOK_AUTOMATIC`
- `Invalid nesting of always blocks and/or initializations`

修复：
- 移除/替换 `automatic` 局部变量声明
- 把部分循环内“带初始化声明”改为“先声明再赋值”

结果：top 能继续进入更深的 Yosys 优化阶段（已越过前述语法阻断点）。

## 5. Top IP Core 面积与时序初步估算

根据当前 `fa_attention_core` 等模块的设计参数以及已经成功合成的子块 STA 结果，对由于规模过大导致卡住的 Top IP 整体情况进行理论评估：

### 5.1 面积估算 (Area Estimation)
根据各类模块在 Yosys 合成输出（`Chip area for module`）的等效面积数值，以及顶层设计（特别是 `fa_attention_core` 中未实例化的宽位数组流）提取：
1. **实例化子块总计**：
   - 寄存器配置平面（`fa_axi_lite_regs`）：约 `4,400`
   - 两组流水乘法器（`fa_mul_sat_q8_8`* 2）：约 `8,900`
   - 指数及 PWL 近似（`fa_exp_pwl_8seg`* 4）：约 `7,568`
   - 求逆倒数（`fa_recip_nr_q16_16`）：约 `15,454`
2. **海量 Flatten 触发逻辑（计算大核平铺）**：
   - **大容量片内寄存器矩阵**：受缺乏专用 SRAM 库制约，目前核心矩阵（`q_buf`, `k_buf0/1`, `v_buf0/1`，以及 `row_acc`）均基于触发器。计算可得总位宽达 **~45.8 万 bit**（e.g. `row_acc` 为 32×64×64 = 13.1 万 bit）。若折合标准触发器综合，对应面积在 **270 万 ~ 320 万** 量级。
   - **完全展开的乘法阵列**：RTL 第 `328` 行中 `for (int k = 0; k < D; k++)` 实现组合逻辑一拍并行，单周期同时展开了 **128 路 `64-bit × 16-bit`** 的加速累加。这导致极大的乘法器阵列堆叠，预估组合逻辑占据约 **10 万 ~ 30 万** 面积当量。
3. **最终 Top 面积估算**：
   受全展开矩阵与乘加树的主导，Top 整体验算 **总面积当量约为 350 万 ~ 400 万 (3.5M~4.0M)**。这也是常规 Yosys `OPT_REDUCE` 展平处理（Flattening）长时卡死的根本原因（综合负载是最大单模块的近百倍）。

### 5.2 时序估算 (Timing Estimation)
- **子模块 WNS 下界**：`fa_row_reduction_core` 本身在 2.0ns（500MHz）约束下，给出了 `-14.15ns` 的 Slack（最长组合路径达 `16.15ns`）。
- **顶层架构阻塞**：除归约操作外，`fa_attention_core` 直接利用了 64 路并发 MUX（`v_buf` 取址）并级联庞大尺寸乘法完成 P×V 累加。未经有效流水截断，此处的组合逻辑深度叠加极大概率会突破 `20ns`。
- **Top Fmax 预估**：综合考虑上述长组合逻辑毛刺与扇出，未深度流水截分的 Top Core 时钟主频预估在 **40 MHz - 60 MHz** 区间，直接达成 500MHz 时序收敛难度极大。
