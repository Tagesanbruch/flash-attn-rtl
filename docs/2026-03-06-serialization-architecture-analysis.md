# FlashAttention 数学模块串行化/流水线化分析报告

**日期：** 2026-03-06

本报告基于当前 `flashattn` 项目中的 RTL 代码以及 `MAC16` 参考设计（特定是其 1.5GHz 的 `exp_sk` 串行优化架构），深入探讨了将内部计算单元（特别是乘法器和除法器）进行串行化或深度流水线化的收益、代价以及是否足够满足当前 500MHz 甚至更高频率的 55nm PDK 设计目标。

## 1. 当前 RTL 现状与时序瓶颈分析

根据最近的 0305 STA 报告（TT corner，500MHz，1.2V/27℃），模块存在不同程度的 Setup 违例，主要集中在以下复杂计算模块：

### 1.1 `fa_recip_nr_q16_16` (求倒数)
- **当前瓶颈**：WNS `= -11.491 ns`，最高可用频率仅为 `74.1 MHz`。
- **结构分析**：当前的 RTL 代码实现并不是迭代的 Newton-Raphson，而是**硬加的一个纯组合逻辑除法器**（`quot = num / {32'd0, i_x_q16_16}`）。在 55nm 下，一个 64-bit / 32-bit 的全组合逻辑除法器会产生极其漫长的逻辑链（Path Delay 达 13.3 ns），这是导致大面积违例和极低频率的核心原因。
- **是否需要优化**：绝对需要。目前的写法在 ASIC 中是不可接受的，必须被替换。

### 1.2 `fa_online_softmax_update` & `fa_row_reduction_core`
- **当前瓶颈**：
  - Softmax update 本身 WNS `= -3.063 ns` (~197 MHz)。
  - Row Reduction Core 直接实例化了 Softmax Update 和倒数模块，并且串联了一个组合逻辑乘法器 `norm_mul_q32_32 = acc_q16_16 * recip_q16_16`，这导致了整条链的 WNS 恶化至 `-14.157 ns`（61.9 MHz）。
- **结构分析**：
  - `fa_online_softmax_update` 的关键路径在一个周期内串行执行了 `减法` -> `PWL 指数计算` -> `64-bit/32-bit 乘法` -> `加法`（更新 `l_req` 和 `acc_reg`）。
  - 这些长计算链完全没有引入中间寄存器。

### 1.3 `fa_mul_sat_q8_8` (乘积饱和器)
- **当前瓶颈**：WNS `= -0.313 ns` (Fmax ~432 MHz)。
- **结构分析**：16-bit × 16-bit 组合逻辑乘法器紧接加减法舍入和边界饱和，总延迟约 2.1ns。已经非常接近 500MHz (2.0ns) 的目标。

## 2. MAC16 架构（串行/流水线）借鉴分析

回顾 `ref/MAC16`（特别是能在 1.5GHz 3个 PVT corners 下通过的 `exp_sk`）：

- **MAC16 架构特点**：它是一个**输入串行、输出串行、内部深度流水并行**的 16-bit 乘加器。在 `exp_sk` 中，为了达到 1.5GHz (0.66ns 周期)，乘法器的 Booth 编码以及 Wallace/CSA 压缩树被强行斩断并划分为 6 级流水线（例如把 6:4 压缩和 4:2 压缩用寄存器隔开）。
- **代价**：Latency 增加到了 6 个周期，面积庞大，而且串行 I/O 带来了复杂的对齐逻辑。

### 2.1 将 FlashAttention 计算单元“串行化”的分析
如果我们考虑将 FlashAttention 内部的点积运算或乘法运算改为类似 MAC16 的“串行输入”结构：

**收益**：
1. **理论上可达极高 Fmax**：通过切分出更短的组合逻辑链，可以像在 MAC16 中那样冲刺 1GHz 甚至 1.5GHz。
2. **引脚/连线数减少**：如果是多核或长距离传输，串行能减少布线拥塞。

**代价（为什么不可行/不推荐）**：
1. **巨大的计算周期代价 (Latency)**：FlashAttention 算法对吞吐量和延迟敏感。在一个 `O(N^2)` 的注意力计算矩阵中，如果每个 16x16 乘法都需要像 MAC16 一样花费 16 个周期输入 + 6 个周期计算，这会让整个 attention 矩阵计算的周期数膨胀 10 倍以上，这完全抵消了提升 Fmax 带来的任何性能收益。
2. **系统架构不匹配**：当前 FA 架构是全并行的（如 `fa_row_reduction_core` 每一个 cycle 都 `i_valid` 地吃入一个 `i_score_q8_8` 和 `i_value_q8_8`）。若改为串行内部计算单元，需要为整个上层控制逻辑（`fa_core_controller`）增加巨大的串并转换（P2S / S2P）FIFO、多相时钟或长周期的状态机停顿（stall），复杂度剧增。

### 2.2 补充评估：多比特（Multi-bit）串行与流水线重叠（Overlapped Pipelining）

如前所述，单比特串行的 Latency 惩罚极大。但如果采用**多比特串行（如 2-bit/4-bit）**或**流水线重叠（Overlapped Execution）**，情况是否会好转？

#### A. 流水线重叠（Overlapped Pipelining）隐藏延迟
串行乘法器（如 MAC16）可以通过打满 Pipeline 来实现 `Initiation Interval (II) = 1` 的高吞吐量吗？
- **对于独立无数据依赖的输入串**：**可以**。只要我们有无穷无尽的独立 `score` 和 `value` 需要计算，即便每个乘法器需要 16 拍输入和 6 拍计算，只要我们每拍都能喂入一对新的位，流水线重叠就可以掩盖 Latency 带来的吞吐损失。
- **在 FlashAttention 中的局限**：FA 的核心瓶颈 `f(x) = exp(x - max)` 和 `acc = acc + f(x)` 存在**强数据依赖（Loop-Carried Dependence）**。以 `fa_online_softmax_update` 为例：
  - 当前 cycle 的 `acc_new` 计算必须等待上一个 cycle 的 `acc_old` 乘以 `exp_old` 缩放后加上新梯队的值。
  - 这种 $acc_{i} = acc_{i-1} \times \text{scale} + \text{new\_val}$ 的累加归约形式，如果算一次乘加需要 16~22 个周期，由于存在数据依赖，下一个 valid 数据的计算就必须**阻塞（Stall）** 22 个周期等待上一轮的 `acc_old` 出结果。这意味着流水线*无法重叠*，吞吐量将产生灾难性的 $1/22$ 暴跌。

#### B. 多比特（2-bit / 4-bit / 8-bit）串行计算
如果采用 2-bit (Radix-4) 或 4-bit (Radix-16) 的串行计算（例如每个时钟输入 4 bit，16-bit 仅需 4 个时钟加载完毕）：
- **面积与延迟折中**：4-bit 串行乘法器的组合逻辑深度介于单比特和全并行之间，可以在 Fmax 和 Latency 之间取得折中（比如 4 拍输入 + 2 拍算完，Latency = 6）。
- **可行性论证**：
  - 如果我们需要跑 1GHz 甚至 1.5GHz，4-bit 串行的组合逻辑确实能够满足（MAC16 单比特都能靠流水硬切到 1.5GHz）。
  - **致命弱点依然是累加依赖**。即使 Latency 优化到了 6 拍，由于 $acc$ 的循环依赖，对于连续输入的序列（如长度为 256 或更高的 K, V 向量序列），硬件每接收一个像素点依然需要等 6 拍。因此 4-bit 串行会带来 `1/6` 的吞吐量降低。
- **与直接并行切流水的对比**：我们可以直接保留全并行的 16x16 乘法器，并在其中横向切 2 刀（增加 2 级流水寄存器）。这样：
  - **Fmax** 同样能达到甚至超过串行方案。
  - **Latency** 同样是增加 2~3 个周期。
  - **控制逻辑** 极大简化（不需要多周期状态机或 P2S 控制器）。
  - 最关键的：并行流水线可以每个钟出结果，在算法层面有办法通过展开展开（Loop Unrolling）或交错（Interleaving）来掩盖这 2 拍的累加 Latency，而串行计算的数据拆散会大幅提升这种调度的难度。

## 3. 推荐的架构演进方案（非单纯串行化）

串行化（Serial in / Serial out）**不适合**当前的 FA 业务逻辑流。相反，**内部计算的级联流水线化（Systolic/Pipeline）**是解决当前违例的唯一正确路径。

### 3.1 乘法器处理 (`fa_mul_sat_q8_8`)
- **结论**：**不需要串行化**，只需要插入**1 级**流水线。
- **原因**：目前 432 MHz 离 500 MHz 极近，直接在乘积计算 （`x * y`）和后续的舍入饱和之间打一拍寄存器资源代价极小，即可轻松满足 1GHz 以上的时序要求，且对系统的 Latency 影响仅为 1 cycle。

### 3.2 除法器处理 (`fa_recip_nr_q16_16`)
- **结论**：**必须替换组合逻辑除法，采用迭代牛顿-拉弗森（NR）或多级流水级**，但非位级别串行。
- **原因**：目前的 `quot = num / i_x` 是一场灾难。应该使用正宗的 Newton-Raphson 乘法器迭代展开（打成 3 到 4 级流水线），或者通过 DSP slice（若有）实现多周期查表预估 + 一次乘法修正。这将让除法从 13ns 的瓶颈降到 1.5ns 左右。

### 3.3 点积与行归约处理 (`fa_online_softmax_update`)
- **结论**：**采用 Systolic/Pipeline 拆分**，断开过长的逻辑链。
- **原因**：目前的逻辑是一拍之内算出 $l_{new} = l_{old} \times exp_a + exp_b$，这相当于（查表 → 乘法 → 加法）被塞进了一个 2.0ns 的时钟周期里。
- **改进方式**：
  1. **Stage 1**: 算出并锁存 $diff = m_{old} - m_{new}$
  2. **Stage 2**: PWL 查表算出 $exp$ 然后锁存
  3. **Stage 3**: 执行大乘法器 $x \times exp$ 并锁存
  4. **Stage 4**: 执行加法累加，写回 Register
  这样会将更新逻辑的 latency 增加到 4 cycles，但是可以在 500MHz~1GHz 顺利收敛，因为 FA 是流式处理行级数据，增加 Pipeline 深度（只要不产生真正的 hazard bubble）不影响吞吐量。

---

## 4. 总结

1. **MAC16 架构的参考价值**：MAC16 `exp_sk` 验证了在 55nm 中，将庞大的组合逻辑（如 CSA 压缩树）利用寄存器斩断（Pipeline）是冲刺 1G+ 的核心手段；但这不意味着应当照抄其“串行输入/输出”的慢速业务形态。
2. **串行化（Bits-serial）不适合我们**：它会破坏现有的 1-cycle 发射架构，引入庞大的序列化控制状态机，且带来无法忍受的 latency 倍增。
3. **正确道路（Pipelining）**：保持现在的并行宽总线（16-bit / 32-bit），针对 WNS 严重的 `row_reduction` 和 `recip` 模块，在其内部数据流中横向切断，插入 2~4 级流水线寄存器。这将完美继承 MAC16 中切短组合逻辑链的时序优势，同时保证 FlashAttention 计算引擎的高吞吐量。
