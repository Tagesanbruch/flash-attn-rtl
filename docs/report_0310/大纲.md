
# FlashAttention IP 设计、验证与综合报告

## 1. 简介

本文档给出当前 FlashAttention-style SDPA 加速器 IP 的完整设计说明、验证闭环、建模方法以及综合结果总结。设计目标面向赛题给定的单 batch、单 head、自注意力场景，输入输出数据格式采用 Q8.8 定点表示，目标问题规模为 $S=256$、$D=64$，并在实现中显式满足 online softmax、K/V tiling、禁止显式存储 $S\times S$ 注意力矩阵、AXI-Lite 配置接口和 AXI4 Master DMA 数据接口等要求。

当前主线 RTL 已形成可运行的顶层系统。系统中包含 AXI-Lite 配置寄存器、AXI DMA 读写通路、片上 tile buffer、在线 softmax 状态维护、QK 点积与 PV 累加、归一化输出以及性能计数器。围绕这些功能，仓库同时建立了 cocotb 回归环境、Verilator C++ 参考测试路径、周期精确 CModel、模块级综合与静态时序分析流程。因此，本项目的工作不再停留于算子级数学原型，而是已经进入“结构可运行、验证可复现、性能可量化、综合可分析”的工程阶段。

截至 2026-03-10，主线 README 汇总的核心结果为：一方面，端到端 RTL 在默认参数下已经达到 $145{,}584$ cycles 的总延迟量级，并保持与 FP32 参考之间 $\text{MAE}=9.71925\times 10^{-4}$、$\text{MaxAE}=2.03197\times 10^{-3}$ 的误差水平；另一方面，针对模块级瓶颈的独立实验已经定位出后续 PPA 优化方向，其中 Online Softmax 独立模块已实现超过 $500\text{MHz}$ 的时序收敛，QK 路径则通过乘法器首拍与全流水加法树的重构被提升到约 $442.5\text{MHz}$ 的量级。这些结果说明当前设计已经具备作为 baseline 提交与继续扩展 bonus 功能的坚实基础。

本文将从整体进度、算法与架构、附加总线模块、功能验证、CModel、LLM 接入思路以及综合实现七个层面进行系统陈述。行文中尽量保持论文式的展开方式，对关键公式、时延估计、带宽估计与实验指标均给出完整说明。

## 3. 具体设计方案

### 3.1 实现算法说明

目标算子为 Scaled Dot-Product Attention。对给定查询矩阵 $Q\in\mathbb{R}^{S\times D}$、键矩阵 $K\in\mathbb{R}^{S\times D}$ 和值矩阵 $V\in\mathbb{R}^{S\times D}$，标准形式可写为

$$
\mathrm{SDPA}(Q,K,V)=\mathrm{softmax}\left(\frac{QK^T}{\sqrt D}\right)V.
$$

若直接先显式形成 $S\times S$ 的 score 矩阵，再统一做 softmax 和乘以 $V$，则在本题规模下会引入明显的片上存储压力。以 $S=256$ 为例，若 score 也采用 16bit 表示，则完整矩阵大小为

$$
256\times 256 \times 16\text{ bits}=1{,}048{,}576\text{ bits}=128\text{ KB},
$$

这已经接近甚至超过当前算子内多个片上 buffer 的总和，并且会破坏 FlashAttention 以流式更新代替显式矩阵存储的核心思想。因此本设计采用 online softmax 递推形式，以行为粒度维护三组状态：当前最大值 $m$、分母累计量 $l$ 以及加权和值累计向量 $\mathrm{acc}$。对于任意新到达的 score $s_j$ 与 value 向量 $v_j$，更新公式为

$$
m' = \max(m, s_j),
$$

$$
l' = l\cdot e^{m-m'} + e^{s_j-m'},
$$

$$
\mathrm{acc}' = \mathrm{acc}\cdot e^{m-m'} + e^{s_j-m'}\cdot v_j.
$$

在一行处理完全部 key 之后，最终输出为

$$
o = \frac{\mathrm{acc}}{l}.
$$

这套递推是 FlashAttention 与 online softmax 文献中的核心思想，其工程优势在于：第一，不再需要存储完整的 score 矩阵；第二，每个 score 一旦算出就可以立刻参与 softmax 更新与 PV 累加；第三，状态只需按 query 行保存，而不依赖于历史全部 score。当前设计又进一步将查询并行度设置为 `ROW_PAR=2`，即每次同时处理两个 query row，从而在不明显增大调度复杂度的前提下提高吞吐效率。

在数值表示上，输入的 $Q$、$K$、$V$ 以及输出 $O$ 都采用 Q8.8 定点格式。两个 Q8.8 数相乘得到 Q16.16 结果，因此点积累加器至少需要 32bit 以上精度。当前主线中，点积路径输出采用 40bit 中间和，行累计 `row_acc` 进一步使用 64bit 以降低长期累计误差。softmax 路径中，指数模块 `fa_exp_pwl_8seg_q1_15` 输出 Q1.15，倒数模块 `fa_recip_nr_q16_16` 输出 Q16.16，而归一化乘法器再将 64bit 累计量与 Q16.16 倒数相乘并回落到 Q8.8。对于 $D=64$ 的默认参数，缩放因子为

$$
\frac{1}{\sqrt{64}} = \frac{1}{8} = 0.125,
$$

映射到 Q8.8 后恰好为 $0.125\times 256 = 32$，因此 `SCALE` 寄存器的默认值设置为十进制 `32`。

当前架构还引入了 tile 化组织。序列长度 $S=256$ 被分成 `TQ=32` 的 query tile 和 `TK=64` 的 key/value tile，因此

$$
\mathrm{NUM\_Q\_TILES}=\frac{256}{32}=8,
\qquad
\mathrm{NUM\_K\_TILES}=\frac{256}{64}=4.
$$

设计采用外层遍历 Q tile、内层遍历 K/V tile 的双层调度。每次只在片上保存一个 Q tile、一个正在计算的 K/V tile 以及一个预取中的 K/V tile。由于 score 的计算与 online softmax 更新是流式进行的，因此整个 tile 过程始终不需要显式写出任何中间注意力矩阵。

### 3.2 设计总体框图

当前顶层结构可以抽象为如下层次：

```text
				┌──────────────────────────────┐
				│      Host / CPU / SoC        │
				│ AXI-Lite cfg + AXI memory    │
				└──────────────┬───────────────┘
							   │
				 ┌─────────────▼─────────────┐
				 │     fa_attention_ip_top    │
				 │                             │
				 │  ┌──────────────────────┐   │
AXI-Lite slave ──┼─▶│  fa_axi_lite_regs    │   │
				 │  └──────────────────────┘   │
				 │                             │
AXI4 master  ────┼─▶ fa_dma_reader            │
				 │  fa_dma_writer             │
				 │                             │
				 │  ┌──────────────────────┐   │
				 │  │  fa_attention_core   │   │
				 │  │  Q/K/V/O tile FSM    │   │
				 │  │  online softmax      │   │
				 │  │  QK + PV + norm      │   │
				 │  └──────────────────────┘   │
				 │                             │
				 │  ┌──────────────────────┐   │
				 │  │  fa_perf_counters    │   │
				 │  └──────────────────────┘   │
				 └─────────────────────────────┘
```

在顶层看来，`fa_axi_lite_regs` 负责软件可见的配置与状态窗口，`fa_dma_reader/fa_dma_writer` 分别负责从系统内存搬运 Q/K/V 与将 O 写回系统内存，而 `fa_attention_core` 则是完整的调度与数据通路中心。值得强调的是，本设计并未将计算控制器与数据通路彻底分离，而是选择将 tile 调度、DMA 命令发起、online softmax 状态维护、QK/PV 计算与最终归一化都放入一个强内聚的核心中。这种做法牺牲了一部分模块边界上的整洁性，但换来了早期迭代阶段更直接的功能闭环和更清晰的时序归因。

### 3.3 模块间数据流向

一次完整 attention 计算的主数据流可叙述如下。首先，软件通过 AXI-Lite 将 `Q_BASE`、`K_BASE`、`V_BASE`、`O_BASE`、`STRIDE_BYTES`、`SCALE`、`NEG_LARGE` 等寄存器写入顶层寄存器文件，然后向 `CTRL` 寄存器写入启动脉冲。顶层寄存器文件将该启动脉冲转化为 `fa_attention_core` 的 `i_start`，同时保持各个配置参数处于稳定状态。

在 `fa_attention_core` 内部，主状态机首先进入 `S_LOAD_Q`，通过 DMA reader 发出一个 query tile 读命令，并将读回的总线 beat 逐个解包为 `q_buf[TQ][D]`。随后，状态机进入 `S_INIT_CONTEXT`，将当前 query tile 对应的 `row_m`、`row_l`、`row_acc` 进行初始化，其中 `row_m` 初始化为 `NEG_LARGE`，`row_l` 初始化为零，`row_acc` 初始化为零向量。

接下来主状态机依次对 4 个 K/V tile 循环。对于每个 tile，先加载 K，再加载 V；进入 `S_COMPUTE` 后，内部子状态机 `cs` 会以 `ROW_PAR=2` 为粒度遍历 query 行对，以 `DP_CHUNKS=2` 为粒度遍历 32-lane 的点积切片，以 `TK=64` 的长度遍历 key/value 行。每个 score pair 先经过 QK 点积，再乘以缩放因子，随后进入 online softmax 更新模块产生新的 `m`、`l` 和 `acc`。由于 `V` 行与新生成的 softmax 权重在同一拍的组合中被使用，因此 score 一旦计算完毕，便立即以流式方式并入 `row_acc`，不需要中间存储 score 阵列。

当所有 K/V tile 完成后，核心进入 `S_NORMALIZE`。此时每个 query row 的 `row_acc` 和 `row_l` 已经累积完毕，归一化逻辑先对 `row_l` 启动倒数模块，再以 `NORM_LANES=8` 的向量宽度将 `row_acc` 分块乘以倒数，得到最终的 `o_buf[TQ][D]`。最后，`S_WRITE_O` 通过 DMA writer 将 O tile 写回系统内存，并在 `S_NEXT_Q` 中决定是否继续处理下一个 Q tile。当全部 tile 结束后，顶层将 `done` 置位并允许软件读取 `CYCLES` 与性能计数器寄存器。

如果将上述过程按一次完整运行的地址搬运量来观察，则 Q 只在每个 Q tile 开始时读取一次，而 K/V 会对每个 Q tile 重复遍历全部 4 个 tile。之所以这样设计，是因为该架构的优化重点并不是极端减少片外流量，而是在片上存储受限的前提下，通过适中的 tile buffer 和 online softmax 流程使运算路径尽可能连续。后续如需支持更长上下文或更多 head，则应在系统层继续引入更高级的外部编排与片上 scratchpad 级缓存，而不是简单扩大当前核心的本地 buffer。

### 3.4 具体算子的实现

#### 3.4.1 QK 点积实现

主线中的点积算子由 `fa_qk_dotprod_slice` 完成。它接受两行 query 数据、一行 key 数据以及当前 chunk 编号，在每个 chunk 内对 `DP_LANES=32` 个元素做并行乘法与求和，并输出两个 query row 对应的局部部分和。由于 `D=64`，因此默认需要两个 chunk 即可完成一次完整内积。内积输出本身为 Q16.16 累加结果，随后在核心中通过右移截取 Q8.8 片段，再送入乘法器与固定缩放系数相乘，得到最终 score。

这种结构的优点是逻辑简单、控制友好，与 `ROW_PAR=2` 的并行方式自然匹配。其问题也很明显：当每拍同时执行 32 个 `16\times 16` 乘法再叠加局部加法树时，单拍组合深度很大，因此在 55nm 目标频率下很容易成为关键路径来源。这正是后续独立实验集中优化的对象。

围绕 QK 点积，本项目在 `experiments/fa_qk_dotprod_slice_pipe` 中开展了多轮实验。早期的 `exp_e` 通过 `8` 组局部乘加块再做 `quarter / half / final` 三级归并，将频率提高到约 `203.8MHz`。2026-03-10 的新一轮实验继续坚持 `32-lane` 和 `II=1`，但把第一级强制改为“纯乘法寄存”，后续全部改成逐级流水的二叉加法树。由此得到的 `exp_f / exp_g / exp_h` 在结构上分别对应“纯乘法首拍”“位宽逐级收敛”“输入预寄存+位宽收敛”三种版本。补跑前台 STA 之后的结果表明：`exp_g` 的最差 slack 为 `-0.650ns`、估算频率约 `377.3MHz`，`exp_h` 的最差 slack 为 `-0.260ns`、估算频率约 `442.5MHz`。这说明 QK 路径的频率瓶颈已经被压缩到单乘法器级，而不再是宽加法树级别，为后续主线集成提供了明确方向。

#### 3.4.2 Online Softmax 实现

online softmax 的核心模块是 `fa_online_softmax_pair`。该模块一次处理两个 query row 的状态更新，输入包括 `score0`、`score1`、历史 `m/l/acc` 以及当前 value 向量 `v_row`。在组合逻辑中，它先比较生成新的最大值，再分别计算旧状态衰减项和新得分激活项，最后更新分母与累计向量。指数部分由 `fa_exp_pwl_8seg_q1_15` 提供，历史累计量与当前新项都在 fixed-point 域内完成乘法和位移。

从算法角度看，这一模块正对应 online softmax 递推公式；从硬件角度看，它是最典型的反馈回路，因为新一拍的 `m/l/acc` 直接依赖上一拍的寄存状态。因此该路径既要保证吞吐，又必须控制反馈回路上的组合深度。在独立实验中，本项目引入了 context interleave、state forwarding 和更细粒度流水拆分。最终 `fa_online_softmax_ctx/exp_d` 已在 500MHz 约束下得到正 slack，估算频率约为 `536.2MHz`。这一结果说明，online softmax 的关键并不是一味牺牲吞吐去做长流水，而是在保证数据相关性正确的前提下，通过多 context 交错和旁路前递切断最重的反馈组合链。

#### 3.4.3 倒数与归一化实现

归一化阶段包含两个子问题。第一个子问题是如何计算分母 $l$ 的倒数，当前使用 `fa_recip_nr_q16_16` 实现 Newton-Raphson 迭代。第二个子问题是如何将 64bit 的累计向量乘以 Q16.16 倒数，再有符号饱和回写到 Q8.8 输出，当前由 `fa_o_normalize_block` 完成。主线中以 `NORM_LANES=8` 的方式分块处理 `D=64` 维，因此每行需要 8 次向量归一化，整块输出需要 256 次倒数请求与 256 次倒数响应，这也与 perf counters 的实际读回相符。

倒数模块是最早完成 500MHz 收敛的子模块之一。`fa_recip_nr_q16_16/exp_c` 采用 16×16 部分积和 10 级流水之后，估算频率可达 `527MHz`，已经表明数值核本身不是系统主瓶颈。归一化块的独立实验则显示，单纯在输出路径上做轻量流水虽然能将频率提升到 `333.9MHz` 至 `360.8MHz`，但与 QK 和 softmax 相比，其收益和优先级仍然偏低。因此当前的工程判断是：归一化阶段已经足以支撑 baseline 主线，后续更适合通过系统级 overlap、倒数前移或更好的物理实现来继续挖掘，而不必把大量前端架构时间继续投入到该路径。

#### 3.4.4 控制、双缓冲与性能计数器

`fa_attention_core` 使用双层状态机组织。主状态机 `ms` 依次执行 `S_LOAD_Q`、`S_INIT_CONTEXT`、`S_LOAD_K`、`S_LOAD_V`、`S_COMPUTE`、`S_NORMALIZE`、`S_WRITE_O`、`S_NEXT_Q` 和 `S_DONE`。内层计算子状态机 `cs` 则在 `S_COMPUTE` 期间执行 `C_DP_RUN`、`C_SCORE_DONE`、`C_SOFTMAX_PREP` 和 `C_DONE`。该控制结构的一个重要优化是取消了多余的空拍控制态，把部分初始化、下标推进和状态过渡内联到关键状态中，从而减少 `cs_ctrl_cycles`。

K/V buffer 方面，主线已经实现 ping-pong 双缓冲。当前活跃 bank 负责参与计算，而另一个 bank 可以在计算期间预取下一 tile。这一结构的意义不在于理论上消灭所有读延迟，而在于把一部分原本显式暴露在主状态机中的 K/V 装载周期掩蔽到 compute 阶段内部。根据当前 perf counters 的读回，`MS_COMPUTE` 约为 `131200 cycles`，而 `MS_LOAD_K`、`MS_LOAD_V` 各约 `2072 cycles`，这说明除首个 tile 外，K/V 访存确实已有相当部分被重叠到计算过程中。

为了使后续优化可以量化，本项目又引入了 `fa_perf_counters` 模块，并在 AXI-Lite 窗口中映射了 `0x80~0xD4` 的只读寄存器。当前可读回的计数包括运行次数、busy 周期、DMA 命令与 beat 数、乘法/指数/倒数事件数、主状态占时和子状态占时。这使得本项目从传统的“看一次 test pass 与否”的验证方式，进一步推进到了“设计行为—计数口径—性能结论”三者一致的工程闭环。

### 3.5 定点实现误差分析

定点误差分析是本项目中最早暴露系统性问题的一环。初始阶段若直接拿 RTL 同构路径与 FP32 结果比较，会发现误差显著大于赛题门限；而若采用“输入量化、softmax 仍在浮点域”的参考模型，则误差又远小于门限。这一现象说明，必须严格区分算法口径与实现口径，否则会高估硬件链路的数值质量。为此，项目后来单独建立了 CModel，并对 dot、score、exp、$l$、acc、norm 六个阶段做逐级误差分解。

阶段误差分解的结果非常具有指导意义。在 `small-int + causal` 条件下，`dot`、`score` 和 `exp` 的 MAE 都在 $10^{-3}$ 量级，而 `acc` 阶段的 MAE 已达到 `135.58`，最终 `norm` 阶段的 MAE 约为 `1.865`。在 `gaussian + causal` 条件下，`acc` 的 MAE 进一步上升到 `464.11`，`norm` 的 MAE 也被拉高到 `33.44`。这表明主导误差并不来自指数近似本身，而是来自长程累计状态 `acc` 的尺度耦合、分母归一化以及掩码后的动态范围放大。

基于该结论，项目在主线中采取了几项稳健策略。第一，`row_acc` 使用 64bit 高精度累计，避免软最大更新过程中被过早截断。第二，`l_new` 在写回前加入最小值保护，防止分母退化为零。第三，归一化阶段保留 `den==0` 的保护分支，并将饱和逻辑集中到末端。第四，精度回归同时保留“RTL 同构 fixed-point 参考”和“FP32 reference”两种口径，避免后续优化只对某一种口径过拟合。从当前主线 README 汇总结果看，最终 RTL 与 FP32 的端到端误差已经收敛到 `MAE=0.000971925`、`MaxAE=0.00203197`，说明这些结构与精度策略在当前 baseline 问题规模下是有效的。

### 3.6 延迟与带宽分析

从理论参数出发，当前设计的主要派生量如下。总线宽度 `BUS_W=128`，因此每个 beat 可携带

$$
\mathrm{ELEMS\_PER\_BEAT}=\frac{128}{16}=8
$$

个 Q8.8 元素。对于 $D=64$，每行需要

$$
\mathrm{BEATS\_PER\_ROW}=\frac{64}{8}=8
$$

个 beat。于是，一个 Q tile 的流量为

$$
32\times 64\times 2\text{ B}=4096\text{ B}=4\text{ KB},
$$

对应 256 个 beat；一个 K tile 或 V tile 的流量为

$$
64\times 64\times 2\text{ B}=8192\text{ B}=8\text{ KB},
$$

对应 512 个 beat。整个 attention 的理论总流量因此为：Q 读取 $8\times 4\text{KB}=32\text{KB}$，K 读取 $8\times 4\times 8\text{KB}=256\text{KB}$，V 读取同为 `256KB`，O 写回为 `32KB`，合计约 `576KB`，即 `36,864` 个 128bit beat。

从计算量角度看，`ROW_PAR=2` 意味着一个 score pair 对应两个 query row；每个 Q tile 中共有

$$
\frac{TQ}{ROW\_PAR}=\frac{32}{2}=16
$$

个 row pair。每个 row pair 需要遍历 `TK=64` 个 key，因此每个 K tile 处理 `16\times 64=1024` 个 score pair，全局一共处理

$$
8\times 4\times 16\times 64 = 32768
$$

个 score pair。当前主线中每个 score pair 的子状态开销大约为 `DP_RUN=2`、`SCORE_DONE=1`、`SOFTMAX_PREP=1`，因此 compute 主体约为

$$
32768\times 4 = 131072\text{ cycles}.
$$

再加上 Q 装载、K/V 装载首拍开销、归一化和写回，就得到当前十几万级的总延迟量级。这一估计与 perf counters 的读回高度一致：`MS_COMPUTE=131200`、`CS_DP_RUN=65536`、`CS_SCORE_DONE=32768`、`CS_SOFTMAX_PREP=32768`。因此可以明确判断，当前 baseline 的主瓶颈是计算路径而不是 AXI 带宽。若总线能做到理想一拍一 beat，则纯传输下限只有 `36,864 cycles`；而当前实际总周期约为 `145,584 cycles`，说明结构优化的主要收益仍然来自减少 QK/softmax/控制气泡，而非继续一味扩展总线带宽。

## 4. 附加模块的设计

### 4.1 DMA 引擎

#### 4.1.1 设计总体思路

DMA 模块采用非常明确的“命令接口 + AXI 主口 + 简单双向流接口”结构。`fa_dma_reader` 接收来自调度器的 `cmd_valid/cmd_ready/cmd_addr/cmd_len`，将其转化为 AXI 读地址突发，再把返回的 R 通道 beat 原样流式送往下游 tile buffer。`fa_dma_writer` 则接受写命令和写数据流，先发起 AXI 写地址，再连续消费输入数据 beat，最后等待写响应完成一个事务。这样的接口形式有两个优点。其一，调度器只需要关心“从哪个地址开始搬多少 beat”，不需要直接操作 AXI 的五个通道。其二，后端 compute core 可以把访存看作简单的流输入和流输出，从而减少控制状态机与总线协议之间的耦合。

读取 DMA 内部支持对过长逻辑命令进行分裂。当总读 beat 数超过 AXI `ARLEN` 能够编码的范围时，模块会自动把一条长命令拆成多个 burst 并递增地址继续读取。这一能力已在 `test_split_long_command` 中得到验证。对本项目而言，这一点的重要性在于它使调度器可以统一以 tile 为粒度给出逻辑长度，而不必人工考虑底层 AXI burst 的最大长度限制。

#### 4.1.2 工作流程及错误处理

读 DMA 的状态机可概括为 `AR_IDLE -> AR_SEND -> AR_STREAM`。在 `AR_IDLE` 状态接收到命令后，模块首先根据剩余 beat 数裁剪出本次 burst 的长度；在 `AR_SEND` 状态与 AXI 地址通道完成握手；随后进入 `AR_STREAM`，在每拍 `RVALID && RREADY` 时向下游输出一个 beat，并更新剩余 beat 计数。当一个 burst 完成而总事务尚未结束时，状态机会自动回到 `AR_SEND` 继续下一个 burst。任何一次 `RRESP != OKAY` 都会将 `error` 置为粘滞态，以便上层统一发现故障。写 DMA 的结构与此对称，其状态机为 `W_IDLE -> W_ADDR -> W_DATA -> W_RESP`，并对 `BRESP` 做粘滞错误记录。

从验证结果看，DMA 模块的行为已经比较稳定。`fa_dma_reader` 的单测覆盖了单 burst、错误标记、字节计数、背靠背命令和超长命令拆分；`fa_dma_writer` 的单测覆盖了写 burst、响应错误和写字节统计。顶层 full-run perf counters 读回的 `DMA_RD_CMD_COUNT`、`DMA_WR_CMD_COUNT`、`DMA_RD_BEAT_COUNT`、`DMA_WR_BEAT_COUNT` 还能与内存模型的统计互相校验，这说明 DMA 模块不仅功能正确，而且其计数口径也足以支撑后续系统级性能分析。

### 4.2 AXI-Lite Config 的实现

#### 4.2.1 AXI-Lite 配置寄存器

AXI-Lite 配置寄存器由 `fa_axi_lite_regs` 实现。其内部使用典型的写地址与写数据分离锁存结构：只有当地址与数据都到齐、且当前没有未完成的写响应时，才视为一次 `write_fire`。读通道则根据 `ARADDR` 直接组合多路选择出 `RDATA`，并用 `RVALID` 做单周期响应控制。这样的实现方式足以覆盖当前简单寄存器文件的需求，同时避免引入更复杂的寄存器总线桥接逻辑。

控制寄存器的语义设计与赛题要求基本对齐。`CTRL` 中 bit0 表示启动脉冲，bit1 表示软复位，bit2 预留为中断使能；`STATUS` 中包含 busy、done-sticky 和 error；`CFG` 当前主要承载 `causal_en`。四组 64bit 基地址通过高低 32bit 寄存器拼接形成 `Q_BASE/K_BASE/V_BASE/O_BASE`。此外，还包括 `STRIDE_BYTES`、`NEG_LARGE`、`SCALE` 和 `CYCLES` 等寄存器。为了支撑架构级调优，又额外加入了 `0x80~0xD4` 的性能计数器窗口，使上层软件无需内部探针即可读取本轮运行的微观行为统计。

#### 4.2.2 寄存器具体功能对照表

表 4-1 给出当前主用寄存器及功能说明。

| 偏移 | 名称 | 功能说明 |
|---|---|---|
| `0x00` | `CTRL` | bit0 启动脉冲，bit1 软复位，bit2 中断使能 |
| `0x04` | `STATUS` | bit0 busy，bit1 done-sticky，bit2 error；支持写 1 清 done |
| `0x08` | `CFG` | bit0 为 `causal_en` |
| `0x14/0x18` | `Q_BASE_L/H` | Q 基地址低 32bit 与高 32bit |
| `0x1C/0x20` | `K_BASE_L/H` | K 基地址低 32bit 与高 32bit |
| `0x24/0x28` | `V_BASE_L/H` | V 基地址低 32bit 与高 32bit |
| `0x2C/0x30` | `O_BASE_L/H` | O 基地址低 32bit 与高 32bit |
| `0x34` | `STRIDE_BYTES` | 行跨度，默认 `128` bytes |
| `0x38` | `NEG_LARGE` | 因果掩码使用的大负数，默认 `0xFFFF8000` |
| `0x3C` | `SCALE` | 缩放因子 Q8.8，默认 `32` |
| `0x40` | `CYCLES` | 当前运行周期计数 |
| `0x80~0xD4` | `PERF_*` | 运行次数、DMA 统计、子状态占时、乘法/指数/倒数计数 |

这种寄存器组织方式在软件接口层非常直接。一方面，它使 host 侧可以把当前 IP 看成标准的“配置—启动—轮询完成—读统计”设备；另一方面，也为未来 UVM reg model 和 SoC driver 的统一抽象提供了天然接口边界。

## 6. UVM 验证——模块功能和完整性测试

### 6.1 UVM 验证结构

UVM 体系目前尚未正式落地，但设计边界已经足够清晰。若进入下一阶段实现，建议将验证平台拆分为 AXI-Lite agent、AXI4 memory agent、寄存器模型、scoreboard、coverage collector 与虚拟序列六个主要部分。AXI-Lite agent 负责寄存器配置与轮询完成，AXI4 memory agent 则负责行为级存储阵列与突发事务。寄存器模型应覆盖当前 `CTRL/STATUS/CFG/BASE/STRIDE/SCALE/PERF` 全部窗口，并支持 `done-sticky` 的写 1 清行为。scoreboard 一方面对比写回的 O 矩阵，另一方面核对 DMA 事务条数和性能计数器口径。虚拟序列则负责组织短序列、全序列、causal/non-causal、错误注入、背靠背任务和长时间稳定性测试等场景。

从结构上看，现有 cocotb 验证已经为 UVM 搭建提供了相当完整的参考：内存模型可以映射到 AXI agent，现有 Python 参考可以迁移为 DPI-C 或离线黄金模型，寄存器访问路径则可以直接转化为 reg model 序列。因此，UVM 的工程量主要体现在把当前脚本化验证重构成类层次清晰、覆盖率可统计、随机约束可扩展的体系，而不是从零开始重建全部行为语义。

### 6.2 UVM 验证结果

截至本报告写作时，UVM 还未启动编码，因此暂无覆盖率统计、回归通过率或约束随机结果可汇报。这一节保留为后续阶段的规划接口。考虑到当前 baseline 功能、周期与精度已经具备稳定基础，下一阶段若进入更强的 SoC 集成和 bonus 功能开发，UVM 平台将成为验证复杂数据流、异常事务和系统互联边界条件的自然下一步。

## 7. 算法实现架构建模

### 7.1 周期精确的 CModel 建立

`cmodel/` 目录中的 C++ 工程承担两类工作：第一类是精度对照，第二类是吞吐与周期建模。其文件组织为 `attention_math.cpp`、`attention_kernels.cpp`、`attention_experiment.cpp`、`attention_lib.cpp` 和公共头文件 `attention_core.hpp`。其中，数学文件实现 fixed-point 算术与近似函数，内核文件实现 attention 计算流程，实验文件实现多种模式扫描、阶段误差分解和 compute-only 架构模型，而库文件则把这些功能组织为可执行工具。

该 CModel 的重要价值并不只是“再写一份软件版 attention”，而是在于它提供了严格对齐 RTL 结构的多种模式。例如 `rtl_strict` 模式沿用 PWL exp、NR reciprocal 和 fixed-point 位移链路；`rtl_real_exp`、`rtl_real_exp_float_norm` 则逐步替换局部算子，用于判断误差究竟来自哪里；`run_stage_decomp` 能对各个算子阶段分别做 MAE、MaxAE 和 RMSE 统计；`run_compute_cycle_model` 则能够在不真正写出 RTL 的前提下，对不同 lane 数、row 并行数和是否引入 NoC 的架构做周期估算。

### 7.2 精度/吞吐量建模及优化

精度建模部分的关键结论前文已经讨论：`acc` 是主导误差源，而不是 `exp` 本身。吞吐量建模部分则给出了另一个很重要的系统性判断。以 `docs/data/20260304_compute_cycle_models_s256d64.csv` 为代表的结果显示，当采用 `fixed_flow_l32_norm8_row2` 时，compute-only 周期约为 `100,608`；若将 row 并行进一步扩大到 4，则可下降到 `51,328`；而引入简单 NoC 后，虽然功能上更灵活，但附加的分发与同步开销会使总周期反而回升。因此，对于当前问题规模和当前设计阶段，固定指令流并行优先于引入额外网络结构，是一个更合理的工程决策。

### 7.3 测试结果

为了便于汇总，表 7-1 列出 CModel 中最具代表性的几组数据。

| 数据类别 | 代表结果 | 结论 |
|---|---|---|
| 阶段误差分解 `small-int + causal` | `acc` MAE=`135.58`，`norm` MAE=`1.865` | 误差主导来自累计与归一化 |
| 阶段误差分解 `gaussian + causal` | `acc` MAE=`464.11`，`norm` MAE=`33.44` | 高动态输入进一步放大累计误差 |
| 方案对比 `small-int + causal` | `acc_float_qout` / `acc_float_real_exp_qout` 可达标 | 证明累计精度是关键方向 |
| 计算周期模型 `fixed_flow_l32_norm8_row2` | `100608 cycles` | 说明当前 RTL 仍有进一步结构优化空间 |
| 计算周期模型 `simple_noc_l32_norm8_row4` | `71808 cycles` | NoC 并非当前规模下的必要条件 |

这些结果有两个直接意义。其一，CModel 不是与 RTL 相互独立的辅助代码，而是架构决策的重要支撑工具。其二，当前主线之所以能够在不牺牲正确性的前提下把周期降到十几万级，并不是凭经验试错，而是因为 CModel 已经提前揭示了哪些方向会有效、哪些方向虽然看起来高级但收益有限。

## 8. IP 核接入大模型推理

### 8.1 模型与推理框架

关于 LLM 接入，本项目已经完成较为系统的可行性分析。总体思路是在 C/C++ 推理框架中拦截 attention 模块调用，把原本由 CPU 完成的 SDPA 运算替换为 RTL IP 或其 Verilator/DPI-C 封装接口。理想情况下，软件侧只需要完成三件事：第一，把进入 attention 的浮点张量量化为 Q8.8；第二，把量化后的 Q/K/V 放入一段 DMA 可见内存；第三，启动 IP 并在完成后把 O 结果从 Q8.8 恢复成浮点再接回后续网络层。

需要指出的是，若完全不修改当前 RTL 主线，则模型选择必须考虑 `head_dim` 与上下文长度的兼容性。当前 IP 以 `D=64` 为默认参数，因此更直接匹配的是 `head_dim=64` 的模型或经过裁剪后的实验模型。若仍坚持沿大纲中最初提到的 `Qwen2.5-0.6B` 继续推进，则必须先确认该模型的 `head_dim` 是否与当前 IP 对齐；若不对齐，就需要将硬件扩展到 `D=128`，或者在软件侧做明确的模型裁剪与验证说明。从现有调研结论看，短期更稳妥的方案是优先选择 `head_dim=64` 的小模型或做受控实验模型，以降低接入阶段的不确定性。

### 8.2 针对 IP 核的推理引擎指令流优化

一旦把 attention 核从纯软件函数替换为硬件外设或其仿真模型，推理引擎层面的编排就变得重要起来。当前 IP 天然支持 tile 化，因此软件侧最直接的优化是让 `run.c` 或等价推理框架把 Q/K/V 的地址组织成与 IP tile 边界一致的布局，减少边界打包和额外拷贝。若未来要支持长于 `S=256` 的上下文，则更需要在推理框架层实现外层 block 调度，把一个长序列拆成多个 `256` 长度的 block，并结合外部存储层次或 scratchpad 做双缓冲搬运。

但需要注意，若要对大于 `256` 的上下文做严格等价的 FlashAttention block merge，IP 需要暴露中间的 $m$ 和 $l$ 状态，或者支持“续算模式”。如果只输出最终归一化后的 O，而不输出 block 级统计状态，那么多个 block 的结果无法在软件层无损合并。因此，当前推理引擎优化可以分成两个层次。第一个层次是不修改 RTL、仅在 `S\le 256` 的范围内做端到端联合仿真；第二个层次是为了支持更长序列，在 IP 协议层增加中间状态可见性，使软件得以正确完成 block merge。当前项目已经完成第一个层次的方案论证，第二个层次则属于 bonus 与系统扩展方向。

### 8.3 实测结果对比

`inference/native` 已经保留了一组本机 Q8.8 attention 替换实验结果，本轮未再重复长耗时跑批，而是把现有结果统一收集到 [docs/report_0310/report/logs/native](docs/report_0310/report/logs/native)。其中可直接引用的文件包括性能日志 [docs/report_0310/report/logs/native/perf.log](docs/report_0310/report/logs/native/perf.log)、trace [docs/report_0310/report/logs/native/trace.log](docs/report_0310/report/logs/native/trace.log)、吞吐汇总 [docs/report_0310/report/logs/native/q8_8_perf_results.csv](docs/report_0310/report/logs/native/q8_8_perf_results.csv) 与文本对比 [docs/report_0310/report/logs/native/q8_8_text_results.csv](docs/report_0310/report/logs/native/q8_8_text_results.csv)。

从文本一致性看，当前 CSV 共记录 `10` 组 prompt，其中 Q8.8 输出与 FP32 输出“完全一致”的只有 `2` 组，按严格字符串口径的 match rate 为 `20%`，统计摘要已单独存放在 [docs/report_0310/report/logs/native/native_metrics_summary.txt](docs/report_0310/report/logs/native/native_metrics_summary.txt)。这说明：一方面，Q8.8 attention 路径已经能够稳定跑通完整推理流程；另一方面，若以最终生成文本逐字一致作为标准，当前定点替换仍会带来明显语义漂移，因此后续对接 RTL 时必须把“是否能跑”与“文本是否严格保持”分开讨论。

从吞吐数据看，`10` 组样本上的平均结果为：FP32 路径 `QKV=7.969 GMAC/s`、`ATTN=1.936 GMAC/s`、`Pipeline=14.833 GMAC/s`、`ATTN_Time_%=13.840%`；Q8.8 路径则为 `QKV=8.243 GMAC/s`、`ATTN=5.582 GMAC/s`、`Pipeline=17.366 GMAC/s`、`ATTN_Time_%=5.440%`。虽然这些数字仍然混合了软件框架与本机 CPU 行为，但它已经说明当前 attention 替换后，热点占比确实从“明显 attention 主导”下降为“attention 不再是主导瓶颈”，这为后续用 DPI-C / RTL 核进一步替换 `flash_attn.c` 提供了现实依据。

具体到单条日志，[docs/report_0310/report/logs/native/perf.log](docs/report_0310/report/logs/native/perf.log) 记录了一次以 “Introduce the history of the Apple company.” 为 prompt 的本机运行。该运行成功完成了模型加载与文本生成，但回答内容明显偏保守、且未真正围绕苹果公司历史展开，这与上面的文本匹配率结论是一致的：当前 native Q8.8 路径已经能证明“算子替换可行”，但尚不能把其输出质量直接视为最终可交付的大模型推理质量。

### 8.4 结合 trace 的数据流分析与优化讨论

[docs/report_0310/report/logs/native/trace.log](docs/report_0310/report/logs/native/trace.log) 给出了 attention 替换在模型推理中的实际数据流展开。以 `pos=0` 的首 token 为例，每层都先执行 `Input RMSNorm`、`Q_proj/K_proj/V_proj` 与 `RoPE`，随后进入“FlashAttention Module Equivalent”阶段。trace 明确表明：当前模型的 attention 输入在每层表现为 `Q [14, 64]`、`K_cache [1, 2, 64]`、`V_cache [1, 2, 64]`，即共有 `14` 个 query head、每个 head 的 `head_dim=64`，而在序列初始阶段每个 head 只需要对极短的 K/V cache 做点积、softmax 与加权求和。

这个 trace 对硬件接入有三个直接启示。第一，当前 IP 的 `D=64` 与 trace 中的单头维度是对齐的，因此最小可行接入不必先扩维到 `128`，而是可以先围绕“单 head、head_dim=64、逐 head 调用”的方式完成 DPI-C 验证。第二，真正需要软件—硬件协同处理的是 head 维与层维的外层循环；对单次核调用而言，硬件只需负责某一 head 的 `QK^T + online softmax + PV`，而不需要吞掉整个 transformer layer。第三，decode 初期 K/V cache 很短，attention 计算量并不大，此时若直接调用 RTL 仿真核，调度、量化、内存拷贝和 DPI 交互开销很可能高于纯计算开销，因此应该优先在 prefill 或较长 decode 上下文中验证收益。

据此，后续优化建议可归纳为四点。其一，先把 `inference/native/flash_attn.c` 中单 head attention 调用封装成稳定接口，再以 DPI-C 替换其中的 `QK/softmax/PV` 核心，避免一开始就尝试把整层全部搬到 RTL。其二，优先复用当前 `trace.log` 中已经出现的 `head_dim=64` 场景，把硬件核视为“每 head 一次调用”的加速器，而不是要求硬件立即支持全部 `14` 个 head 并行。其三，在 RTL 侧应继续优先吸收 `fa_qk_dotprod_slice_pipe/exp_h` 与 `fa_online_softmax_ctx/exp_d` 这类已经完成频率验证的结构，因为它们恰好对应 trace 中最核心的两段计算。其四，若未来要覆盖更长序列，就必须把 block merge 所需的中间 `m/l` 状态或等效统计信息通过接口暴露出来，否则软件无法在多 block 场景下正确合并 attention 结果。

## 9. Bonus 功能实现

虽然本报告主体仍以 baseline 为中心，但当前工程中实际上已经包含若干具有 bonus 性质的能力。第一，perf counters 不仅满足调试需要，也为后续系统级性能感知与软件侧调度提供了硬件事件基础。第二，K/V 双缓冲预取与主线控制空拍压缩，使当前设计不再只是“功能正确的串行原型”，而是具备了真实吞吐优化特征。第三，QK 点积的多轮实验已经从浅层归并推进到乘法首拍和全流水加法树，为进一步逼近高频提供了结构模板。第四，围绕长上下文支持、block merge、DPI-C 联合仿真和 LLM 接入的方案分析，也已把 bonus 扩展的技术边界梳理得较为清楚。

若从后续优先级看，最具价值的 bonus 方向有三个。其一，是把当前独立实验中验证有效的 QK 与 Online Softmax 结构真正回灌到主线，使 baseline 的频率潜力与结构清晰度进一步提升。其二，是扩展长上下文支持，为软件—硬件协同 FlashAttention 提供 block merge 所需的状态接口。其三，是完成 LLM 端到端接入，把“功能正确、周期可测”的 attention IP 进一步提升为“真实推理流程可调用”的硬件加速组件。

## 10. 逻辑综合与物理实现

### 10.1 具体方案

当前综合与时序分析采用两阶段策略。前期使用 Yosys 进行逻辑综合，并通过 iEDA 完成基于 icsprout55 的 pre-P\&R 静态时序分析，主要目标是定位中前端的结构瓶颈，而不是给出最终流片级物理结果。后期若项目进入更完整的实现阶段，则再迁移到 Cadence 工具链做完整后端流程，包括 floorplan、placement、CTS、routing、功耗分析和版图签核。

这种策略的合理性在于，当前项目仍处于架构快速迭代期。对于 QK、Online Softmax、Normalization 等模块，决定频率上限的往往是“这一拍做了什么组合逻辑”，而不是“标准单元摆在芯片上的具体位置”。因此先用综合和 STA 快速识别最长路径、面积量级和结构性趋势，再决定是否继续拆拍或重构 datapath，是成本最低、信息量最高的做法。

### 10.2 版图结果与面积分析

当前尚无完整 Cadence 版图结果，因此面积分析仍以综合报告中的 cell area 为主。尽管如此，这些数据已经足以揭示各热点模块的相对规模。举例而言，`fa_online_softmax_ctx/exp_d` 的面积约为 `27216.28`，说明 softmax 路径虽然时序敏感，但绝对面积并不高；`fa_o_normalize_block_pipe/exp_d` 的面积约为 `238672.84`，说明 64bit 归一化链路会带来较大面积负担；QK 点积实验 `exp_g` 与 `exp_h` 的面积分别约为 `272855.24` 和 `286906.48`，则表明高宽度并行乘加树是当前最主要的面积热点之一。倒数模块 `fa_recip_nr_q16_16/exp_c` 的面积约为 `60594`，在达到 500MHz 收敛的同时面积增量仍然可接受。

这些数据有一个直接推论。若未来需要进一步压缩面积，单靠在线 softmax 或倒数模块的局部优化意义有限，因为它们的绝对面积并不构成系统主导项；真正需要做结构权衡的是 QK 和归一化等高位宽、高并行路径。与此同时，若只从“面积—频率收益比”角度看，Online Softmax 是目前最值得继续保留和吸收独立实验成果的模块，因为它已经证明可以以相对温和的面积代价换来非常显著的频率提升。

#### 10.3.2 功耗分析

当前流程尚未形成完整的向量驱动功耗报告，因此本节只能给出定性分析而不提供签核级数值。一般而言，QK 点积模块由于具有大量并行乘法器和较宽寄存器阵列，是最可能同时成为面积与功耗热点的单元。归一化模块虽然频率较低，但 64bit 数据路径同样会带来不低的切换活动。Online Softmax 模块的面积和切换范围都相对较小，因此在总功耗中的占比预计不会像其时序重要性那样突出。待后续引入更稳定的门级网表与活动文件后，可再补充 VCD/SAIF 驱动的动态功耗分析与静态泄漏分析。

### 10.4 DRC \& LVS 验证

基于 Cadence 的完整后端尚未开展，因此目前没有可报告的 DRC 与 LVS 结果。现阶段使用 Yosys+iEDA 的目的主要是进行中前端结构收敛，而不是替代完整签核流程。后续若项目进入版图阶段，应在统一工艺库和约束环境下补齐版图生成、DRC、LVS、IR drop 和功耗完整报告。

### 10.5 总结

基于 icsprout55 的当前工作已经足够支持一个明确判断：项目的中前端热点和优化方向已被较清晰地定位。倒数与 Online Softmax 路径已经证明能够通过适当流水化达到或超过 500MHz；Normalization 有改善但优先级次之；QK 路径在本轮通过全流水乘法—加法树重构后已经被显著推进到 400MHz 以上，但仍是距离 500MHz 最近却也最难完全闭合的关键瓶颈。基于 Cadence 的完整物理实现尚未启动，但这并不妨碍当前基于 pre-P\&R 的结果对主线架构演进产生直接指导价值。

### 10.6 自评：`syn/` 覆盖完整性与自顶向下 PPA 估算

本小节仅用于自评，不作为正式报告对外展示内容。首先从 `syn/` 对 `rtl/` 的直接覆盖情况看，本轮已将审计结果保存到 [docs/report_0310/report/logs/syn_coverage_audit.txt](docs/report_0310/report/logs/syn_coverage_audit.txt)。当前 `rtl/` 下共检测到 `17` 个模块定义，而 `syn/` 中能够找到直接对应综合目录的仅有 `7` 个，直接覆盖率约为

$$
\frac{7}{17} \approx 41.2\%.
$$

未被直接覆盖的模块包括 `fa_dma_reader`、`fa_dma_writer`、`fa_attention_core`、`fa_o_normalize_block`、`fa_online_softmax_pair`、`fa_qk_dotprod_slice`、`fa_row_context_rf`、`fa_tile_compute_engine`、`fa_attention_ip_top` 与 `fa_perf_counters`。这说明当前 `syn/` 的组织方式更偏向“对关键瓶颈模块和实验版本做定点分析”，而不是“对仓库全部 RTL 做系统性全覆盖综合”。若从工程成熟度角度打分，这一状态足以支撑架构决策，但还不足以支撑一份完全严格的 top-down PPA 台账。

其次，从主线实例化关系看，当前 `fa_attention_ip_top` 直接例化 `1` 个 `fa_axi_lite_regs`、`1` 个 `fa_perf_counters`、`1` 个 `fa_dma_reader`、`1` 个 `fa_dma_writer` 与 `1` 个 `fa_attention_core`；`fa_attention_core` 内部再直接例化 `1` 个 `fa_qk_dotprod_slice`、`2` 个 `fa_mul_sat_q8_8`、`1` 个 `fa_online_softmax_pair`、`1` 个 `fa_recip_nr_q16_16` 与 `1` 个 `fa_o_normalize_block`。因此，若只看“当前已在主线中真正被使用”的模块，直接有精确综合数据的只有 `fa_axi_lite_regs`、`fa_mul_sat_q8_8` 与 `fa_recip_nr_q16_16`，其余关键块仍需要通过实验版本间接估算。

为了得到可用的 top-down 粗估，本报告采用“主线实例数 × 当前最佳候选模块面积”的保守方法，对未来主线若吸收最佳实验结构后的核心面积做一个下界估计。参与估算的单模块面积分别取：`fa_axi_lite_regs=4399.64`，`fa_mul_sat_q8_8=4469.36`，`fa_recip_nr_q16_16(exp_c)≈60594`，`fa_online_softmax_ctx(exp_d)=27216.28`，`fa_o_normalize_block_pipe(exp_d)=238672.84`，`fa_qk_dotprod_slice_pipe(exp_h)=286906.48`。按 `1×AXI-Lite + 2×mul_sat + 1×recip + 1×softmax + 1×normalize + 1×QK` 相加，可得到一个“只覆盖主要已知计算块”的面积下界：

$$
4399.64 + 2\times 4469.36 + 60594 + 27216.28 + 238672.84 + 286906.48 = 626727.96.
$$

这个 `626727.96` 只能视为**核心已知块的面积下界**，因为它还没有计入 `fa_attention_core` 本身的控制逻辑、`fa_dma_reader`、`fa_dma_writer`、`fa_perf_counters`、顶层 glue logic，以及更重要的片上 buffer / 寄存阵列在完整顶层中的真实物理代价。换言之，如果未来把 `exp_h + exp_d + exp_d + exp_c` 这组最佳候选真正集成进主线，那么完整顶层的面积只会比这个数字更高，不会更低。

从时序角度看，这个自评还揭示了一个很关键的现实：当前 `syn/` 最强的一组数据并不是“当前主线模块原封不动综合”的结果，而是“若主线吸收最佳实验结构后可能达到的局部能力”。也就是说，`syn/` 对“候选最优微结构”的覆盖反而比对“当前主线精确净表”的覆盖更完整。因此后续若要把自评真正做扎实，优先级应是：第一，补齐 `fa_attention_core` 与 `fa_attention_ip_top` 的直接综合；第二，补齐 `fa_dma_reader`、`fa_dma_writer` 和 `fa_perf_counters` 的模块级面积/时序；第三，在主线正式集成 `fa_qk_dotprod_slice_pipe` 与 `fa_online_softmax_ctx` 后再生成一版新的 top-level pre-P\&R 结果。届时才能把当前这套“模块最佳值拼接估算”升级为真正可信的系统级 PPA 评估。

## 11. 总结

### 11.1 已完成的题目要求功能性能指标

若对照赛题要求逐项审视，当前项目已经完成绝大多数 baseline 项目。online softmax 已在主线实现，并且从算法到独立实验都证明了这一思路的正确性；K/V tiling 与 tile 级流式调度已完整落地；输入输出采用 Q8.8 定点表示，内部累计精度满足高于 32bit 的要求；顶层具备 AXI-Lite 控制与 AXI4 Master DMA 数据接口；寄存器映射已按要求实现；禁止显式存储完整注意力矩阵的设计约束已被满足；端到端周期与精度指标也已达到当前 baseline 目标。若从 bonus 角度看，perf counters、双缓冲预取、CModel 架构建模、QK 深流水实验和 LLM 接入方案研究，都已经形成具有扩展潜力的成果。

因此，当前项目最重要的工作重心已经从“把功能做出来”转变为“把结构做得更强、更规整、更容易在工艺约束下收敛”。在这一背景下，下一步最推荐的动作不是再盲目扩展新功能，而是优先把独立实验中已经验证有效的 QK 与 Online Softmax 优化真正吸收回主线，以获得更好的频率潜力和更清晰的系统节奏。
