## 8. IP 核接入大模型推理

### 8.1 模型与推理框架

关于 LLM 接入，本项目已经完成较为系统的可行性分析。总体思路是在 C/C++ 推理框架中拦截 attention 模块调用，把原本由 CPU 完成的 SDPA 运算替换为 RTL IP 或其 Verilator/DPI-C 封装接口。理想情况下，软件侧只需要完成三件事：第一，把进入 attention 的浮点张量量化为 Q8.8；第二，把量化后的 Q/K/V 放入一段 DMA 可见内存；第三，启动 IP 并在完成后把 O 结果从 Q8.8 恢复成浮点再接回后续网络层。

需要指出的是，若完全不修改当前 RTL 主线，则模型选择必须考虑 `head_dim` 与上下文长度的兼容性。当前 IP 以 `D=64` 为默认参数，因此更直接匹配的是 `head_dim=64` 的模型或经过裁剪后的实验模型。若仍坚持沿大纲中最初提到的 `Qwen2.5-0.6B` 继续推进，则必须先确认该模型的 `head_dim` 是否与当前 IP 对齐；若不对齐，就需要将硬件扩展到 `D=128`，或者在软件侧做明确的模型裁剪与验证说明。从现有调研结论看，短期更稳妥的方案是优先选择 `head_dim=64` 的小模型或做受控实验模型，以降低接入阶段的不确定性。

### 8.2 针对 IP 核的推理引擎指令流优化

一旦把 attention 核从纯软件函数替换为硬件外设或其仿真模型，推理引擎层面的编排就变得重要起来。当前 IP 天然支持 tile 化，因此软件侧最直接的优化是让 `run.c` 或等价推理框架把 Q/K/V 的地址组织成与 IP tile 边界一致的布局，减少边界打包和额外拷贝。若未来要支持长于 `S=256` 的上下文，则更需要在推理框架层实现外层 block 调度，把一个长序列拆成多个 `256` 长度的 block，并结合外部存储层次或 scratchpad 做双缓冲搬运。

但需要注意，若要对大于 `256` 的上下文做严格等价的 FlashAttention block merge，IP 需要暴露中间的 $m$ 和 $l$ 状态，或者支持“续算模式”。如果只输出最终归一化后的 O，而不输出 block 级统计状态，那么多个 block 的结果无法在软件层无损合并。因此，当前推理引擎优化可以分成两个层次。第一个层次是不修改 RTL、仅在 `S\le 256` 的范围内做端到端联合仿真；第二个层次是为了支持更长序列，在 IP 协议层增加中间状态可见性，使软件得以正确完成 block merge。当前项目已经完成第一个层次的方案论证，第二个层次则属于 bonus 与系统扩展方向。

### 8.3 实测结果对比

`inference/native` 已经保留了一组本机 Q8.8 attention 替换实验结果，本轮未再重复长耗时跑批，而是把现有结果统一收集到 [docs/report_0310/report/logs/native](docs/report_0310/report/logs/native)。其中可直接引用的文件包括性能日志 [docs/report_0310/report/logs/native/perf.log](docs/report_0310/report/logs/native/perf.log)、trace [docs/report_0310/report/logs/native/trace.log](docs/report_0310/report/logs/native/trace.log)、吞吐汇总 [docs/report_0310/report/logs/native/q8_8_perf_results.csv](docs/report_0310/report/logs/native/q8_8_perf_results.csv) 与文本对比 [docs/report_0310/report/logs/native/q8_8_text_results.csv](docs/report_0310/report/logs/native/q8_8_text_results.csv)。

从文本一致性看，当前 CSV 共记录 `10` 组 prompt，其中 Q8.8 输出与 FP32 输出“完全一致”的只有 `2` 组，按严格字符串口径的 match rate 为 `20%`，统计摘要已单独存放在 [docs/report_0310/report/logs/native/native_metrics_summary.txt](docs/report_0310/report/logs/native/native_metrics_summary.txt)。这说明：一方面，Q8.8 attention 路径已经能够稳定跑通完整推理流程；另一方面，若以最终生成文本逐字一致作为标准，当前定点替换仍会带来明显语义漂移，因此后续对接 RTL 时必须把“是否能跑”与“文本是否严格保持”分开讨论。

从吞吐数据看，`10` 组样本上的平均结果为：FP32 路径 `QKV=7.969 GMAC/s`、`ATTN=1.936 GMAC/s`、`Pipeline=14.833 GMAC/s`、`ATTN_Time_%=13.840%`；Q8.8 路径则为 `QKV=8.243 GMAC/s`、`ATTN=5.582 GMAC/s`、`Pipeline=17.366 GMAC/s`、`ATTN_Time_%=5.440%`。虽然这些数字仍然混合了软件框架与本机 CPU 行为，但它已经说明当前 attention 替换后，热点占比确实从“明显 attention 主导”下降为“attention 不再是主导瓶颈”，这为后续用 DPI-C / RTL 核进一步替换 `flash_attn.c` 提供了现实依据。

具体到单条日志，[docs/report_0310/report/logs/native/perf.log](docs/report_0310/report/logs/native/perf.log) 记录了一次以 “Introduce the history of the Apple company.” 为 prompt 的本机运行。该运行成功完成了模型加载与文本生成，但回答内容明显偏保守、且未真正围绕苹果公司历史展开，这与上面的文本匹配率结论是一致的：当前 native Q8.8 路径已经能证明“算子替换可行”，但尚不能把其输出质量直接视为最终可交付的大模型推理质量。

### 8.4 结合 trace 的数据流分析与优化讨论

[docs/report_0310/report/logs/native/trace.log](docs/report_0310/report/logs/native/trace.log) 给出了 attention 替换在模型推理中的实际数据流展开。以 `pos=0` 的首 token 为例，每层都先执行 `Input RMSNorm`、`Q_proj/K_proj/V_proj` 与 `RoPE`，随后进入“FlashAttention Module Equivalent”阶段。trace 明确表明：当前模型的 attention 输入在每层表现为 `Q [14, 64]`、`K_cache [1, 2, 64]`、`V_cache [1, 2, 64]`，即共有 `14` 个 query head、每个 head 的 `head_dim=64`，而在序列初始阶段每个 head 只需要对极短的 K/V cache 做点积、softmax 与加权求和。

这个 trace 对硬件接入有三个直接启示。第一，当前 IP 的 `D=64` 与 trace 中的单头维度是对齐的，因此最小可行接入不必先扩维到 `128`，而是可以先围绕“单 head、head_dim=64、逐 head 调用”的方式完成 DPI-C 验证。第二，真正需要软件—硬件协同处理的是 head 维与层维的外层循环；对单次核调用而言，硬件只需负责某一 head 的 `QK^T + online softmax + PV`，而不需要吞掉整个 transformer layer。第三，decode 初期 K/V cache 很短，attention 计算量并不大，此时若直接调用 RTL 仿真核，调度、量化、内存拷贝和 DPI 交互开销很可能高于纯计算开销，因此应该优先在 prefill 或较长 decode 上下文中验证收益。

据此，后续优化建议可归纳为四点。其一，先把 `inference/native/flash_attn.c` 中单 head attention 调用封装成稳定接口，再以 DPI-C 替换其中的 `QK/softmax/PV` 核心，避免一开始就尝试把整层全部搬到 RTL。其二，优先复用当前 `trace.log` 中已经出现的 `head_dim=64` 场景，把硬件核视为“每 head 一次调用”的加速器，而不是要求硬件立即支持全部 `14` 个 head 并行。其三，在 RTL 侧应继续优先吸收 `fa_qk_dotprod_slice_pipe/exp_h` 与 `fa_online_softmax_ctx/exp_d` 这类已经完成频率验证的结构，因为它们恰好对应 trace 中最核心的两段计算。其四，若未来要覆盖更长序列，就必须把 block merge 所需的中间 `m/l` 状态或等效统计信息通过接口暴露出来，否则软件无法在多 block 场景下正确合并 attention 结果。


## 8.5 0324 接入状态：DPI 与 CModel 双后端并行

本阶段推理接入的本质变化是：attention 后端已经从单一软件路径扩展为可切换后端体系。

- `FLASH_ATTN_BACKEND=sw`
- `FLASH_ATTN_BACKEND=dpi`
- `FLASH_ATTN_BACKEND=cmodel`

并且 `inference/dpi/` 已形成 C API + Verilator wrapper + AXI-Lite/队列提交骨架，为后续真实 RTL 联调提供了稳定接口层。

## 8.6 DPI 现状与瓶颈量化

### 8.6.1 速度量级

当前 DPI 长跑样本显示：

- `prefill tok/s ≈ 0.0238`
- `decode tok/s ≈ 0.0232`

按 prefill 30 token 估算，首个 decode token 约需：

$$
30 / 0.0238 \approx 1260s \approx 21\text{分钟}.
$$

这与非 DPI 软件路径（几十 tok/s）存在数量级差距，说明当前瓶颈主要在仿真执行本体，而非单纯日志开关。

### 8.6.2 可读性问题

DPI 路径在 decode 早期出现 `token=72030 (/API)` 重复采样，形成模式坍缩。当前已通过三类证据定位：

1. top-k 直接对照（SW vs DPI）；
2. 层/头热力图（`layer23`、`head1/8~13` 热点明显）；
3. 最后激活统计（DPI `maxabs` 明显抬升）。

结论：问题已从“现象级”收敛到“logits 分布级”。

### 8.6.3 热点修复实验结果

热点回填（hotfix）能明显缓解 `/API` 坍缩，证明“晚层 attention 输出失配”是主链路；但该方案属于工程缓解，不是根因修复。

## 8.7 CModel 后端的阶段成果

### 8.7.1 可读性恢复

mode14 修复后，cmodel 在 chat/role 两类样本下均实现可读输出并与 sw 主干对齐。

### 8.7.2 速度对比

按 20260320 回归摘要，cmodel 在 chat 场景的平均吞吐处于可用区间：

- mode14: `avg_prefill≈23.933 tok/s`, `avg_decode≈16.649 tok/s`
- mode15+ks: `avg_prefill≈28.298 tok/s`, `avg_decode≈18.319 tok/s`（但质量不稳定）
- mode17+ks: `avg_prefill≈25.309 tok/s`, `avg_decode≈14.198 tok/s`

因此当前最合理的工程定位是：

1. cmodel 先作为稳定参考；
2. fixed 路线继续追质量，不以短期 tok/s 优势替代质量门槛。

## 8.8 从“可跑通”到“可交付”仍缺的三件事

1. DPI 需要从仿真级跑通转为质量稳定，先解决 decode 分布坍缩；
2. mode15/17 需要跨过 role prompt 稳定门槛，才能替代 mode14；
3. 推理框架需形成统一 benchmark 协议（同 prompt 集、同温度/采样、同统计窗口）以避免跨日志口径漂移。

这三件事完成后，IP 接入才可从“技术可行”进入“结果可交付”。
