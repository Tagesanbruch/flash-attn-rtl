## 9. Bonus 功能实现

虽然本报告主体仍以 baseline 为中心，但当前工程中实际上已经包含若干具有 bonus 性质的能力。第一，perf counters 不仅满足调试需要，也为后续系统级性能感知与软件侧调度提供了硬件事件基础。第二，K/V 双缓冲预取与主线控制空拍压缩，使当前设计不再只是“功能正确的串行原型”，而是具备了真实吞吐优化特征。第三，QK 点积的多轮实验已经从浅层归并推进到乘法首拍和全流水加法树，为进一步逼近高频提供了结构模板。第四，围绕长上下文支持、block merge、DPI-C 联合仿真和 LLM 接入的方案分析，也已把 bonus 扩展的技术边界梳理得较为清楚。

若从后续优先级看，最具价值的 bonus 方向有三个。其一，是把当前独立实验中验证有效的 QK 与 Online Softmax 结构真正回灌到主线，使 baseline 的频率潜力与结构清晰度进一步提升。其二，是扩展长上下文支持，为软件—硬件协同 FlashAttention 提供 block merge 所需的状态接口。其三，是完成 LLM 端到端接入，把“功能正确、周期可测”的 attention IP 进一步提升为“真实推理流程可调用”的硬件加速组件。

## 9.2 “完成”的分层定义

为了避免术语混淆，本报告把 bonus 完成度分 4 级：

1. L0 方案：只有文档。
2. L1 原型：有模块与局部测试。
3. L2 系统：有 top/IP 级回归证据。
4. L3 可并线：具备并入主线的质量与边界说明。

按该定义：

- #3/#4/#5/#9 已达 `L2`；
- #2 当前在 `L2`（顺序 MHA）；
- #1/#7 多处停留在 `L1~L2` 之间；
- #6/#8 仍在 `L0`。

## 9.3 当前最值得继续推进的 bonus 组合

从“收益/风险/可交付性”综合排序，建议优先级为：

1. `#2 + #9`（系统调度扩展）
2. `#3/#4/#5`（补覆盖与性能解释，收尾交付）
3. `#1`（BF16/FP16 收口成可比版本）
4. `#7`（INT8/FP8 保持研究线）
5. `#8/#6`（后置）

该排序与当前分支成熟度一致，也最利于在不破坏 baseline 的前提下持续产出可提交成果。

## 9.4 各 bonus 线的关键风险

1. #2：若要超越线性缩放，必须进入 core 重构，风险从“控制层”升级到“数据通路层”。
2. #9：控制语义和软件驱动耦合增强，若寄存器定义频繁变化会影响验证稳定性。
3. #1：吞吐与面积压力仍大，且与 baseline 主线差异过大，不宜直接并线。
4. #7：数值误差长尾明显，不能以局部 PASS 替代系统级可用性。
5. #8：会引入新接口验证体系，若与 DMA 版混杂开发容易放大维护成本。

## 9.5 建议的分支治理

下一阶段建议以 `baseline` 为稳定父分支，按技术族拆开：

1. `exp/multihead-queue`：合并 #2 与 #9 的系统调度线；
2. `exp/stream-top`：独立推进 #8；
3. `exp/fp16-bf16-next`：继续 #1；
4. `exp/int8-fp8-next`：继续 #7；
5. `exp/padding-mask-s512` 保持冻结收尾，仅补覆盖与报告。

这样可确保 bonus 之间可比、可审计、可回退。
