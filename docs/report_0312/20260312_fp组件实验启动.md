# 20260312 FP 组件实验启动记录

## 1. 目的

在 `exp/bonus1-bf16` 分支先不直接改顶层 attention RTL，而是先把 BF16 / FP16 的基础算术前端拆成独立实验模块，验证三件事：

1. **格式扩展代价**：BF16 / FP16 输入到 FP32 内部格式的转换复杂度；
2. **乘法前端代价**：进入 MAC 前，符号、指数、尾数拆解后的关键数据宽度；
3. **后续 RTL 路线**：确认 Bonus 1 第一阶段更适合走 `BF16 输入 + FP32 累加`，还是需要同时保留 FP16 支持。

### 2.1 `fa_bf16_to_fp32`

功能：将 16-bit BF16 直接扩展为 32-bit FP32 位模式。

结论：

- BF16 与 FP32 **指数位宽相同**，因此 widen 基本等价于高 16 位保留、低 16 位补零；
- 这意味着如果主路线选 BF16，**输入桥接成本非常低**。

### 2.2 `fa_fp16_to_fp32`

功能：将 IEEE FP16 扩展为 FP32 位模式。

结论：

- FP16 正常数转换只需指数偏置平移与尾数补零；
- **次正规数需要前导 1 检测与规格化**；
- 相比 BF16，FP16 widen 前端明显更复杂。

### 2.3 `fa_bf16_mul_prealign`

功能：对两个 BF16 输入做乘法前端拆解，输出：

- 符号异或；
- 无偏置指数和；
- 8-bit × 8-bit 尾数乘积；
- `zero / inf / nan / subnorm` 标志。

结论：

- BF16 有效尾数宽度仅 8 bit（含隐藏位），乘法前端压力较低；
- 适合进一步尝试接入“尾数乘积 + 高精度累加”的 mixed-precision 路线。

### 2.4 `fa_fp16_mul_prealign`

功能：对两个 FP16 输入做同类前端拆解。

结论：

- FP16 有效尾数宽度为 11 bit（含隐藏位）；
- 相比 BF16，乘法器与规格化前端都更重。

### 2.5 `fa_bf16_mul_norm_fp32`

功能：把 BF16 乘法前端给出的 `sign / exp_sum / mant_prod / special flags` 规格化并舍入为 FP32。

结论：

- BF16 乘积进入 FP32 时，主路径可以直接映射为“前导 1 检测 + 指数修正 + 次正规舍入”；
- 这说明 `BF16 multiply front-end + FP32 accumulate/back-end` 可以自然分成两级 primitive，而不必一开始就写完整大模块。

### 2.6 `fa_fp32_to_bf16`

功能：将 FP32 回写为 BF16，采用 RNE 舍入，并处理 `inf / nan` 特例。

结论：

- 该模块补齐了“**局部 FP32 累加，stage 边界 BF16 存储**”所需的关键回写路径；
- 从实现复杂度看，`fp32 -> bf16` 比 `fp16 -> fp32` 简洁得多，适合作为第一阶段固定回写口径。

### 2.7 `fa_bf16_mul_lane`

功能：把 `fa_bf16_mul_prealign`、`fa_bf16_mul_norm_fp32` 与 `fa_fp32_to_bf16` 组合成最小 BF16 乘法 lane。

结论：

- 该 lane 已能跑通 `BF16 x BF16 -> FP32 -> BF16` 的完整链路；
- 这为后续 dot-product lane 提供了可直接复用的基础单元。

### 2.8 `fa_fp32_accum`

功能：提供最小 FP32 累加器原语，接口包含 `clear / hold / valid`，内部通过本地 `fa_fp32_add` 完成逐拍累加。

结论：

- 这补齐了 `QK partial sum` 与 `PV/softmax` 局部和更新所需的最小累加状态机；
- 当前实验口径已经能独立验证“**局部 FP32 accumulator**”这件事本身，而不必等到大模块联调。

### 2.9 `fa_fp32_max_compare`

功能：提供 FP32 `gt / lt / eq / unordered` 判定，并直接输出 `max` 值。

结论：

- 这对应 online softmax 里的 `m_new = max(m_old, rowmax)` 基础原语；
- 对 `NaN` 和 `±0` 的口径也已固定，后续接入行级状态机时不需要再临时约定比较语义。

### 2.10 `fa_fp32_recip`

功能：提供最小 FP32 reciprocal 原语，当前实现采用 **`FP32 -> Q16.16 -> reciprocal -> FP32`** 的桥接近似。

结论：

- 对 softmax 分母 `1 / l` 而言，这已经足够作为第一阶段可验证 primitive；
- 它不是完整 IEEE 级高精度除法器，而是面向当前 Bonus 1 路线的 **工程近似版本**。

### 2.11 `fa_fp32_exp2_pwl`

功能：提供最小 FP32 `exp2` 近似原语，当前实现采用 **`FP32 -> Q8.8` 前端量化 + 16 段 PWL + `Q16.16 -> FP32`** 回写。

结论：

- 这补齐了 base-2 online softmax 所需的指数 primitive；
- 当前版本已经能覆盖 `[-16, 16)` 范围内的实验验证，足够支撑下一步把 `max / exp2 / reciprocal / accum` 串成更完整的数据通路。

### 2.12 `fa_bf16_dotprod_lane`

功能：把 `fa_bf16_mul_lane + fa_fp32_accum` 组合为最小 BF16 dot-product lane，并同时给出 `mul_fp32 / mul_bf16 / acc_fp32 / acc_bf16`。

结论：

- 这说明 Bonus 1 第一阶段已经从“单个 primitive”走到“lane 级组合”；
- 后续只需继续把 `max / exp2 / reciprocal` 接到行级状态，就能开始形成最小 online softmax update 子路径。

### 2.13 `fa_fp32_softmax_update_scalar`

功能：把 `bf16 widen + fp32 max/compare + exp2_pwl + q16.16 mul + reciprocal` 串成单拍标量 online softmax update 子块，输出 `m_new / l_new / acc_new / inv_l_new` 与中间 `exp_old / exp_new`。

结论：

- 这已经构成 Bonus 1 第一阶段最小可跑通的 softmax 状态更新路径；
- 当前实现口径不是完整 IEEE 高精度 datapath，而是面向工程验证的 `PWL + Q16.16` 近似组合；
- 其价值在于先把 primitive 组合边界、状态接口、golden 参考与误差级别固定下来，为后续行级/核级集成做准备。

### 2.14 `fa_fp32_softmax_row`

功能：在 `fa_fp32_softmax_update_scalar` 之上增加时序状态寄存器，支持 `valid / row_start / row_end` 驱动的逐元素行级 online softmax 更新，并输出每拍更新后的 `m / l / acc / inv_l`。

结论：

- 这标志着当前 BF16/FP32 softmax 路线已经从“组合标量子块”推进到“行级时序状态机”；
- 后续继续扩展时，重点可以转向多上下文并发、与 dot-product/ctx 路径对接，以及 stage-store 量化策略。

## 4. 当前判断

基于这组组件实验，可以得到一个更明确的工程判断：

1. **BF16 仍应作为 Bonus 1 第一阶段主路线**；
2. `BF16 -> FP32` bridge 极轻，明显优于 `FP16 -> FP32`；
3. 若内部采用 `BF16 mantissa multiply + FP32 accum`，硬件复杂度更可控；
4. `FP32 -> BF16` 回写已补齐，说明“FP32 局部累加 + BF16 stage-store”路线具备基本落地条件；
5. 最小 `bf16 mul lane` 已验证通过，可作为后续 `dot-product lane` 的直接基础；
6. `FP32 accum / max / reciprocal / exp2` 这组 softmax 核心 primitive 已全部具备独立实验支撑；
7. `bf16 dot-product lane` 已验证通过，说明乘法 lane 与 FP32 累加器接口已经贯通；
8. 纯 FP32 与 mixed-precision 两条 golden 路径已具备共享 Python 参考实现，可作为后续 softmax / datapath 联调的统一验收基线；
9. 最小 `fp32 softmax update scalar` 子块已验证通过，说明当前 primitive 组合已能支撑行级 online softmax 状态更新实验；
10. `fp32 softmax row` 已验证通过，说明 softmax 关键状态 `m/l/acc` 已完成时序封装；
11. FP16 更适合作为第二阶段兼容格式，而不是第一阶段主实现目标。

但这里需要补充一个更细的判断：

- **“FP32 累加”不等于“所有中间结果都用 FP32 存储”**；
- 真正浪费面积/带宽的通常不是 lane 内部的局部 FP32 accumulator，而是把跨 stage 的 SRAM/VRAM/FIFO 也全部升级到 FP32；
- 因此更合理的路线通常是：**局部计算用 FP32 accum，跨阶段存储尽量回落到 BF16**。

## 5. 外部论文与参考实现分析

本节补充阅读了两条外部路线：

1. `papers/arXiv-tex/2507.11331` 及其实现 `ref/FSA`；
2. `papers/arXiv-tex/2509.09505` 及其模拟器 `ref/PLENA_Simulator`。

虽然二者都不是“直接做一个与本项目同构的 BF16 FlashAttention IP”，但它们对**累加精度、阶段边界存储精度、softmax 所需 primitive** 给了很有价值的参考。

### 5.1 从 2507 / FSA 得到的启发

2507 这篇的主线不是“低成本 BF16 attention bridge”，而是把 FlashAttention 尽量融合进单一 systolic array 中。

但有两个点与本项目非常相关：

1. 文中在评估部分明确采用 **16-bit floating-point activation + 32-bit accumulation**；
2. 它把输出与中间累加放在单独的 **Accumulation SRAM**，而不是要求所有流经 datapath 的值都保持 32-bit。

从 tex 和源码看，`ref/FSA` 的实现方式本质上是：

- PE 乘法输入可以是较窄浮点；
- accumulator 使用更宽的 `accType`；
- `FPMacUnit` / `FPAccUnit` 同时支持 `elemType` 与 `accType` 两套格式；
- `exp2` 通过 PWL 完成；
- `reciprocal` 由独立 multi-cycle 除法路径完成；
- 比较器负责 `rowmax` / `max` 路径；
- 最终通过 rounding/cvt 在不同精度之间转换。

这说明它并不是“全系统 FP32 化”，而是采用了更典型的混合精度结构：

- **输入/乘法格式较窄**；
- **累加/关键归一化状态更宽**；
- **边界处显式 round/cvt**。

因此，如果本项目坚持 FlashAttention 原始数值语义，2507 给出的结论更偏向：

- `Q·K` 的 partial sum、
- online softmax 的 `l` / `O` 累加状态、
- 以及 reciprocal 之前后的关键状态

保留较高精度是合理的；问题不在于“要不要更宽累加”，而在于**宽精度状态究竟停留在哪一层**。

### 5.2 从 2509 / PLENA 得到的启发

2509 的路线与本项目差异更大：它主打的是 long-context 推理优化与 asymmetric precision，而不是纯粹的 BF16 FlashAttention datapath 复刻。

但它恰好给出另一个很重要的工程答案：

- **HBM/外存侧用更激进的低精度格式（MXFP/MXINT）**；
- **片上 Vector SRAM / Scalar FP 路径用 plain FP**；
- 当前配置里 `exponent=8, mantissa=7`，本质上就是 **BF16 风格片上格式**；
- 测试与模拟中，很多算子采用 **float32 accumulation + BF16 intermediate storage**。

在 `ref/PLENA_Simulator` 里能直接看到这种分层：

- `plena_settings.toml` 中片上 `MATRIX_SRAM_TYPE`、`VECTOR_SRAM_TYPE`、`SCALAR_FP` 都是 `E8M7`；
- HBM 权重/KV/激活则用 `MX` 格式，带独立 scale；
- `transactional_emulator/testbench/ffn_test.py` 明确写了 `float32 accumulation, BF16 intermediate storage`；
- `transactional_emulator/testbench/gelu_test.py` 也显式模拟了“每一步算完先落 BF16，再进入下一步”的误差传播；
- `flashattn_prefill_test.py` / `flashattn_decode_test.py` 则把 online softmax 所需的 `exp_m_res`、`exp_sum_new` 单独作为关键中间状态进行校验。

这一路线给本项目的启发不是“直接照抄 MX 数据格式”，而是：

1. **没有必要把所有中间 SRAM 都升级成 FP32**；
2. 更现实的折中是：**局部运算高精度，stage 边界 BF16 化**；
3. 如果以后进一步做更激进低精度，必须补上 **cast / quant-dequant / scale metadata** 这整套桥接逻辑。

### 5.3 对“FP32 累加是否浪费”的结论

结合 2507、2509 与当前实验，可以把这个问题拆成三层：

#### A. 局部 accumulator 用 FP32，是否浪费？

**不算太浪费，而且很常见。**

原因是：

- `Q·K` 点积跨多个 lane 累加，动态范围和舍入误差都比较敏感；
- online softmax 中的 `exp_sum` 与 `O` 累积本身就是误差放大点；
- 若为了节省少量寄存器/加法器位宽而把这些都压回 BF16，后面往往要在 softmax 误差和极值 case 上补更多复杂修正。

#### B. 把所有中间 SRAM 都做成 FP32，是否浪费？

**是，通常这是最不划算的部分。**

因为这会同时放大：

- SRAM 容量；
- SRAM 端口能耗；
- DMA/搬运宽度；
- crossbar / mux / buffer 宽度；
- 回归和格式桥接复杂度。

#### C. 更合适的第一阶段方案是什么？

更推荐下面这条 **MVP 数值分层**：

1. **输入/输出主格式：BF16**；
2. **乘法前端：BF16 decode / prealign**；
3. **lane 内乘加与关键累加：FP32**；
4. **stage 边界存储：优先 BF16，必要状态保留更宽格式**；
5. **关键特例**：`exp_sum`、reciprocal 输入、最终 normalize 前的 `O` 累积，可以视误差结果决定是否保留 FP32 tile-local buffer。

这意味着第一阶段不应追求“整条链路 FP32 存储”，而应优先追求：

- **FP32 只停留在真正需要它的 accumulator / normalize 关键点**；
- **其余可回落状态尽快 downcast 到 BF16**。

### 5.4 结合外部分析后，本项目还缺哪些组件

结合当前已做的 11 个实验，Bonus 1 的最小 primitive 库已经从“格式前端”扩展到了“softmax 核心算子”。

已经补齐的组件包括：

1. **`fp32 -> bf16` downcast**
2. **`bf16 mul lane`**
3. **FP32 dot-product / sum accumulator primitive**
4. **FP32 max / compare primitive**
5. **FP32 reciprocal primitive**
6. **FP32 exp2 / PWL primitive**

此外，验证基础设施侧也已补齐：

7. **共享 golden 路径工具**
	- 纯 FP32 reference；
	- `BF16 input + FP32 accum + BF16 stage-store` reference。

在此基础上，若要把 Bonus 1 从“算术 primitive 实验”推进到“可落地 datapath”，当前仍需继续补齐：

#### 第一层：点积与归一化核心

1. **在线 softmax 更新 primitive 组合**
	- 把 `max / exp2 / l update / reciprocal` 串成可复用子块；
	- 为后续 `m/l/O` 状态机实验提供直接接口。

#### 第三层：stage 边界与状态管理

2. **关键状态寄存器/缓冲定义**
	- `m_old / m_new`
	- `l_old / l_new`
	- `o_old / o_new`
	- 明确哪些必须 FP32，哪些允许 BF16 存储。

3. **BF16/FP32 cast 边界规范**
	- 在哪个 stage 进入 FP32；
	- 在哪个 stage 回落到 BF16；
	- 避免“内部悄悄升精度/降精度”导致验证口径混乱。

4. **误差基准与 golden 路径**
	 - 至少要同时有：
		- 纯 FP32 reference；
		- `BF16 input + FP32 accum + BF16 stage-store` reference；
	 - 否则无法判断误差来自算法还是来自 stage 边界量化。

### 5.5 对当前分支的直接建议

基于上述参考，我不建议下一步直接做“全 FP32 SRAM 版 attention core”。

更合适的是：

1. 保持 **Bonus 1 主路线 = BF16 输入 / FP32 局部累加**；
2. 明确 **stage-store 默认 BF16**；
3. 只对 `exp_sum`、normalize 前 `O` 累积这类关键状态保留“可选 FP32 buffer”方案；
4. 当前已具备 `fp32->bf16`、`bf16 mul lane`、`fp32 accum/max/recip/exp2` 与 `bf16 dot-product lane`，下一步应转向更高层的 softmax 组合与状态边界定义。

## 6. 下一步建议

建议按以下顺序继续推进：

1. 组合出最小 **online softmax update** 子路径，把 `max / exp2 / reciprocal / accum` 连起来；
2. 明确 `l / O` 哪些状态必须 FP32 常驻，哪些可在 stage 边界回落 BF16；
3. 增加 `BF16 input + FP32 accum + BF16 stage-store` 的 golden 路径与误差基准；
4. 等这些 primitive 稳定后，再考虑进入 `rtl/core/` 的 attention datapath 变体。
