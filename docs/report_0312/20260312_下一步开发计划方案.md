# 2026-03-12 下一步开发计划方案

## 1. 目的与输入依据

本文档结合以下三份外部调研报告：

- [report/20260312-chatgpt.md](../../report/20260312-chatgpt.md)
- [report/20260312-gemini.md](../../report/20260312-gemini.md)

并以当前仓库**实际源码、分支状态、已完成验证结果**为最终裁决依据，给出 FlashAttention IP 的下一步开发计划。这里特别强调：外部调研只作为路线参考，优先级判断必须服从当前工程现实，而不是重新回到已经完成或已经被证伪的方向。

截至当前时点，仓库已经在独立 bonus 分支上完成：

- Bonus 2：多 head（`exp/bonus2-mha`）

- Bonus 5：其他定点格式 `Q6.10/Q4.12`（`exp/padding-mask-s512`）
- Bonus 9：DMA / 任务队列（`exp/bonus9-task-queue`）

因此，下一步计划的核心问题已经不再是“先做 MHA 还是先做 task queue”，而应转为：

1. 如何把已完成的 5 项 bonus 稳定下来；
2. 剩余 Bonus 1/6/7/8 中应该优先做哪一项；
3. 如何在不污染 baseline 主线的前提下继续推进新的展示点与研究点。

## 2. 三份调研报告的共识与分歧

### 2.1 共识

三份报告虽然排序略有差异，但有三个强共识：

1. **多 head 与任务队列属于“高展示价值、低侵入”的优先方向**；
2. **AXI4-Stream 改动顶层协议与验证环境，优先级不应过高**；
3. **低精度/浮点路线需要单独分支推进，不能直接掺入当前稳定 datapath。**

这些判断与当前仓库状态是吻合的：因为 Bonus 2 和 Bonus 9 已经被独立分支完成，所以未来优先级应自然后移；而 Bonus 8、Bonus 1/7 仍未落地，说明它们确实更难、更慢、更需要研究分支。

### 2.2 分歧

三份报告的主要分歧只有两点：

1. **MHA 与任务队列哪个更该先做**
   - ChatGPT / Miromind 更偏向先做 MHA；
   - Gemini 更偏向先做任务队列；
   - 当前仓库中，这一争论已经没有实际意义，因为两项都已完成独立版本。

2. **下一步数值路线选 BF16/FP16 还是 INT8/FP8**
   - ChatGPT 倾向先做 BF16/FP16；
   - Gemini 明确推荐 BF16 优先；
   - Miromind 更偏向先试 INT8；
   - 结合当前工程现状，本项目更适合**先做 BF16/FP16，再看 INT8/FP8**。原因见第 4 章。

## 3. 当前工程现实下的路线重排

如果只按题目剩余未完成 Bonus 来看，当前待选项是：

- Bonus 1：BF16/FP16
- Bonus 6：Dropout
- Bonus 7：INT8/FP8
- Bonus 8：AXI4-Stream

其中：

- Bonus 6 对当前推理型 IP 的展示价值最低；
- Bonus 8 的协议改造面最大；
- Bonus 7 的数值/验证风险高于 Bonus 1；
- Bonus 1 既能展示“从定点升级到浮点/混合精度”，又比 FP8/INT8 更容易保持正确性闭环。

因此，结合三份调研与当前仓库实际状态，下一步开发优先级应重排为：

1. **P0：先稳定并制度化已完成的 5 项 bonus**
2. **P1：Bonus 1（优先 BF16，次选 FP16）**
3. **P2：Bonus 7（INT8/FP8，建议在 Bonus 1 之后立项）**
4. **P3：Bonus 8（AXI4-Stream wrapper）**
5. **P4：Bonus 6（Dropout）**

## 4. 推荐的下一步主开发方向：Bonus 1（BF16/FP16）

### 4.1 为什么推荐 Bonus 1 作为下一步主线

相比剩余三项未完成 bonus，Bonus 1 具有最好的综合平衡：

1. **展示价值高**：从 Q8.8 精确 attention 升级到 BF16/FP16，是一个很直观的“能力升级”；
2. **与当前 attention 结构兼容性更高**：相比 INT8/FP8，BF16/FP16 不需要一上来就引入复杂 block scaling metadata；
3. **验证路径更清晰**：可以直接对齐 PyTorch 的 `torch.float16` / `torch.bfloat16` 参考路径；
4. **更适合成为 Bonus 7 的前置台阶**：先把浮点通路与 softmax / reciprocal / normalize 重写稳定，再往 FP8/INT8 走会更顺。

### 4.2 为什么不是先做 Bonus 7（INT8/FP8）

当前仓库虽然已经有 Bonus 5 的 `Q6.10/Q4.12` 外部格式桥接，但那仍然是**内部统一 Q8.8** 的方案；这与真正的 INT8/FP8 低精度 attention 不是一回事。若直接跳到 Bonus 7，会同时遇到：

- dot-product 动态范围与 scale 设计问题；
- online softmax 指数与分母的稳定性问题；
- output cast 与 metadata 的系统联动问题；
- 更高的验证复杂度与更难的误差归因。

也就是说，Bonus 7 并不是“比 Bonus 1 更简单的低精度试点”，而是更重的研究型工作。因此应放到 Bonus 1 之后。

### 4.3 Bonus 1 的推荐实现形态

推荐首版采用：

- **输入：BF16**
- **关键累加：FP32**
- **输出：BF16 或 FP16**
- **控制面：保持 AXI-Lite + DMA 基本不变**
- **验证面：先做 core 级，再做 top/IP 级**

这里不建议一步到位做“全模块混合精度 + 所有 bonus 组合场景”，而是先定义一个最小可落地版本。

### 4.4 Bonus 1 的 MVP 定义

建议把 MVP 锁定为：

1. 新建独立分支 `exp/bonus1-bf16`；
2. 保持 `S=256`、`D=64`、单 head；
3. 保持 tiling / online softmax / DMA 组织不变；
4. 仅重写以下数值核：
   - `dot-product` 乘加路径
   - softmax 所需 `exp` / `max` / `sum`
   - reciprocal / normalize
5. 暂不与多 head、queue、S=512、padding 做组合验证；
6. 先达到“功能正确 + 误差可解释 + cocotb 可跑通”的最低闭环。

### 4.5 Bonus 1 的阶段计划

#### Phase A：参考模型与位宽口径先行

先不要直接写 RTL，而是先建立 Python/CModel 的 BF16 路径，明确：

- dot-product 中间量是否统一转 FP32；
- online softmax 的 `m/l/acc` 分别使用什么格式；
- reciprocal 采用 LUT、NR 还是混合策略；
- 输出格式是 BF16 还是再裁回 FP16。

这一阶段的产出应是：

- 一份 BF16/FP16 数值方案文档；
- 一套 Python 参考实现；
- 一组误差基准数据。

#### Phase B：先落 core 级 MVP

优先在 `fa_attention_core` 上闭环，不急着改 top：

- 建一个 `fa_attention_core_bf16` 测试目标；
- 只验证单任务、单 head、`S=256`；
- 把 fixed-like 对照切换为 BF16/FP32 双参考；
- 先不要求 perf counters 全部闭合。

#### Phase C：再接 top/IP 级

在 core 通过后，再把新数据格式接入 top/IP：

- 新增 `REG_DATA_FMT` 扩展枚举，纳入 BF16/FP16；
- DMA 入口/出口加入 BF16/FP16 pack/unpack；
- top cocotb 增加 full-run case；
- 重新读取 `cycles` / `rd_cmd` / `rd_beat` / `wr_cmd` / `wr_beat`。

#### Phase D：再决定是否扩大覆盖

只有在单 head BF16/FP16 完全稳定后，才考虑与现有 bonus 分支组合，例如：

- BF16 + multi-head
- BF16 + task queue
- BF16 + `S=512`

这些都不应进入第一轮目标。

### 4.6 Bonus 1 的模块级任务拆分

为了把 Bonus 1 从“方向判断”落到真正可执行的工程任务，建议按模块拆分，而不是按抽象概念分工。

#### 任务 A：数据格式与寄存器定义

涉及模块：

- `rtl/bus/fa_axi_lite_regs.sv`
- `rtl/top/fa_attention_ip_top.sv`
- 对应 cocotb `test_fa_attention_ip_top_regs.py`

具体任务：

1. 扩展 `REG_DATA_FMT` 编码，明确 `Q8.8 / BF16 / FP16` 的枚举；
2. 定义内部活动格式与外部格式的关系，避免“外部 BF16、内部仍被默默转回 Q8.8”这种语义歧义；
3. 明确软件可见的默认值、非法值处理与回读行为；
4. 在 top 级把数据格式一路传到 compute core。

#### 任务 B：输入 pack/unpack 与 DMA 桥接

涉及模块：

- `rtl/top/fa_attention_ip_top.sv`
- `rtl/core/fa_attention_core.sv`
- 可能新增格式转换 helper 模块

具体任务：

1. 明确 BF16/FP16 在 AXI beat 内的打包方式；
2. 在 DMA 读出后将输入转换为 core 内部使用的格式；
3. 在 DMA 写回前将输出重新编码回目标格式；
4. 确保转换逻辑与 `STRIDE_BYTES`、tile unpack 流程不冲突。

如果第一阶段决定“内部直接跑 BF16 + FP32 accum”，则这里的桥接逻辑要尽量轻量，避免重新引入大量格式来回切换。

#### 任务 C：QK 点积路径重写

涉及模块：

- `rtl/core/fa_qk_dotprod_slice.sv`
- 可能新增 BF16/FP16 乘法原语

具体任务：

1. 明确输入是 BF16 还是 FP16；
2. 明确乘积结果与累加器位宽，推荐先使用 FP32 accum；
3. 保持现有 `DP_LANES` / `ROW_PAR` / chunk 化接口尽量不变；
4. 优先保证功能闭环，而不是一开始就追求高频 leaf。

#### 任务 D：online softmax 数值核重写

涉及模块：

- `rtl/core/fa_online_softmax_ctx.sv` 或其 BF16/FP16 变体
- 可能新增 `exp` / reciprocal 子模块

具体任务：

1. 重新定义 `m/l/acc` 的格式；
2. 明确 `exp` 的实现路线（LUT、base-2 近似或其它）；
3. 明确是否继续保留 `SOFTMAX_CTXS=4` 的多 context 交错；
4. 在数值上优先保证不溢出、不失稳，再看周期与面积。

这一任务是 Bonus 1 的核心风险点，应优先配套 Python/CModel 的中间量对照。

#### 任务 E：normalize 与输出裁回

涉及模块：

- `rtl/core/fa_recip_nr_q16_16.sv`（如不再适用则需替换）
- `rtl/core/fa_o_normalize_block.sv`

具体任务：

1. 若分母与累加器已改为浮点，需要重新设计 reciprocal 路径；
2. 重新定义 normalize 的乘法与舍入策略；
3. 明确输出回落到 BF16 还是 FP16；
4. 给出与 FP32 golden 的误差分解。

#### 任务 F：验证与比对工具链

涉及模块/文件：

- `dv/cocotb/tests/test_fa_attention_core.py`
- `dv/cocotb/tests/test_fa_attention_ip_top_regs.py`
- `cmodel/` 与 Python 参考脚本

具体任务：

1. 增加 BF16/FP16 golden 路径；
2. 增加中间量 dump 选项，用于比对 `score / max / sum / acc / norm`；
3. 区分 core 级和 top 级 smoke/full-run；
4. 保留与 baseline Q8.8 的对照，避免新路线把旧行为悄悄带坏。

#### 任务 G：性能与 PPA 复盘

涉及产出：

- perf counters 对比
- `experiments/` 中必要的 leaf 级实验

具体任务：

1. 至少对 QK、softmax、normalize 三条关键路径重新评估时序代价；
2. 与当前 Q8.8 baseline 比较 `cycles`、关键 perf counter 与面积趋势；
3. 决定 Bonus 1 是否值得继续扩展到多 head / queue / `S=512`。

### 5.1 推荐定位

Bonus 7 不建议作为下一步主开发目标，而建议作为：

- **在 Bonus 1 完成后启动的研究分支**；
- 或者与 Bonus 1 并行进行的“纸面设计 + CModel 试验”分支。

   - FP8 + block scaling
   - 还是 INT8 + per-tile/per-head scale

不建议直接在现有 `exp/route-a-low-precision-research` 名字下继续堆文档而不落代码。下一轮若真做 Bonus 7，应给出明确工程目标，否则它会长期停留在“研究名义存在、实现内容为空”的状态。

## 6. 后续开发方向：Bonus 8（AXI4-Stream）

### 6.1 当前建议

AXI4-Stream 依然有价值，但不建议立即做。原因有三：

1. 它会显著改变顶层数据平面与验证方式；
2. 当前项目主要展示链仍然是 AXI-Lite + DMA；
3. 没有明确 SoC 级联对象时，做出来的 stream 版本展示收益有限。

### 6.2 真要推进时的建议形态

若后续确实需要做 Bonus 8，建议采用：

- `compute core + wrapper` 的结构；
- 新建 `attention_stream_top` 包装器；
- 不要直接重写现有 top/IP。

这样可以把：

- 当前 DMA 版 top 保留为 baseline/bonus 旧版本；
- AXIS 版作为独立 wrapper；
- 核心计算逻辑最大化复用。

### 6.3 进入条件

Bonus 8 建议满足以下任一条件后再启动：

1. 需要和其他 stream IP 级联展示；
2. 已经完成 Bonus 1，数值面暂时告一段落；
3. 希望做一个更强 SoC 集成 demo。

---

## 7. 最低优先方向：Bonus 6（Dropout）

Dropout 当前不是一个值得优先实现的目标，原因很明确：

- 当前项目定位是推理型 attention IP，而不是训练型 attention accelerator；
- Dropout 对展示吞吐和带宽优势帮助小；
- 它会引入 RNG、seed、可复现性与额外验证成本。

因此，Bonus 6 建议明确放到最后，不作为近期计划的一部分。

## 11. 验证矩阵与资源估算建议

### 11.1 验证矩阵

为了避免新路线一开始就陷入“组合爆炸”，建议采用分层验证矩阵，而不是对所有 bonus 做全交叉覆盖。

#### Bonus 1 第一阶段建议只覆盖

| 维度 | 建议取值 |
|---|---|
| head | `1` |
| `SEQ_LEN` | `256` |
| mask | `causal=0/1` |
| valid_len | 不覆盖 |
| queue | 不覆盖 |
| data_fmt | `BF16`（可选 `FP16`） |

#### Bonus 1 第二阶段再覆盖

| 维度 | 建议取值 |
|---|---|
| head | `2/4` |
| `SEQ_LEN` | `256`，必要时补 `512` |
| valid_len | `192` |
| queue | `FIFO_DEPTH=4` |

换言之，推荐策略是：

1. **先保证单维闭环**；
2. **再做少量组合覆盖**；
3. **不要在第一个版本就和所有已完成 bonus 做笛卡尔积。**

### 11.2 计算资源与回归预算

根据当前仓库的回归规模，可以对后续验证成本做一个保守估算：

1. 顶层 `fa_attention_ip_top` 单次全量回归已经在几十秒量级；
2. `FIFO_DEPTH=8`、`S=512`、multi-head 等参数扩展会明显增加 Verilator 编译与运行时间；
3. 因此新数值路线的第一阶段应优先使用 **core 级用例**，避免每个小改动都触发大规模 top full-run。

建议的回归节奏是：

- 日常开发：`core` 小回归 + 1 个代表性 top smoke test；
- 每日收敛点：top full-run；
- 关键节点：再补参数点（如 multi-head / queue / `S=512`）。

### 11.3 人工分析时间预算

Bonus 1 与已有 Q8.8 路线最大的不同，不是 RTL 代码量，而是数值分析时间。因此建议明确预留：

- 至少 `30%~40%` 的时间用于参考模型、误差定位与中间量 dump；
- 不要把全部时间预算都压到“先把 RTL 写出来”。

这一点也是三份调研报告的共同暗示：**低精度/浮点路线的真正瓶颈在验证和数值稳定，而不是接口胶水逻辑。**
