# 2026-03-15 BF16/FP16 统一模式设计稿（单 RTL、运行时可切换）

## 1. 目标

在不复制一套新 RTL 的前提下，让当前 BF16 核心支持 FP16：

1. 单一控制器、单一 DMA/Buffer/调度框架；
2. 运行时通过寄存器选择 `BF16` 或 `FP16`；
3. 内部统一使用 FP32 累加与归一化，降低数值风险；
4. 对当前周期优化主线影响最小。

## 2. 非目标

1. 本阶段不引入 FP8/INT8 执行体；
2. 本阶段不重构成完整 MMA 阵列；
3. 本阶段不追求极限面积最优，优先保证功能与节奏。

## 3. 建议架构

## 3.1 顶层模式寄存器

新增 `PRECISION_MODE` 字段（建议放入 CFG 扩展位）：

- `0`: BF16
- `1`: FP16

同时增加只读状态寄存器回显当前模式，便于测试与驱动检查。

## 3.2 数据通路复用原则

1. Q/K/V/O 存储格式维持 16-bit，不改 DMA 宽度与地址步进；
2. 前端转换统一成：
   - `fp16_or_bf16_to_fp32(mode, x16)`
3. 计算主路径维持 FP32：
   - dot
   - score scale/mask
   - softmax update
   - acc update
   - normalize
4. 输出转换统一成：
   - `fp32_to_fp16_or_bf16(mode, x32)`

这样可最大化复用现有状态机和缓存组织。

## 3.3 需改造的模块边界

### A. 输入 widen

当前是 BF16 专用 widen，改为 mode-aware widen：

- 新模块：`fa_f16x_to_fp32`（`mode` 选择 BF16/FP16 解释）
- 或两个模块并存 + mux 选择输出。

### B. 输出 downcast

当前是 FP32->BF16，改为 mode-aware downcast：

- 新模块：`fa_fp32_to_f16x`
- 支持两种舍入策略（至少 RNE），并保留溢出处理一致性。

### C. softmax 输入格式

若软更新模块输入目前绑定 BF16：

- 方案 1：改为 FP32 输入（推荐，统一精度语义）；
- 方案 2：保持 16-bit 输入但增加 mode 解释。

优先建议方案 1，可减少格式耦合。

## 4. 时序/面积风险与规避

## 4.1 风险点

1. mode-aware 转换路径会增加组合复杂度；
2. mux 插入可能压缩 slack；
3. downcast 舍入逻辑在高频下容易成为局部热点。

## 4.2 规避策略

1. 转换模块边界前后各打一拍可选寄存（参数化开关）；
2. 模式选择尽量前置，避免在热路径深处多级 mux；
3. 保留 `BUILD_MODE` 编译开关：
   - `RUNTIME_DUAL`：单网表运行时切换
   - `STATIC_BF16` / `STATIC_FP16`：为时序收敛保底

## 5. 周期影响预期

若仅替换格式转换层，且主状态机不变，理论上：

1. `dp_run/softmax_prep/score_done` 计数不应发生结构性变化；
2. 总周期变化应主要来自控制边界与可能新增的寄存拍（若开启）；
3. 可通过 perf 计数做 A/B：BF16 old vs BF16 new-mode0 应基本一致。

## 6. 验证计划

## 6.1 功能正确性

每个模式至少覆盖：

1. noncausal 全量
2. causal 全量
3. trace 对齐（首分歧）
4. 随机种子与边界输入（大值、小值、零、符号混合）

验收门槛：

- BF16: 与当前 BF16 基线一致（MAE/MaxAE 不劣化）
- FP16: 对 FP32 参考满足预设门槛，并给出误差分布

## 6.2 性能一致性

必看计数器：

- `cycles`
- `compute`
- `dp_run`
- `softmax_prep`
- `score_done`
- `lane_idle`
- `tile_switch_bubbles`

验收门槛：

- BF16 mode0 相对当前基线周期漂移 <= 1%
- FP16 mode1 不出现结构性退化（例如 >10% 的无解释增长）

## 6.3 回归矩阵

| 模式 | causal | 数据规模 | 目标 |
|---|---|---|---|
| BF16 | off/on | S=256,D=64 | 与现基线对齐 |
| FP16 | off/on | S=256,D=64 | 功能通过 + 性能可接受 |
| BF16/FP16 | off/on | 边界输入集 | 稳定性检查 |

## 7. 落地顺序（建议 4 个小阶段）

1. 阶段 A：定义 `precision_mode` 寄存器并打通到 core
2. 阶段 B：输入/输出转换改为 mode-aware（仅 BF16 回归）
3. 阶段 C：打开 FP16 模式，补齐 cocotb 对比
4. 阶段 D：补 perf 对比与报告，冻结 BF16/FP16 收尾基线

## 8. 与后续 INT8/FP8 的接口关系

完成本稿后，建议抽象统一微接口：

- `dtype_in`
- `dtype_acc`
- `rounding_mode`
- `saturation_mode`

这样后续 INT8/FP8 可以在同一调度框架下扩展，而无需再改一次控制平面。

## 9. 一句话结论

BF16/FP16 在当前项目里最稳妥的方式是“单 RTL + 运行时 mode + FP32 累加复用”。这条路线能在较小工程风险下完成分支收尾，并为后续 INT8/FP8 预留干净接口。
