# 03 验证结果与完整周期评估

## 3.1 本轮使用的验证与评估流

本轮主要使用三类流程：

1. **完整周期与误差评估**：`make rtl-latency-profile`
2. **完整参数 attention core 验证**：`make test MODULE=fa_attention_core_full`
3. **顶层寄存器/接口验证**：`make test MODULE=fa_attention_ip_top`

其中：

- `rtl-latency-profile` 给出当前主线 RTL 的完整周期 CSV 与误差统计；
- `fa_attention_core_full` 负责在 `S=256, D=64, TQ=32, TK=64` 下做端到端功能验证；
- `fa_attention_ip_top` 负责检查题目要求中的寄存器、启动/完成语义与 `CYCLES` 行为。

## 3.2 当前 baseline 完整周期结果

### 主结论

当前主线 RTL 在 baseline 条件下处理一次 `S=256, d=64, causal` SDPA 的主结论是：

$$
	ext{Total Cycles} = 148{,}656
$$

题目要求为：

$$
\text{Cycles} < 300{,}000
$$

因此当前周期目标满足，余量为：

$$
300{,}000 - 148{,}656 = 151{,}344
$$

约等于 **50.4%** 的绝对余量，或约 **2.02×** 的目标余量。

需要特别说明：此前 `145,584 cycles` 与 0305 报告一致，并不是 profile 流程没有刷新，而是旧版主线 `fa_attention_core` 的 `S_NORMALIZE` 仍使用**内联除法**。本轮已修复为显式实例化 `fa_recip_nr_q16_16` 的流水归一化，因此新的周期结果才真实反映 reciprocal 主路径落地后的代价。

### 交叉验证结果

独立 cocotb 完整参数运行中，观察到：

- `Core done after 148682 cycles`

与 profiler 结果的差异仅为：

$$
148{,}682 - 148{,}656 = 26
$$

相对误差仅约 $0.017\%$。因此可认为两条流对当前主线周期结论是相互一致的。

## 3.3 周期分解

### 3.3.1 profiler 汇总结果

当前 `docs/data/20260304_rtl_summary.csv` 给出：

| 指标 | cycles |
|---|---:|
| `total_cycles` | 148,656 |
| `rd_q_cycles` | 2,048 |
| `rd_k_cycles` | 16,384 |
| `rd_v_cycles` | 16,383 |
| `wr_o_cycles` | 2,048 |
| `ms_compute_cycles` | 131,200 |
| `ms_normalize_cycles` | 2,056 |
| `ms_other_cycles` | 15,400 |
| `cs_dp_cycles` | 98,304 |
| `cs_score_cycles` | 32,768 |
| `cs_softmax_pv_cycles` | 32 |
| `cs_ctrl_cycles` | 96 |

### 3.3.2 计算视角的理解

从计算核内部拆分来看：

1. **点积阶段（DP）**：`98,304 cycles`
   - 是当前总周期中的最大头部；
   - 说明大部分时间仍然花在 `QK^T` 上。

2. **score 形成阶段**：`32,768 cycles`
   - 主要对应 scale、mask 与后续 softmax 前准备；

3. **归一化阶段**：`2,056 cycles`
   - 相对总周期占比很低；
  - 但修复后还新增了 reciprocal pipeline 启动等待，这部分被 profiler 计入 `ms_other_cycles`，因此 `ms_other_cycles` 从旧值 `12,328` 提高到了 `15,400`；
  - 换言之，归一化本身仍不是总周期主导，但它已经真实反映到端到端周期，不再被旧版内联除法“掩盖”。

4. **控制与其他阶段**：
   - `cs_ctrl_cycles = 96`
   - `ms_other_cycles = 12,328`
   - 说明控制开销存在，但不是当前 baseline 周期主瓶颈。

### 3.3.3 DMA 角度的理解

按当前参数：

- 总线宽度：128-bit = 16 bytes/beat
- 每行 `D=64`、元素 16-bit，因此每行数据量：
  $$64 \times 2 = 128\ \text{bytes}$$

据此可得 baseline 的理论 DMA 字节量：

#### Q 读入

- 256 行，每行 128 bytes：
  $$256 \times 128 = 32{,}768\ \text{bytes}$$

#### K 读入

- 每个 Q tile 都会遍历全量 K，共 8 个 Q tile；
- 每次全量 K 数据量为 32,768 bytes；
- 总计：
  $$8 \times 32{,}768 = 262{,}144\ \text{bytes}$$

#### V 读入

- 与 K 同量：
  $$262{,}144\ \text{bytes}$$

#### O 写回

- 256 行输出，每行 128 bytes：
  $$32{,}768\ \text{bytes}$$

#### 合计

$$
32{,}768 + 262{,}144 + 262{,}144 + 32{,}768 = 589{,}824\ \text{bytes}
$$

即当前 baseline 一次 attention 的外部主存 traffic 约为：

$$
576\ \text{KiB}
$$

这也解释了为什么当前设计虽然没有存储 `S×S` 矩阵，但仍然对 K/V 重复读带宽较敏感。

## 3.4 正确性结果

`rtl-latency-profile` 的 C++ TB 给出：

| 指标 | 数值 | 题目门限 |
|---|---:|---:|
| RTL vs FP32 `MAE` | 0.00291701 | <= 0.03 |
| RTL vs FP32 `MAX_AE` | 0.00588431 | <= 0.10 |

可见：

- 当前主线 RTL 的数值误差远小于门限；
- 当前 reciprocal / exp 近似方案在 baseline 下是可接受的；
- 后续如果为时序或面积做新近似替换，必须重新以此门限回归验证。

## 3.6 周期结论的工程意义

从赛题角度，当前 **148,656 cycles** 这一结果非常关键，因为它说明：

1. 当前设计即使在 500MHz 未完全闭合的情况下，**架构级周期数已经进入可提交区间**；
2. 后续若能继续提升频率而不显著增加 cycles，则 wall-clock latency 还能进一步改善；
3. 下一阶段优化重点应转向：
   - **同周期下冲频**；
   - **在不破坏正确性的前提下降面积/降带宽**；
   - 而不是再去做会大幅增加 cycles 的结构性回退。

本章最终结论是：

- 当前主线 RTL 的 baseline 周期目标**已经满足**；
- 当前主线 RTL 的误差目标**已经满足**；
- 当前主线 attention core 与 top-level 寄存器接口验证**已经满足**；
- 且该周期结果已经真实反映 reciprocal 流水落地后的主路径行为；
- 因而当前版本已经具备“baseline 功能与周期交卷”的基础；
- 剩余主要矛盾转移为：**500MHz 收敛与 top 级面积/实现闭环**。
