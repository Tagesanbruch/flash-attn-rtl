# 1 项目概述与赛题解读

## 1.1 项目目标

本项目目标是实现一个可综合的 FlashAttention-style 硬件 IP，在固定规模 `S=256, d=64, batch=1, head=1` 下完成 attention 计算，并满足控制接口、数据搬运、误差门限与性能约束。相较于“只做数学正确”的软件实现，硬件版本需要同时平衡四类约束：

1. **算法正确性**：输出与 FP32 golden 保持可控误差；
2. **结构正确性**：必须体现 online softmax 与 K/V tiling，且不能显式存储 `S×S` 矩阵；
3. **接口完整性**：需具备 AXI4-Lite 控制与 AXI4 Master DMA 数据通路；
4. **工程可交付性**：提供可复现验证、综合、时序与报告证据。

## 1.2 赛题硬约束（对实现最敏感的部分）

结合 `problem.md`，对工程实现影响最大的条款如下：

### (a) 算法与结构约束

- 计算目标为标准 SDPA：
  $$O = softmax(\frac{QK^T}{\sqrt{d}} + M)V$$
- 必须使用 online softmax；
- 必须对 K/V 做 tiling；
- 禁止存储 score/p 全矩阵。

这意味着设计不能走“先算完 `QK^T` 再做 softmax”的离线路径，而要将分块读入、增量归一化与输出累积融合在同一数据流中。

### (b) 定点与位宽约束

- 输入/输出统一 Q8.8；
- 点积累计位宽至少 32-bit（建议更高）；
- softmax 路径允许更高位宽与近似算法。

该约束直接决定了算子拆分方式：乘法器、累加器、指数近似与倒数近似必须在位宽、饱和与舍入上统一规则，否则端到端误差不可控。

### (c) 接口与运行模式约束

- 主机通过 AXI4-Lite 配置寄存器并启动；
- 加速器通过 AXI4 Master + DMA 搬运 Q/K/V/O；
- 需提供 CYCLES 与带宽统计（RD/WR bytes）用于性能评估。

因此，设计不是“纯计算核”，而是“控制 + 搬运 + 计算”的完整 IP。

## 1.3 当前工程定位

当前代码已具备“可扩展到完整 baseline”的骨架，但仍处于中期阶段：

- 已完成：
  - online softmax 核心子模块；
  - AXI-Lite 寄存器与状态流；
  - 模块级 cocotb 回归；
  - Python 对 torch 的误差评估链路；
  - 单模块综合/STA 流程。

- 尚未完成：
  - AXI4 Master DMA；
  - K/V tile 缓冲与调度；
  - RTL 端到端 `S=256,d=64,causal` 闭环；
  - top 级 PPA 与带宽统计。

因此本文的核心任务，不是“宣称全部完成”，而是把**已完成证据、关键缺口、可执行闭环路径**讲清楚。

## 1.4 报告组织原则

为了避免模板迁移导致的“内容错位”，本报告遵循三条组织原则：

1. 章节按 FlashAttention 的真实实现链路组织：需求 → 架构 → 算法 → RTL → 验证 → PPA → 闭环计划；
2. 每章都回答一个工程问题，例如“为什么必须 tiling”“当前 RTL 到底完成了什么”；
3. 每个结论尽量对应文件、脚本或数据，避免空泛描述。

## 1.5 本章小结

赛题真正难点不在单个算子，而在“用受限位宽和受限存储，把 online softmax 与 DMA 数据流稳定拼接起来”。后续章节将围绕这一主线展开。
