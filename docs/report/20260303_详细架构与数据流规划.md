# FlashAttention 端侧 IP：详细架构与数据流演进规划

基于对赛题（S=256, d=64, Q8.8位宽）以及前期架构调研（`report/miromind.md`）的充分分析，本规划将原有的粗略骨架扩展为**具备细粒度数据流、清晰模块边界和可执行状态机的确切实现方案**。

本规划解答三个核心问题：
1. **做什么**：内部计算组件与 SRAM 怎么切分（面积/门数受限下）。
2. **怎么编排数据流**：QK^T、Online Softmax、PV 计算如何与 DMA / Ping-Pong Buffer 配合流水。
3. **下一步执行计划**：如何把现阶段的“子算子层”缝合成“端到端全阵列”。

---

## 一、 顶层硬件组件切分与规模设定

为了在 $\le 2M$ 门（约折合 10~15 $mm^2$ 内）实现极致的资源复用并隐藏访存延迟，建议采用 **$16 \times 64$ 或 $32 \times 64$ 的基于脉动/向量运算的时分复用计算阵列**。考虑到 $d=64$ 是定长，且 $S=256$，我们将一个处理分块（Tile）的大小设为 **$T_q=32, T_k=64$**（以下以该参数为例描述）。

### 1.1 存储与缓存层 (Memory & Cache Plane)
赛题限制片上不能存 $S \times S$ 矩阵，必须极度控制 SRAM 面积。
- **K/V Ping-Pong Buffer (SRAM)**
  - **Buffer A & Buffer B** 双缓冲。
  - 每个 Buffer 容纳一个 K_tile (64行 $\times$ 64列) 和一个 V_tile (64行 $\times$ 64列)。
  - 大小算账：$64 \times 64 \times 2$ (Q8.8 16bit = 2 Byte) $= 8$ KB。
  - K 和 V 均为 8 KB。两个 Buffer 总计 32 KB。
  - 极小的 SRAM 占用极低的门数折算（远小于 2M 门预算）。
- **Q Buffer / Q Register Bank**
  - Q_tile 作为本地 Stationary 数据，缓存在靠近计算阵列的 Register Bank 中。
  - 容量：$T_q \times d = 32 \times 64 \times 2$ Bytes $= 4$ KB。
- **Row Context RF (m, l, acc)**
  - 维护当前 Q_tile 的 $T_q$ (32行) 状态。
  - 每行：`m` (16-bit), `l` (32-bit), `acc` (64×32-bit 累加和 = 256B)。
  - 共需 $32 \times (\sim 262B) \approx 8.4$ KB。

### 1.2 核心计算引擎 (Compute Plane)
- **MAC 计算阵列 (Multiply-Accumulate Array)**
  - 为匹配 $d=64$，设计为 **$32 \times 64$** 个 MAC 单元（约 2048 个 Multiplier）。
  - 支持 `16-bit×16-bit -> 32-bit` 的定点乘加。
  - **时分复用**：第一阶段执行 `Q_tile * K_tile^T` (产出 S_block)，第二阶段执行 `P_block * V_tile` (产出 O_acc_block)。
- **VFU (Vector Function Unit)**
  - 放置在阵列侧边（行维度），包含 32 个通道，每个通道涵盖：
    - Comparator (求 RowMax，更新 `m`)。
    - 减法器 (计算 $S - m_{new}$ 和 $m_{old} - m_{new}$)。
    - **PWL-EXP 模块** (`fa_exp_pwl_8seg_q1_15`)，使用 8 段线性插值求定点指数。
    - Adder (求 RowSum，更新 `l`)。
- **Reciprocal Unit (倒数/除法器)**
  - 行级处理流水线末端共享一个或少量 **牛顿-拉夫逊 (Newton-Raphson)** 倒数迭代器 (`fa_recip_nr_q16_16`)。
  - 仅在所有 K/V tile 循环结束后运行一次，计算 $1/l$，将最终的 `acc` 归一化。

## 二、 详细数据流与时空编排 (Dataflow Orchestration)

数据流的关键在于隐藏 AXI DMA 读取 K/V 的延迟，并实现 Online Softmax 前后依赖的数据持续流动。

### 假设场景设置
总规模：$S=256, d=64$
分块大小：$T_q=32, T_k=64$
总循环次数：
- **Outer Loop** (`q_idx` 从 0 到 7，共 8 次，每次处理 32 行 Q)。
- **Inner Loop** (`k_idx` 从 0 到 3，共 4 次，每次处理 64 行 K/V)。

### 详细流水线编排

**【外层循环 - 加载 Q】**
当进入某一个 `q_idx` 时：
1. **DMA Read Q**：触发 AXI 读取对应 $32 \times 64$ 的 Q_tile。
2. 存入本地 Q Buffer，并在整个内层循环期间保持驻留（Load Stationary）。
3. 初始化 `Row Context RF` 中当前 32 行的 `m = 负无穷`, `l = 0`, `acc = 0`。

**【内层循环 - 拼图式的块计算】**
对于 `k_idx` $= 0, 1, 2, 3$：

**并行流水级 1：DMA 取数 (Ping-Pong)**
- 若当前计算处理的是 Buffer A 中的 $K_{idx}, V_{idx}$，与之并行的，AXI DMA 开始配置预取 $K_{idx+1}, V_{idx+1}$ 放入 Buffer B。通过 Ping-Pong 交替，只要 DMA 带宽能撑住计算阵列的时钟周期，读取开销被完全隐藏。

**并行流水级 2：$QK^T$ (AttnScore)**
- 每一拍，K_tile 的一列（对应 $d=64$ 维空间）流过阵列。
- 与本地 Q Buffer 进行点积累加。经历 $d=64$ 个 cycle 后，在阵列内侧计算出完整的 $32 \times 64$ 的局部相似度矩阵 $S_{block}$。
- 为了应对 Causal Mask，可在此阶段增加逻辑：若当前行号 `i < 列号 j`，强制在输出 $S_{block}$ 结果上置换为 `NEG_LARGE`。

**并行流水级 3：Online Softmax 更新 (VFU 环节)**
- 针对前一级输出的每行 $S_{block}$ (共 64 个元素)：
  - **M 步**：遍历 64 个元素，得到 $m_{nxt} = \max(m_{cur}, \max_{j}(S_{i,j}))$。
  - **D 步**：计算校正系数 $e^{m_{cur} - m_{nxt}}$ (利用 `fa_exp` 原语)。并将旧的 `l` 和 `acc` 乘以此校正系数进行回退衰减。
  - **E 步**：对每一个 $S_{i,j}$ 计算 $P_{block} = e^{S_{i,j} - m_{nxt}}$。
  - **L 步**：$l_{nxt} = l_{cur} \cdot e^{m_{cur} - m_{nxt}} + \sum_{j} P_{block}$。

**并行流水级 4：$P \cdot V$ 累加计算**
- 算出的 $P_{block}$ 不写全矩阵大 SRAM，而是直接暂存进内部极小的流水线 Buffer（仅需存 $32 \times 64$ Q8.8 = 4 KB）。
- 阵列进入时分复用的“第二相”：
  - K 对应的是 $S_{block}$ 的计算，现在让 V_tile 流进该相同的乘加阵列。
  - 对 32 行并发，以 $P_{block}$ 作为行激活向量，计算与 V_tile 的矩阵乘法。
  - 产出局部输出 $\Delta O$，随后执行 `acc_nxt = acc_decayed + \Delta O`。

**【循环收尾 - 归一化与写回】**
当 4 个 K/V tile 全部迭代结束：
1. **Recip 级**：从 `Row Context RF` 中取出每行的 $l_{final}$，送入 `fa_recip_nr_q16_16` 计算其倒数 $1/l_{final}$。
2. **Norm 级**：将对应的 $acc_{final}$ 乘以倒数，得到归一化的最终单行输出 $O_i$。由于是 $d=64$ 个通道，该过程可以通过少量乘法器分拍完成。
3. **DMA Write O**：将完成的 32 行 $O_{tile}$ 通过 AXI AW/W 通道突发写回主存。

## 三、 基于当前 RTL 骨架的下一步执行细化

目前代码库中已经有了计算核子路径（`fa_online_softmax_update`, `fa_mul_sat_q8_8`, `fa_exp_*`, `fa_recip_*` 和基础的 `fa_core_controller`, `fa_axi_lite_regs`）。要实现上述架构，后续具体编码需拆解为四个战役：

### Phase 1：数据搬运面 (Data Mover Plane) 建设
*目的：构建 SRAM Ping-Pong Buffer 机制，使数据能从 AXI 源源不断流向片上。*
- **开发任务**:
  - 编写 `fa_dma_master.sv`，对接 AXI4 Master (AR/R 和 AW/W/B)。
  - 编写 `fa_tile_sram_bank.sv`，使用标准 Dual-Port RAM 形式，实现 Ping-Pong 封装。
  - 开发 `fa_dma_scheduler.sv`，根据寄存器的 `BASE/STRIDE` 参数自动生成逐行的 Burst 读写请求。
- **验证手段**: cocotb 下连接 Python AXI RAM 模型，只配置参数走一遍“空跑读取->写入”，验证带宽和地址计算，检查边界回绕问题。

### Phase 2：计算阵列的二维化 (Matrix Array Scaling)
*目的：将当前的标量算子扩展为多通道脉动/向量阵列，适应 $32 \times 64$ 吞吐。*
- **开发任务**
  - 使用现有的 `fa_mul_sat_q8_8`，将其包装为 `fa_mac_array_32x64.sv` 工具阵列。
  - 增加复用 MUX 逻辑，支持 `Mode 0: 算 Q*K^T`，`Mode 1: 算 P*V` 两种路由模式。
  - 开发行维度的在线更新组 `fa_row_context_rf.sv`。
- **验证手段**: 构造纯运算的 tb_mac_array 验证模式 0 与模式 1 下的数据位宽是否溢出/截断正确。

### Phase 3：Tile Loop 与流水控制面合并 (Control Loop Merge)
*目的：控制各个引擎的交织与数据依赖。*
- **开发任务**
  - 扩展已有的 `fa_core_controller.sv`。
  - 内部实现三个 FSM：
    1. **Master FSM**: 接收 `START`，派发 Q_loop 任务，等待所有 Q 行完成，宣告 `DONE`。
    2. **Tile FSM**: 发送 DMA 取数指令并管理 Ping-pong ptr（处理 `wait_for_dma`, `wait_for_compute` 的握手）。
    3. **Pipe FSM**: 发挥调度阵列执行 `LOAD_Q -> MAC_QK -> EXP/UPDATE -> MAC_PV -> RECIP/OUT` 指令字的作用。
- **验证手段**: Python 中打入 `S_q=32, S_k=64` 的单个缩尺测试，将中间的 `m`, `l`, `acc` 打印到日志中，并与 `dv/python/ref_attention.py` 环节的数据强行比特对齐验证。

### Phase 4：Top 集成与系统端到端对齐 (System E2E)
*目的：拼成完整赛题规定规格，进行全面统计与跑分。*
- **开发任务**
  - 顶层 `fa_attention_ip_top.sv` 端口配平（Lite 从机 + Master 主机 + 核心模块）。
  - 在 Controller 模块中加入对 AXI-Lite 中 `RD_BYTES`、`WR_BYTES`、`CYCLES` 寄存器的硬件打点支持。
  - 增加针对 `Causal Mask` 的 `j > i` 置大负值的过滤逻辑。
- **验证手段**:
  - `S=256, d=64` 满配运行。
  - 计算周期数，理论上每组外层($T_q$)耗时大约由内层 DMA 或者内层 MAC (4 组) 占优。通过 cycles 统计确认是否满足 < 300k cycles 的赛题硬底线。

## 四、 PPA 对账与风险声明
- **理论 Cycles 估算**：外层 8 次 $\times$ 内层 4 次 $\times$ (加载+计算 $\approx$ 128 cycle/tile) $\approx$ 4096 cycles，加上流水线启动/排空，理想情况下单次 attention 远远小于 300k cycles 的要求，即使串行跑也完全可达标。
- **风险**：Online softmax 的多级流水依赖 (算出 max 后再算 exp)，对布线和时序压力较大。
- **缓解计划**：在 VFU 模块中，从 Max $\to$ 减法 $\to$ 查表 $\to$ PWL 乗加 中间**强制插入 2 到 3 级 Register**，牺牲微小的 latency 换取较高的跑频。

## 五、2026-03-04 架构复核修正

- 原“4096 cycles 即可达标”的估算不适用于当前串行点积实现。
- 实测满参数结果：约 `4,511,050 cycles`，与 `<300k` 目标存在约 15 倍差距。
- 造成差距的主因是 `(qi,kj)` 对逐个串行计算且每次点积按 `D` 周期推进；当前架构需要并行 MAC 与访存重叠才能接近目标。
