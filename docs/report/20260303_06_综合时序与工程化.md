# 6 综合时序与工程化

## 6.1 工程化目标

本章关注两类问题：

1. 如何保证项目可持续迭代（构建、测试、脚本化）；
2. 如何逐步把模块级结果推进到 top 级 PPA 结论。

当前阶段的定位是“打通单模块综合/STA流程并沉淀统一入口”。

## 6.2 现有构建与脚本化能力

### 6.2.1 Make 入口

当前 `Makefile` 已支持：

- lint
- test
- regress
- compare-torch
- audit-algo
- sta-list / sta-module

这使得开发、验证、时序分析可以通过统一命令驱动，便于日常回归与答辩复现。

### 6.2.2 STA 模块映射与约束

- `cfg/sta_modules.mk`：维护模块与依赖映射；
- `syn/sdc/default_clocked.sdc`：时序模块约束；
- `syn/sdc/default_comb.sdc`：组合模块最小约束；
- `syn/scripts/sta_no_power.tcl`：规避组合模块 power 阶段崩溃。

通过这些文件，单模块从 netlist 生成到时序报告已形成固定流程。

## 6.3 当前 STA 结果边界

当前可得到的结论主要限于单模块：

- `fa_core_controller`、`fa_mul_sat_q8_8` 等模块可产出综合与时序报告；
- 报告可用于早期发现位宽、组合深度、关键路径问题；
- 不能替代 top 级结论，也不能直接作为最终赛题成绩依据。

换言之，当前 STA 价值是“排雷”和“趋势判断”，不是“最终签核”。

## 6.4 从单模块到 top 级的推进路径

要形成完整 PPA 结论，需要依次补齐：

1. top 数据通路（DMA+tiling）完成；
2. top 可综合 netlist 与完整 SDC；
3. 关键路径定位与微架构优化；
4. 功耗分析激励准备（VCD/SAIF）；
5. 报告口径统一（面积、频率、功耗、门数折算）。

每一步都应与对应验证数据绑定，避免“时序优化破坏功能”。

## 6.5 工程风险与控制手段

### 6.5.1 典型风险

- DMA 接入后状态交互复杂，回归不稳定；
- 近似算子插入流水后误差上升；
- 为追时序过度加流水导致控制复杂化。

### 6.5.2 控制手段

- 每次改动必须保留可回滚分支点；
- 功能回归和误差回归必须绑定执行；
- 将性能优化拆成独立 patch，防止“功能+优化”混改。

## 6.6 本章小结

工程化基础已经可支撑下一阶段快速推进。真正的里程碑是把当前“模块级时序可见”升级到“top 级 PPA 可交付”，其前提仍是先完成 DMA+tiling 端到端功能闭环。
