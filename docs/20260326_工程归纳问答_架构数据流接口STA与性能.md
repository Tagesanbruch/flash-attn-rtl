> 问题1：加速器顶层模块名、主要子模块、模块间接口分别是什么？

**回答**
- 顶层模块是 `fa_attention_ip_top`。
- 主要子模块：`fa_axi_lite_regs`（配置/状态）、`fa_dma_reader`（AXI读DMA）、`fa_dma_writer`（AXI写DMA）、`fa_attention_core`（计算与调度）、`fa_perf_counters`（性能计数）。
- 顶层对外接口：
  - AXI-Lite Slave：寄存器配置与读回。
  - AXI4 Master：DMA读写内存。
- 子模块间主要接口：
  - `core <-> dma_reader`：`dma_rd_cmd_*` + `dma_rd_data_*`。
  - `core <-> dma_writer`：`dma_wr_cmd_*` + `dma_wr_data_*`。
  - `core -> perf`：`ms/cs` 状态脉冲、recip事件、active_rows。

**证据**
- `rtl/top/fa_attention_ip_top.sv`：端口定义 + `u_regs/u_dma_rd/u_dma_wr/u_core/u_perf` 实例化。
- `rtl/bus/fa_axi_lite_regs.sv`：寄存器映射与AXI-Lite行为。
- `rtl/top/fa_perf_counters.sv`：计数器输入事件定义。

> 问题2：数据流具体是什么？Q/K/V 的 tile 尺寸、搬运顺序、片上缓存组织方式如何？

**回答**
- 默认参数：`SEQ_LEN=256, D=64, TQ=32, TK=64, BUS_W=128`。
- Tile与beat：
  - `ELEMS_PER_BEAT=8`（每拍8个Q8.8）。
  - `BEATS_PER_TILE_Q=256`（32x64/8）。
  - `BEATS_PER_TILE_KV=512`（64x64/8）。
- 搬运顺序（主状态机）：`S_LOAD_Q -> S_INIT_CONTEXT -> (S_LOAD_K -> S_LOAD_V -> S_COMPUTE)* -> S_NORMALIZE -> S_WRITE_O -> S_NEXT_Q`。
- 片上缓存组织：
  - `q_buf[TQ][D]`。
  - `k_buf0/1[TK][D]`、`v_buf0/1[TK][D]`（K/V ping-pong双缓冲）。
  - 行状态：`row_m[TQ]`、`row_l[TQ]`、`row_acc[TQ][D]`。
- 预取：`S_COMPUTE` 内 `PF_CMD_K/PF_DATA_K/PF_CMD_V/PF_DATA_V` 在计算时预取下一tile到对侧bank。

**证据**
- `rtl/core/fa_attention_core.sv`：localparam、buffer定义、`prefetch_state_t`、主状态机逻辑。
- `docs/report_0310/大纲.md`：对同一流程的文字化解释（与源码一致）。

> 问题3：Online Softmax 的硬件实现状态机/流水线结构是什么？

**回答**
- 有两层实现：
  1) **Core级调度**：`C_DP_RUN` 中将 QK partial-sum 聚合后发 `score_issue`，并与 softmax更新重叠（`score_done/softmax_prep` 事件并发打点）。
  2) **核内部流水**：`fa_online_softmax_ctx` 为 5级寄存流水（`s0~s4`），每级处理 `m/l/acc` 递推的一部分。
- `fa_online_softmax_ctx` 支持 `CTX_COUNT=4` 上下文状态（`m_state/l_state/acc_state`），并带forwarding避免同ctx冒险。
- Core里按维复制 `fa_online_softmax_ctx`：`genvar gk < D`，对 row0/row1各一套（共与 `D` 和 `ROW_PAR` 相关的复制）。

**证据**
- `rtl/core/fa_attention_core.sv`：`comp_state_t`、`gen_softmax_ctx` 生成逻辑、`sm_row*_` 接口。
- `rtl/core/fa_online_softmax_ctx.sv`：`s0..s4` 流水寄存与 `m/l/acc` 更新。

> 问题4：Q8.8 定点格式在哪些路径上使用？累加位宽和舍入/截断策略是什么？

**回答**
- Q8.8使用路径：Q/K/V输入、score缩放后、O输出均为Q8.8语义。
- 关键位宽：
  - QK点积中间和：`dp_partial_sum*` 为 40-bit（`logic signed [39:0]`）。
  - 行累计：`row_acc` 为 64-bit（`logic signed [63:0]`）。
  - 分母 `row_l`：32-bit（Q16.16语义）。
  - 倒数输出：`norm_recip_out_q16_16`。
- 归一化路径：`row_acc` 进入归一化前有 `<<< 8` 对齐，再与Q16.16倒数相乘，最终回落Q8.8并饱和。
- CModel里可配置舍入策略（实验）：`FLASH_ATTN_CMODEL_ROUND_BIAS`、`...PV_SHIFT`、`...CHUNK_SIZE`，用于 dual-buffer merge 行为对比。

**证据**
- `rtl/core/fa_attention_core.sv`：`dp_partial_sum`、`row_acc`、`row_l`、`norm_acc_chunk[lane] = row_acc[...] <<< 8`。
- `rtl/core/fa_o_normalize_block.sv` / `rtl/softmax/fa_recip_nr_q16_16.sv`（归一化+倒数模块）。
- `cmodel/csrc/attention_kernels.cpp`：`div_round_sat_s16`、`mul_q1_15_round_*` 与环境变量入口。

> 问题5：AXI4 DMA 的 burst 策略、最大 burst 长度、地址对齐处理方式是什么？

**回答**
- 读DMA（`fa_dma_reader`）支持“长命令自动拆burst”：
  - `AXI_LEN_W=8`，故单burst最大 `2^8=256` beats。
  - `cmd_len` 是逻辑总长（beats-1），模块内部按 `clip_burst_beats` 分段发 `ARLEN`。
- 写DMA（`fa_dma_writer`）当前是单命令单burst，不做内部拆分；`cmd_len` 位宽由 `AXI_LEN_W=8` 限制。
- 地址对齐：
  - 顶层 enqueue 时检查 `Q/K/V/O base` 与 `stride` 的低4位为0（16B对齐），否则置 `desc_error`。
  - `arsize/awsize = log2(AXI_DATA_W/8)`，128-bit总线即16B beat。
- 当前默认核心参数下：
  - Q tile写回/读取长度 256 beat（合法单burst）。
  - K/V tile读取逻辑长度 512 beat，由读DMA拆分成两个burst。

**证据**
- `rtl/bus/fa_dma_reader.sv`：`MAX_BURST_BEATS` 与拆分状态机。
- `rtl/bus/fa_dma_writer.sv`：`W_IDLE->W_ADDR->W_DATA->W_RESP`。
- `rtl/top/fa_attention_ip_top.sv`：`enqueue_desc_aligned` 检查。
- `dv/cocotb/tests/test_fa_dma_reader.py`：`ARLEN` split 用例断言（如 `[255, 43]` / `[255,255]`）。

> 问题6：性能计数器统计了哪些事件？寄存器地址或读取方式是什么？

**回答**
- 事件类别：
  - 运行级：`run_count`、`busy_cycles`。
  - DMA：`rd/wr cmd_count`、`rd/wr beat_count`。
  - 计算：`comp_launch_count`、`exp_eval_count`、`mul_eval_count`、`recip_req/rsp_count`。
  - 状态占时：`MS_*`（主状态）与 `CS_*`（子状态）。
- AXI-Lite地址窗口：`0x80 ~ 0xD4`（只读统计）。
- 读取方式：软件或DPI通过AXI-Lite读寄存器（例如 `fa_dpi_read_perf` 内部驱动 `FaAxilDriver.read32`）。

**证据**
- `rtl/top/fa_perf_counters.sv`：输入事件与计数更新。
- `rtl/bus/fa_axi_lite_regs.sv`：`REG_PERF_*` 地址定义。
- `inference/dpi/src/fa_dpi_backend.cpp`：`read_perf` 从寄存器读回。

> 问题7：CModel 的输入输出接口、与 RTL 对照的粒度、误差指标如何定义？

**回答**
- CModel C接口：`fa_cmodel_attention_head(...)`，输入为单head `q_head/k_seq/v_seq`（`int16_t` Q8.8），输出单head `out_head`。
- 对照粒度：
  - 最常见为**head级对照**（同一 head 的 `D=64` 输出向量逐元素比较）。
  - 在 `dpi_cmodel_rtl_compare.cpp` 中按 `seq_len` 多case、多随机样本统计。
- 误差口径：
  - LSB口径：`max_abs_lsb`、`sum_abs`、`diff_points`（RTL与CModel之间）。
  - 浮点口径（在DV/报告中）：`MAE`、`MaxAE`（相对FP32参考）与 `mae_lsb/max_err_lsb`（相对fixed参考）。
- CModel模式：`mode 0~18`，含 `FA_CORE_COMPAT`、`FIXED_Q8_IMPROVED`、dual-buffer等模式。

**证据**
- `inference/cmodel/bridge/fa_cmodel_bridge.h/.cpp`。
- `inference/dpi/tests/dpi_cmodel_rtl_compare.cpp`。
- `dv/cocotb/tests/test_fa_attention_ip_top_regs.py` 中 `_calc_i16_metrics/_calc_fp32_metrics`。

> 问题8：Llama.cpp 接入采用了什么调用边界？是函数调用、设备文件还是仿真接口？

**回答**
- 当前仓库主线是**函数调用边界**：在 `flash_attn.c` 中通过 `flash_attention_forward` 调用后端。
- 后端类型：
  - `FA_BACKEND_SW`：纯软件。
  - `FA_BACKEND_CMODEL`：函数调用到 CModel bridge。
  - `FA_BACKEND_DPI`：函数调用到 DPI API，再由 Verilator模型驱动AXI-Lite/AXI内存仿真。
- 不是 Linux 设备文件（如 `/dev/...`）模式；当前是进程内库 + 仿真接口模式。

**证据**
- `inference/native/flash_attn.c`：`flash_attention_set_backend` 与 `FLASH_ATTN_BACKEND` 选择。
- `inference/dpi/include/fa_dpi_backend.h`：`fa_dpi_init/submit_task/mem_read/mem_write` 等接口。
- `inference/docs/report_0312_vlm_dpic_integration.md`：对 `run.c/llama.cpp` 与 DPI-C 的接入方案描述。
