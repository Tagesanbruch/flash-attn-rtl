
# FlashAttention IP 设计、验证与综合报告

## 1. 简介

本文档给出当前 FlashAttention-style SDPA 加速器 IP 的完整设计说明、验证闭环、建模方法以及综合结果总结。设计目标面向赛题给定的单 batch、单 head、自注意力场景，输入输出数据格式采用 Q8.8 定点表示，目标问题规模为 $S=256$、$D=64$，并在实现中显式满足 online softmax、K/V tiling、禁止显式存储 $S\times S$ 注意力矩阵、AXI-Lite 配置接口和 AXI4 Master DMA 数据接口等要求。

当前主线 RTL 已形成可运行的顶层系统。系统中包含 AXI-Lite 配置寄存器、AXI DMA 读写通路、片上 tile buffer、在线 softmax 状态维护、QK 点积与 PV 累加、归一化输出以及性能计数器。围绕这些功能，仓库同时建立了 cocotb 回归环境、Verilator C++ 参考测试路径、周期精确 CModel、模块级综合与静态时序分析流程。因此，本项目的工作不再停留于算子级数学原型，而是已经进入“结构可运行、验证可复现、性能可量化、综合可分析”的工程阶段。

截至 2026-03-11，仓库当前唯一活动主线 `main` 的核心结果为：端到端 RTL 在默认参数下已经达到 $85{,}928$ cycles 的总延迟量级，并保持与 fixed Q8.8 参考逐点一致、与 FP32 参考之间 $\text{MAE}=0.002499$、$\text{MaxAE}=0.006583$ 的误差水平。与此同时，模块级独立实验已经明确定位出 leaf 级 PPA 边界：Online Softmax `ctx/exp_d` 超过 $500\text{MHz}$，QK 路径 `exp_h` 达到约 $442.5\text{MHz}$，倒数模块也超过 $500\text{MHz}$。这说明当前设计不仅已经满足 baseline 提交约束，而且已经完成一次从“高频 leaf 恢复态”到“system-level overlap 真正闭环”的主线收敛。

本文将从整体进度、算法与架构、附加总线模块、功能验证、CModel、LLM 接入思路以及综合实现七个层面进行系统陈述。行文中尽量保持论文式的展开方式，对关键公式、时延估计、带宽估计与实验指标均给出完整说明。

本项目的推进大致经历了五个阶段。第一阶段是功能基线搭建，主要完成 Q8.8 定点算术原语、online softmax 基本链路、控制寄存器映射和 DMA 基础接口，使得顶层能够完成从配置、启动到完成的完整状态流转。第二阶段是精度与周期的系统审计，通过 Python 参考模型、C++ CModel 和 Verilator 对照路径，明确区分“算法级浮点近似正确”与“RTL 同构定点正确”这两个口径，并逐步将主线实现收敛到通过精度门限的版本。第三阶段是架构级优化，重点包括控制空拍压缩、K/V 双缓冲重叠、row2 并行组织与性能计数器读回，使主线周期先降到十几万级。第四阶段是面向 55nm 工艺的模块级 PPA 优化，通过在 `experiments/` 目录下构造对照实验，分析倒数、online softmax、QK 点积与归一化模块的结构性时序瓶颈。第五阶段则是把 `exp_h + ctx/exp_d + exp_d` 这组高频 leaf 真正以 tag 化、批流式和多上下文交错的方式吸收到 `fa_attention_core` 中，使当前主线周期进一步收敛到 `85928`。

## 3. 具体设计方案

### 3.1 实现算法说明

目标算子为 Scaled Dot-Product Attention。对给定查询矩阵 $Q\in\mathbb{R}^{S\times D}$、键矩阵 $K\in\mathbb{R}^{S\times D}$ 和值矩阵 $V\in\mathbb{R}^{S\times D}$，标准形式可写为

$$
\mathrm{SDPA}(Q,K,V)=\mathrm{softmax}\left(\frac{QK^T}{\sqrt D}\right)V.
$$

若直接先显式形成 $S\times S$ 的 score 矩阵，再统一做 softmax 和乘以 $V$，则在本题规模下会引入明显的片上存储压力。以 $S=256$ 为例，若 score 也采用 16bit 表示，则完整矩阵大小为

$$
256\times 256 \times 16\text{ bits}=1{,}048{,}576\text{ bits}=128\text{ KB},
$$

这已经接近甚至超过当前算子内多个片上 buffer 的总和，并且会破坏 FlashAttention 以流式更新代替显式矩阵存储的核心思想。因此本设计采用 online softmax 递推形式，以行为粒度维护三组状态：当前最大值 $m$、分母累计量 $l$ 以及加权和值累计向量 $\mathrm{acc}$。对于任意新到达的 score $s_j$ 与 value 向量 $v_j$，更新公式为

$$
m' = \max(m, s_j),
$$

$$
l' = l\cdot e^{m-m'} + e^{s_j-m'},
$$

$$
\mathrm{acc}' = \mathrm{acc}\cdot e^{m-m'} + e^{s_j-m'}\cdot v_j.
$$

在一行处理完全部 key 之后，最终输出为

$$
o = \frac{\mathrm{acc}}{l}.
$$

这套递推是 FlashAttention 与 online softmax 文献中的核心思想，其工程优势在于：第一，不再需要存储完整的 score 矩阵；第二，每个 score 一旦算出就可以立刻参与 softmax 更新与 PV 累加；第三，状态只需按 query 行保存，而不依赖于历史全部 score。当前设计又进一步将查询并行度设置为 `ROW_PAR=2`，即每次同时处理两个 query row，从而在不明显增大调度复杂度的前提下提高吞吐效率。

在数值表示上，输入的 $Q$、$K$、$V$ 以及输出 $O$ 都采用 Q8.8 定点格式。两个 Q8.8 数相乘得到 Q16.16 结果，因此点积累加器至少需要 32bit 以上精度。当前主线中，点积路径输出采用 40bit 中间和，行累计 `row_acc` 仍保留为 64bit 存储接口以兼容归一化通路。online softmax 恢复为 `ctx` 方案后，模块内部的 `l/acc` 标量状态使用 Q16.16 和 32bit 累计，再由 core 以符号扩展方式写回 `row_acc[63:0]`，从而在不重写 normalize 接口的前提下先恢复主线功能。倒数模块 `fa_recip_nr_q16_16` 输出 Q16.16，而归一化乘法器再将 64bit 累计量与 Q16.16 倒数相乘并回落到 Q8.8。对于 $D=64$ 的默认参数，缩放因子为

$$
\frac{1}{\sqrt{64}} = \frac{1}{8} = 0.125,
$$

映射到 Q8.8 后恰好为 $0.125\times 256 = 32$，因此 `SCALE` 寄存器的默认值设置为十进制 `32`。

当前架构还引入了 tile 化组织。序列长度 $S=256$ 被分成 `TQ=32` 的 query tile 和 `TK=64` 的 key/value tile，因此

$$
\mathrm{NUM\_Q\_TILES}=\frac{256}{32}=8,
\qquad
\mathrm{NUM\_K\_TILES}=\frac{256}{64}=4.
$$

设计采用外层遍历 Q tile、内层遍历 K/V tile 的双层调度。每次只在片上保存一个 Q tile、一个正在计算的 K/V tile 以及一个预取中的 K/V tile。由于 score 的计算与 online softmax 更新是流式进行的，因此整个 tile 过程始终不需要显式写出任何中间注意力矩阵。

### 3.2 设计总体框图

当前顶层结构可以抽象为如下层次：

```text
				┌──────────────────────────────┐
				│      Host / CPU / SoC        │
				│ AXI-Lite cfg + AXI memory    │
				└──────────────┬───────────────┘
							   │
				 ┌─────────────▼─────────────┐
				 │     fa_attention_ip_top    │
				 │                             │
				 │  ┌──────────────────────┐   │
AXI-Lite slave ──┼─▶│  fa_axi_lite_regs    │   │
				 │  └──────────────────────┘   │
				 │                             │
AXI4 master  ────┼─▶ fa_dma_reader            │
				 │  fa_dma_writer             │
				 │                             │
				 │  ┌──────────────────────┐   │
				 │  │  fa_attention_core   │   │
				 │  │  Q/K/V/O tile FSM    │   │
				 │  │  online softmax      │   │
				 │  │  QK + PV + norm      │   │
				 │  └──────────────────────┘   │
				 │                             │
				 │  ┌──────────────────────┐   │
				 │  │  fa_perf_counters    │   │
				 │  └──────────────────────┘   │
				 └─────────────────────────────┘
```

在顶层看来，`fa_axi_lite_regs` 负责软件可见的配置与状态窗口，`fa_dma_reader/fa_dma_writer` 分别负责从系统内存搬运 Q/K/V 与将 O 写回系统内存，而 `fa_attention_core` 则是完整的调度与数据通路中心。值得强调的是，本设计并未将计算控制器与数据通路彻底分离，而是选择将 tile 调度、DMA 命令发起、online softmax 状态维护、QK/PV 计算与最终归一化都放入一个强内聚的核心中。这种做法牺牲了一部分模块边界上的整洁性，但换来了早期迭代阶段更直接的功能闭环和更清晰的时序归因。

### 3.3 模块间数据流向

一次完整 attention 计算的主数据流可叙述如下。首先，软件通过 AXI-Lite 将 `Q_BASE`、`K_BASE`、`V_BASE`、`O_BASE`、`STRIDE_BYTES`、`SCALE`、`NEG_LARGE` 等寄存器写入顶层寄存器文件，然后向 `CTRL` 寄存器写入启动脉冲。顶层寄存器文件将该启动脉冲转化为 `fa_attention_core` 的 `i_start`，同时保持各个配置参数处于稳定状态。

在 `fa_attention_core` 内部，主状态机首先进入 `S_LOAD_Q`，通过 DMA reader 发出一个 query tile 读命令，并将读回的总线 beat 逐个解包为 `q_buf[TQ][D]`。随后，状态机进入 `S_INIT_CONTEXT`，将当前 query tile 对应的 `row_m`、`row_l`、`row_acc` 进行初始化，其中 `row_m` 初始化为 `NEG_LARGE`，`row_l` 初始化为零，`row_acc` 初始化为零向量。

接下来主状态机依次对 4 个 K/V tile 循环。对于每个 tile，先加载 K，再加载 V；进入 `S_COMPUTE` 后，内部子状态机 `cs` 会以 `ROW_PAR=2` 为粒度遍历 query 行对，以 `DP_CHUNKS=2` 为粒度遍历 32-lane 的点积切片，以 `TK=64` 的长度遍历 key/value 行。每个 score pair 先经过 QK 点积，再乘以缩放因子，随后进入 online softmax 更新模块产生新的 `m`、`l` 和 `acc`。由于 `V` 行与新生成的 softmax 权重在同一拍的组合中被使用，因此 score 一旦计算完毕，便立即以流式方式并入 `row_acc`，不需要中间存储 score 阵列。

当所有 K/V tile 完成后，核心进入 `S_NORMALIZE`。此时每个 query row 的 `row_acc` 和 `row_l` 已经累积完毕，归一化逻辑先对 `row_l` 启动倒数模块，再以 `NORM_LANES=8` 的向量宽度将 `row_acc` 分块乘以倒数，得到最终的 `o_buf[TQ][D]`。最后，`S_WRITE_O` 通过 DMA writer 将 O tile 写回系统内存，并在 `S_NEXT_Q` 中决定是否继续处理下一个 Q tile。当全部 tile 结束后，顶层将 `done` 置位并允许软件读取 `CYCLES` 与性能计数器寄存器。

![Q/KV tile schedule](../wavedrom/svg/fig11_3_tile_schedule.svg)

如果将上述过程按一次完整运行的地址搬运量来观察，则 Q 只在每个 Q tile 开始时读取一次，而 K/V 会对每个 Q tile 重复遍历全部 4 个 tile。之所以这样设计，是因为该架构的优化重点并不是极端减少片外流量，而是在片上存储受限的前提下，通过适中的 tile buffer 和 online softmax 流程使运算路径尽可能连续。后续如需支持更长上下文或更多 head，则应在系统层继续引入更高级的外部编排与片上 scratchpad 级缓存，而不是简单扩大当前核心的本地 buffer。

### 3.4 具体算子的实现

#### 3.4.1 QK 点积实现

主线中的点积算子由 `fa_qk_dotprod_slice` 完成。与更早期的组合式 slice 不同，当前同名主线模块已经吸收了 `exp_h` 的结构：输入先寄存，再经过乘法首拍与逐级二叉加法树，共形成一条约 `8` 拍的局部部分和流水。它每次仍只处理一个 `DP_LANES=32` 的 chunk，且对两个 query row 同时给出局部部分和；由于 `D=64`，默认仍需两个 chunk 才能完成一次完整内积。也就是说，主线接口名没有变，但内部微结构已经从“组合乘加块”切换为“高频长流水树”。

![QK slice pipeline](../wavedrom/svg/fig10_3_qk_pipeline_migration.svg)

这种结构的优点是逻辑简单、控制友好，与 `ROW_PAR=2` 的并行方式自然匹配。其问题也很明显：当每拍同时执行 32 个 `16\times 16` 乘法再叠加局部加法树时，单拍组合深度很大，因此在 55nm 目标频率下很容易成为关键路径来源。这正是后续独立实验集中优化的对象。

围绕 QK 点积，本项目在 `experiments/fa_qk_dotprod_slice_pipe` 中开展了多轮实验。早期的 `exp_e` 通过 `8` 组局部乘加块再做 `quarter / half / final` 三级归并，将频率提高到约 `203.8MHz`。2026-03-10 的新一轮实验继续坚持 `32-lane` 和 `II=1`，但把第一级强制改为“纯乘法寄存”，后续全部改成逐级流水的二叉加法树。由此得到的 `exp_f / exp_g / exp_h` 在结构上分别对应“纯乘法首拍”“位宽逐级收敛”“输入预寄存+位宽收敛”三种版本。补跑前台 STA 之后的结果表明：`exp_g` 的最差 slack 为 `-0.650ns`、估算频率约 `377.3MHz`，`exp_h` 的最差 slack 为 `-0.260ns`、估算频率约 `442.5MHz`。这说明 QK 路径的频率瓶颈已经被压缩到单乘法器级，而不再是宽加法树级别，为后续主线集成提供了明确方向。

#### 3.4.2 Online Softmax 实现

online softmax 的当前主线实现已经切回 `fa_online_softmax_ctx` 家族，并完成了 system-level 的流式接入。这里的关键变化不再只是“把 `pair` 换成 `ctx`”，而是把 `exp_d` 的标量、4-context、带 forwarding 的流水更新单元，与 `fa_attention_core` 中的 `QK` tag 回收和 batch 调度真正绑定起来。当前主线设置 `SOFTMAX_CTXS=4`，并以 `QPAIR_BATCH_ROWS = ROW_PAR \times SOFTMAX_CTXS = 8` 的粒度组织 row-pair batch；对同一个 compute tile 而言，`score retire`、`softmax issue` 与 `QK` issue 已经发生重叠，而不是像恢复态那样逐个 score-pair 串行等待。

![Online softmax update](../wavedrom/svg/fig11_4_online_softmax_update.svg)

从算法角度看，这一结构仍然对应 online softmax 递推公式；从硬件角度看，它通过 `ctx_id`、多级流水和状态前递，明确切断了最重的 recurrence datapath。独立实验中，`fa_online_softmax_ctx/exp_d` 在 500MHz 约束下的最差 slack 为 `+0.135ns`、估算频率约为 `536.2MHz`，这是当前 softmax 家族里最强的 leaf 结果；而在当前主线中，它已不再停留在“可以工作”的恢复态，而是通过 `4-context` 交错真正参与 system-level overlap。最新主线 perf 读回中，`cs_softmax_prep_cycles=32768`，已经从先前恢复态的 `229376` 显著回落，并与 `score retire` 事件数对齐，说明 `ctx` 的吞吐潜力已经被当前调度兑现。

#### 3.4.3 倒数与归一化实现

归一化阶段包含两个子问题。第一个子问题是如何计算分母 $l$ 的倒数，当前使用 `fa_recip_nr_q16_16` 实现 Newton-Raphson 迭代。第二个子问题是如何将 64bit 的累计向量乘以 Q16.16 倒数，再有符号饱和回写到 Q8.8 输出，当前由 `fa_o_normalize_block` 完成。这里的 `fa_o_normalize_block` 也已经不是早期的纯组合版本，而是吸收 `exp_d` 后形成的两拍流水实现：第一级完成部分积展开，第二级完成重组、舍入与饱和。主线中以 `NORM_LANES=8` 的方式分块处理 `D=64` 维，因此每行需要 8 次向量归一化，整块输出需要 256 次倒数请求与 256 次倒数响应，这也与 perf counters 的实际读回相符。

![Normalize pipeline](../wavedrom/svg/fig10_4_norm_datapath_split.svg)

倒数模块是最早完成 500MHz 收敛的子模块之一。`fa_recip_nr_q16_16/exp_c` 采用 16×16 部分积和 10 级流水之后，估算频率可达 `527MHz`，已经表明数值核本身不是系统主瓶颈。归一化块的独立实验则显示，单纯在输出路径上做轻量流水虽然能将频率提升到 `333.9MHz` 至 `360.8MHz`，但与 QK 和 softmax 相比，其收益和优先级仍然偏低。因此当前的工程判断是：归一化阶段已经足以支撑 baseline 主线，后续更适合通过系统级 overlap、倒数前移或更好的物理实现来继续挖掘，而不必把大量前端架构时间继续投入到该路径。

#### 3.4.4 控制、双缓冲与性能计数器

`fa_attention_core` 使用双层状态机组织。主状态机 `ms` 依次执行 `S_LOAD_Q`、`S_INIT_CONTEXT`、`S_LOAD_K`、`S_LOAD_V`、`S_COMPUTE`、`S_NORMALIZE`、`S_WRITE_O`、`S_NEXT_Q` 和 `S_DONE`。内层计算子状态机 `cs` 则在 `S_COMPUTE` 期间执行 `C_DP_RUN`、`C_SCORE_DONE`、`C_SOFTMAX_PREP` 和 `C_DONE`。该控制结构的一个重要优化是取消了多余的空拍控制态，把部分初始化、下标推进和状态过渡内联到关键状态中，从而减少 `cs_ctrl_cycles`。

K/V buffer 方面，主线已经实现 ping-pong 双缓冲。当前活跃 bank 负责参与计算，而另一个 bank 可以在计算期间预取下一 tile。这一结构的意义不在于理论上消灭所有读延迟，而在于把一部分原本显式暴露在主状态机中的 K/V 装载周期掩蔽到 compute 阶段内部。根据当前 perf counters 的读回，`MS_COMPUTE=67584`，而 `MS_LOAD_K=4144`、`MS_LOAD_V=4144`；结合每个 `Q tile × K/V tile` 仅额外承担约 `32` 个 compute 控制边界周期这一事实，可以看出当前主线的 compute 主体已经非常接近“批流式 issue 下界 + 少量 tile/control 气泡”的状态。

为了使后续优化可以量化，本项目又引入了 `fa_perf_counters` 模块，并在 AXI-Lite 窗口中映射了 `0x80~0xD4` 的只读寄存器。当前可读回的计数包括运行次数、busy 周期、DMA 命令与 beat 数、乘法/指数/倒数事件数、主状态占时和子状态占时。这使得本项目从传统的“看一次 test pass 与否”的验证方式，进一步推进到了“设计行为—计数口径—性能结论”三者一致的工程闭环。

### 3.5 定点实现误差分析

定点误差分析是本项目中最早暴露系统性问题的一环。初始阶段若直接拿 RTL 同构路径与 FP32 结果比较，会发现误差显著大于赛题门限；而若采用“输入量化、softmax 仍在浮点域”的参考模型，则误差又远小于门限。这一现象说明，必须严格区分算法口径与实现口径，否则会高估硬件链路的数值质量。为此，项目后来单独建立了 CModel，并对 dot、score、exp、$l$、acc、norm 六个阶段做逐级误差分解。

阶段误差分解的结果非常具有指导意义。在 `small-int + causal` 条件下，`dot`、`score` 和 `exp` 的 MAE 都在 $10^{-3}$ 量级，而 `acc` 阶段的 MAE 已达到 `135.58`，最终 `norm` 阶段的 MAE 约为 `1.865`。在 `gaussian + causal` 条件下，`acc` 的 MAE 进一步上升到 `464.11`，`norm` 的 MAE 也被拉高到 `33.44`。这表明主导误差并不来自指数近似本身，而是来自长程累计状态 `acc` 的尺度耦合、分母归一化以及掩码后的动态范围放大。

基于该结论，项目在主线中采取了几项稳健策略。第一，`row_acc` 使用 64bit 高精度累计，避免软最大更新过程中被过早截断。第二，`l_new` 在写回前加入最小值保护，防止分母退化为零。第三，归一化阶段保留 `den==0` 的保护分支，并将饱和逻辑集中到末端。第四，在 streamed `ctx` 主线稳定后，又进一步修正了 `acc` 进入 normalize 之前的尺度口径：当前实现会在 normalize 入口对 `row_acc` 做 `<<< 8` 的对齐补偿，从而使 `ctx` 产生的 `Q16.16` 累计值与当前倒数-归一化链路保持一致。最终顶层 full-run 读回已达到：RTL 相对 fixed-q8.8 参考 `mae_lsb=0`、`max_err_lsb=0`，相对 FP32 参考 `MAE=0.002499`、`MaxAE=0.006583`，说明当前主线在本题规模下已经重新实现周期与精度双闭环。

### 3.6 延迟与带宽分析

从理论参数出发，当前设计的主要派生量如下。总线宽度 `BUS_W=128`，因此每个 beat 可携带

$$
\mathrm{ELEMS\_PER\_BEAT}=\frac{128}{16}=8
$$

个 Q8.8 元素。对于 $D=64$，每行需要

$$
\mathrm{BEATS\_PER\_ROW}=\frac{64}{8}=8
$$

个 beat。于是，一个 Q tile 的流量为

$$
32\times 64\times 2\text{ B}=4096\text{ B}=4\text{ KB},
$$

对应 256 个 beat；一个 K tile 或 V tile 的流量为

$$
64\times 64\times 2\text{ B}=8192\text{ B}=8\text{ KB},
$$

对应 512 个 beat。整个 attention 的理论总流量因此为：Q 读取 $8\times 4\text{KB}=32\text{KB}$，K 读取 $8\times 4\times 8\text{KB}=256\text{KB}$，V 读取同为 `256KB`，O 写回为 `32KB`，合计约 `576KB`，即 `36,864` 个 128bit beat。

从计算量角度看，`ROW_PAR=2` 意味着一个 score pair 对应两个 query row；每个 Q tile 中共有

$$
\frac{TQ}{ROW\_PAR}=\frac{32}{2}=16
$$

个 row pair。每个 row pair 需要遍历 `TK=64` 个 key，因此每个 K tile 处理 `16\times 64=1024` 个 score pair，全局一共处理

$$
8\times 4\times 16\times 64 = 32768
$$

个 score pair。若按当前 streamed 主线的 batch 调度来估算，则每个 `Q tile × K/V tile` 计算块中：

- 总 row-pair 数为 `16`；
- 每 batch 覆盖 `SOFTMAX_CTXS=4` 个 row-pair；
- 因此每个 compute tile 共有 `4` 个 batch；
- 每个 batch 的有用 `QK` issue 周期为 `4 × 64 × 2 = 512`；
- 再加一次 `QK_LAT=8` 的流水 fill/drain；
- 每个 batch 约为 `520` 个 `DP` 周期。

于是全局 `QK` 主体近似为：

$$
8 \times 4 \times 4 \times 520 = 66560.
$$

当前实测恰好读回：`CS_DP_RUN=66560`。而 `CS_SCORE_DONE=32768` 与 `CS_SOFTMAX_PREP=32768` 在当前实现中已不再表示“独占 compute 的串行状态占时”，而更接近“在 `DP` 流水内部发生的 retire / issue 事件计数”，它们与 `QK` issue 已存在大量重叠，因此不能再简单与 `CS_DP_RUN` 线性相加。当前每个 compute tile 的总占时约为：

$$
4 \times 520 + 32 = 2112,
$$

其中额外的 `32` 个周期对应 tile/control 边界气泡。全局共有 `32` 个 compute tile，因此：

$$
MS\_COMPUTE = 32 \times 2112 = 67584,
$$

与 perf 读回完全一致。再加上 `Q/K/V/O` 访存与 normalize，就得到当前主线总延迟：

$$
cycles = 85928.
$$

因此当前主线已经可以明确判断：主瓶颈不再是“重复支付 leaf 流水延迟”，而是后续若要继续提升，则更可能来自 bonus 级扩展能力、top-level PPA 与更高层次的软件—硬件协同。


## 3.7 0324 架构增量：从单任务基线到可扩展任务形态

0310 版本的主线架构已完成 baseline 闭环；0324 版本新增的关键不是“替换原算法”，而是在保持 baseline 数据通路不破坏的前提下，把可扩展能力下沉到寄存器、调度和控制边界。新增能力主要来自三条线：

1. `valid_len/data_fmt`（Bonus #3/#4/#5）
2. `head loop`（Bonus #2）
3. `task FIFO`（Bonus #9）

三条线的共同策略是：尽量不重写 `fa_attention_core` 的核心 online-softmax 计算链，而在 top 级调度与寄存器语义层做增量扩展。

### 3.7.1 `valid_len` 的数据流影响

`valid_len` 的硬件作用已经从“配置项存在”推进到“完整数据流生效”：

1. query 侧：`q >= valid_len` 的行不参与有效更新；
2. key 侧：`k >= valid_len` 的分数被打成 `NEG_LARGE`；
3. 输出侧：padded query 行归一化后强制写零；
4. 周期侧：`valid_len=192` 时总周期由 `85928` 下降到 `73880`。

这一行为说明当前实现已经有“计算裁剪”收益，但 DMA 仍按完整 tile 读写，尚未引入“流量裁剪”。

### 3.7.2 `data_fmt` 的桥接语义

`Q6.10/Q4.12` 路径目前采用外部桥接，内部统一回到 `Q8.8`。因此当前 architecture 本质仍是“单内部格式 + 多外部格式适配器”。该策略的工程优点是：

1. 不破坏 `row_m/row_l/row_acc` 既有位宽链路；
2. 不引入第二套 normalize/recip 实现；
3. 可以较低风险完成 Bonus #5 功能验收。

局限是：`Q6.10` 与 `Q4.12` 在当前激励下会退化到同一内部有效值集合，无法体现真正的内部多精度差异。

### 3.7.3 多 head 的最小侵入实现

`exp/bonus2-mha` 采用的是 single-core sequential MHA：

1. `fa_attention_core` 不改；
2. top 级增加 `NUM_HEADS` + `HEAD_STRIDE`；
3. 通过 head 外层循环顺序执行。

这种组织的核心好处是可验证性强，且实测显示 top 切换开销几乎可忽略：`cycles`、`comp_launch`、`recip_req` 都随 head 数严格线性扩展。其代价是吞吐上限完全受单 head core 限制。

### 3.7.4 task queue 的从 P1 到 P2

Bonus #9 已从 `active+next` 的影子寄存器（P1）推进到真正 FIFO（P2）：

1. 任务描述寄存器作为 staging port；
2. `QUEUE_CMD.ENQUEUE` 显式入队；
3. 内部 FIFO（默认深度 4）自动调度出队；
4. 任务级计数器（accept/done/error）独立维护。

这意味着 IP 控制语义从“一次 start 对应一次任务”扩展到“单次批次排空”，为后续链式任务和软件驱动优化提供接口基础。

## 3.8 IP 吞吐量与关键参数的统一量化

为了让不同分支结果可横向比较，本节给出统一吞吐口径。定义：

$$
N_{MAC}=2\cdot S\cdot S\cdot D,
\quad
N_{OPS}=2\cdot N_{MAC}=4\cdot S\cdot S\cdot D.
$$

### 3.8.1 baseline (`S=256,D=64,cycles=85928`)

$$
N_{MAC}=8,388,608,
\quad
N_{OPS}=16,777,216.
$$

单位 GHz 吞吐：

$$
\text{GMAC/GHz}=\frac{8,388,608}{85,928}=97.624,
\quad
\text{GOPS/GHz}=195.247.
$$

单位 GHz 任务吞吐：

$$
\text{attn/s/GHz}=\frac{10^9}{85,928}\approx 11,638.
$$

对应典型频点：

- `400MHz`: `attn/s≈4,655`, `GOPS≈78.10`
- `500MHz`: `attn/s≈5,819`, `GOPS≈97.62`

### 3.8.2 `S=512` (`cycles=307024`)

$$
N_{MAC}=33,554,432,
\quad
N_{OPS}=67,108,864.
$$

$$
\text{GMAC/GHz}=109.290,
\quad
\text{GOPS/GHz}=218.580,
\quad
\text{attn/s/GHz}\approx 3,257.
$$

对应 `500MHz`：`attn/s≈1,628`，`GOPS≈109.29`。

这说明虽然 `S=512` 周期上升，但每次 attention 的操作量增长更快，因此单位周期算术吞吐反而提高；系统瓶颈逐步由控制边界转向数据搬运与重读。

### 3.8.3 multi-head 顺序版吞吐性质

由于 `head=1/2/4/8` 周期严格线性，顺序 MHA 的“每 head 吞吐”与单 head baseline 等价。即：

1. 总任务吞吐随 head 数反比下降；
2. 总算术吞吐与单 head 基本同级；
3. 不引入额外并行资源时，不会凭空获得超线性收益。

因此若下一阶段目标是提升 MHA 总吞吐，必须进入跨 head overlap 或多 core 并行，而不是继续优化 top 级 head 切换状态。

## 3.9 带宽-计算协同的阶段性判断

按照 `BUS_W=128bit`，baseline 理论总流量 `589,824B`，结合 `cycles=85928`：

$$
\text{bytes/cycle}=6.864,
\quad
\text{bus util} \approx 42.9\%.
$$

其中 K/V 流量占比约 `88.9%`。对 architecture 的启示是：

1. 当前系统不是纯内存瓶颈，但 K/V 重读已主导流量；
2. `valid_len` 目前只优化计算，不优化流量；
3. 进一步做带宽优化应优先瞄准“最后 tile 裁剪”和“task 间 K/V 复用”而非 Q/O。

以上判断与 Bonus #9 queue 化方向天然兼容：任务排队后可在调度层观察相邻任务的 K/V 地址相关性，为未来的跨任务数据复用提供结构入口。
## 4. 附加模块的设计

### 4.1 DMA 引擎

#### 4.1.1 设计总体思路

DMA 模块采用非常明确的“命令接口 + AXI 主口 + 简单双向流接口”结构。`fa_dma_reader` 接收来自调度器的 `cmd_valid/cmd_ready/cmd_addr/cmd_len`，将其转化为 AXI 读地址突发，再把返回的 R 通道 beat 原样流式送往下游 tile buffer。`fa_dma_writer` 则接受写命令和写数据流，先发起 AXI 写地址，再连续消费输入数据 beat，最后等待写响应完成一个事务。这样的接口形式有两个优点。其一，调度器只需要关心“从哪个地址开始搬多少 beat”，不需要直接操作 AXI 的五个通道。其二，后端 compute core 可以把访存看作简单的流输入和流输出，从而减少控制状态机与总线协议之间的耦合。

读取 DMA 内部支持对过长逻辑命令进行分裂。当总读 beat 数超过 AXI `ARLEN` 能够编码的范围时，模块会自动把一条长命令拆成多个 burst 并递增地址继续读取。这一能力已在 `test_split_long_command` 中得到验证。对本项目而言，这一点的重要性在于它使调度器可以统一以 tile 为粒度给出逻辑长度，而不必人工考虑底层 AXI burst 的最大长度限制。

#### 4.1.2 工作流程及错误处理

读 DMA 的状态机可概括为 `AR_IDLE -> AR_SEND -> AR_STREAM`。在 `AR_IDLE` 状态接收到命令后，模块首先根据剩余 beat 数裁剪出本次 burst 的长度；在 `AR_SEND` 状态与 AXI 地址通道完成握手；随后进入 `AR_STREAM`，在每拍 `RVALID && RREADY` 时向下游输出一个 beat，并更新剩余 beat 计数。当一个 burst 完成而总事务尚未结束时，状态机会自动回到 `AR_SEND` 继续下一个 burst。任何一次 `RRESP != OKAY` 都会将 `error` 置为粘滞态，以便上层统一发现故障。写 DMA 的结构与此对称，其状态机为 `W_IDLE -> W_ADDR -> W_DATA -> W_RESP`，并对 `BRESP` 做粘滞错误记录。

![DMA / tile-buffer handshake](../wavedrom/svg/fig11_5_dma_tilebuffer_handshake.svg)

从验证结果看，DMA 模块的行为已经比较稳定。`fa_dma_reader` 的单测覆盖了单 burst、错误标记、字节计数、背靠背命令和超长命令拆分；`fa_dma_writer` 的单测覆盖了写 burst、响应错误和写字节统计。顶层 full-run perf counters 读回的 `DMA_RD_CMD_COUNT`、`DMA_WR_CMD_COUNT`、`DMA_RD_BEAT_COUNT`、`DMA_WR_BEAT_COUNT` 还能与内存模型的统计互相校验，这说明 DMA 模块不仅功能正确，而且其计数口径也足以支撑后续系统级性能分析。

### 4.2 AXI-Lite Config 的实现

#### 4.2.1 AXI-Lite 配置寄存器

AXI-Lite 配置寄存器由 `fa_axi_lite_regs` 实现。其内部使用典型的写地址与写数据分离锁存结构：只有当地址与数据都到齐、且当前没有未完成的写响应时，才视为一次 `write_fire`。读通道则根据 `ARADDR` 直接组合多路选择出 `RDATA`，并用 `RVALID` 做单周期响应控制。这样的实现方式足以覆盖当前简单寄存器文件的需求，同时避免引入更复杂的寄存器总线桥接逻辑。

控制寄存器的语义设计与赛题要求基本对齐。`CTRL` 中 bit0 表示启动脉冲，bit1 表示软复位，bit2 预留为中断使能；`STATUS` 中包含 busy、done-sticky 和 error；`CFG` 当前主要承载 `causal_en`。四组 64bit 基地址通过高低 32bit 寄存器拼接形成 `Q_BASE/K_BASE/V_BASE/O_BASE`。此外，还包括 `STRIDE_BYTES`、`NEG_LARGE`、`SCALE` 和 `CYCLES` 等寄存器。为了支撑架构级调优，又额外加入了 `0x80~0xD4` 的性能计数器窗口，使上层软件无需内部探针即可读取本轮运行的微观行为统计。

#### 4.2.2 寄存器具体功能对照表

表 4-1 给出当前主用寄存器及功能说明。

| 偏移 | 名称 | 功能说明 |
|---|---|---|
| `0x00` | `CTRL` | bit0 启动脉冲，bit1 软复位，bit2 中断使能 |
| `0x04` | `STATUS` | bit0 busy，bit1 done-sticky，bit2 error；支持写 1 清 done |
| `0x08` | `CFG` | bit0 为 `causal_en` |
| `0x14/0x18` | `Q_BASE_L/H` | Q 基地址低 32bit 与高 32bit |
| `0x1C/0x20` | `K_BASE_L/H` | K 基地址低 32bit 与高 32bit |
| `0x24/0x28` | `V_BASE_L/H` | V 基地址低 32bit 与高 32bit |
| `0x2C/0x30` | `O_BASE_L/H` | O 基地址低 32bit 与高 32bit |
| `0x34` | `STRIDE_BYTES` | 行跨度，默认 `128` bytes |
| `0x38` | `NEG_LARGE` | 因果掩码使用的大负数，默认 `0xFFFF8000` |
| `0x3C` | `SCALE` | 缩放因子 Q8.8，默认 `32` |
| `0x40` | `CYCLES` | 当前运行周期计数 |
| `0x80~0xD4` | `PERF_*` | 运行次数、DMA 统计、子状态占时、乘法/指数/倒数计数 |

这种寄存器组织方式在软件接口层非常直接。一方面，它使 host 侧可以把当前 IP 看成标准的“配置—启动—轮询完成—读统计”设备；另一方面，也为未来 UVM reg model 和 SoC driver 的统一抽象提供了天然接口边界。


## 4.3 0324 新增控制与队列语义

0310 版本的控制平面以“单任务配置 + start”语义为主；0324 版本在不破坏 baseline 的前提下新增了队列化能力，形成了“staging descriptor + queue command/status + auto scheduler”的结构。

### 4.3.1 队列寄存器窗口

新增并稳定使用以下地址窗口：

- `0x44` `REG_QUEUE_CMD`
- `0x48` `REG_QUEUE_STATUS`
- `0x4C` `REG_QUEUE_CAPACITY`
- `0x50` `REG_TASK_ACCEPT_COUNT`
- `0x54` `REG_TASK_DONE_COUNT`
- `0x58` `REG_TASK_ERROR_COUNT`
- `0x5C` `REG_LAST_ERROR`

`QUEUE_STATUS` 的位域语义已固定为可软件轮询的组合状态：

1. `queue_empty`
2. `queue_full`
3. `queue_ready_for_enqueue`
4. `queue_busy_exec`
5. `queue_count/free_slots`
6. `overflow/underflow/desc_error sticky`

这套位域在软件侧可直接实现“可入队判定 + 容量估算 + 异常恢复”。

### 4.3.2 descriptor 校验与异常处理

当前入队前校验已覆盖：

1. `stride_bytes != 0`
2. `scale_q8_8 != 0`
3. `Q/K/V/O base` 16B 对齐
4. `stride_bytes` 16B 对齐

不满足时拒绝入队并置位 `desc_error_sticky`。此外：

1. `flush_queue` 仅清空 pending，不打断 active；
2. 空队列下 flush 会触发 `underflow_sticky`；
3. sticky 位可通过命令寄存器单独清除。

该异常语义已经在 cocotb 顶层测试覆盖，不再停留在寄存器定义层。

## 4.4 AXI-Lite 的扩展字段与兼容边界

除了 queue 相关字段，本阶段还在部分分支预留了未来可扩展字段：

1. `DATA_FMT`（Bonus #5）
2. `VALID_LEN`（Bonus #4）
3. `NUM_HEADS/HEAD_STRIDE`（Bonus #2）
4. `PRECISION_MODE`（BF16/FP16 研究线）

当前这些字段在不同分支成熟度不同，但一个重要工程原则已经确立：

- baseline 只启用严格必要字段；
- bonus 字段独立分支验证，不回写污染 baseline 结论。

这一点直接降低了“功能扩展导致主线回归不确定性”的风险。

## 4.5 DMA 语义的阶段划分

0324 版本需要明确区分两类 DMA 语义，避免报告口径混淆：

1. 主线 Q8.8 IP 的真实 DMA 握手路径（top-level AXI master）；
2. FP8 full-core 实验中的 phase/beat 模型计数（更接近事件建模，不等价于主线 DMA 协议完整实现）。

前者用于 baseline 合规；后者用于低精度原型阶段的性能可视化。该边界在 0324 报告中必须显式标注，防止把实验核计数误认成可提交 IP 的 DMA 证据。

## 4.6 接口演进建议

基于当前实现状态，控制/数据平面后续建议如下：

1. 保持 AXI-Lite 作为统一控制面，不为 bonus9 单独引入 instruction-fetch 控制器。
2. task queue 优先走 descriptor/FIFO 路线，保持与现有 regbank 兼容。
3. AXI4-Stream 若推进，建议作为独立 top wrapper，与 DMA top 并存，避免影响 baseline 驱动与验收脚本。

该策略能保证“接口创新”和“baseline 可交付”并行推进。
## 5. 功能验证——Testbench 仿真与波形说明

### 5.1 功能验证具体环境

当前功能验证环境以 Python、cocotb 和 Verilator 为主。项目根目录 `Makefile` 通过 `uv venv .venv` 建立虚拟环境，并固定安装 `cocotb==1.9.2`、`pytest` 和 `numpy`。本地实际使用的版本为：Python `3.13.5`、cocotb `1.9.2`、Verilator `5.034`、Apple clang `17.0.0`。所有 cocotb 用例均通过 `dv/cocotb/Makefile` 调度运行，构建时统一把仓库 `.venv` 注入到 `PATH` 中，以避免系统环境中不同版本的 Python 包影响仿真一致性。

对于模块级实验目录 `experiments/`，则单独维护了自己的 `Makefile`，能够直接以 `verif`、`lint`、`synth` 和 `sta` 为入口完成实验闭环。这样的组织方式使主线验证与独立 PPA 实验既共享同一套 Python 虚拟环境，又保持了各自的脚本自治性。

### 5.2 Testbench 文件描述

验证文件大致可以分为四类。第一类是算术原语与基础通路单测，例如 `test_fa_mul_sat_q8_8.py`、`test_fa_exp_pwl_8seg_q1_15.py`、`test_fa_recip_nr_q16_16.py`、`test_fa_dma_reader.py` 和 `test_fa_dma_writer.py`，用于保证局部算子的行为与接口握手正确。第二类是中层与核心模块测试，例如 `test_fa_attention_core.py`，其内部实现了内存模型、fixed-point Python 参考路径和 FP32 参考路径，能够在小参数与全参数两种配置下验证 attention 核心功能。第三类是顶层系统测试，例如 `test_fa_attention_ip_top_regs.py`，它通过 `AxiLiteMaster` 和行为级 `AxiMemoryModel` 模拟软件配置与外部存储系统，从顶层口径验证寄存器语义、DMA 事务、整轮 attention 运行和性能计数器读回。第四类是独立实验 testbench，例如 `experiments/fa_qk_dotprod_slice_pipe/tb/test_fa_qk_dotprod_slice_pipe.py`，用于对比多个实验变体之间的功能一致性。

从测试功能分布上看，当前验证体系已经覆盖了算子正确性、总线时序、配置语义、顶层运行、参考对照和性能计数这几个关键维度。虽然它还不是完整的约束随机与覆盖率驱动体系，但对当前项目阶段而言，已经能够有效发现设计 bug、握手偏差和性能计数口径问题。例如，之前顶层 perf counters 联调时，就是通过内存模型时序重写和对读写命令条数、beat 数的交叉比对，定位了 full-run 超时与统计口径不一致等问题。

### 5.3 具体功能验证说明

当前主线回归中，最重要的验证场景是 `fa_attention_core` 和 `fa_attention_ip_top` 的 full-parameter 用例。对前者而言，测试会以 `S=256`、`D=64`、`TQ=32`、`TK=64` 的默认参数构造 Q/K/V 数据，将矩阵写入仿真内存，再启动核心并等待全部 O 结果写回。测试中同时计算 fixed-point Python 参考和 FP32 参考，分别从“实现一致性”和“对算法高精度参考的偏差”两个维度给出量化结果。对后者而言，测试不仅要观察 `busy` 和 `done`，还要确认 `CTRL/STATUS` 的读写语义、DMA 命令发起情况和 perf counters 的统计值是否与内存模型计数一致。

从波形观察角度，最有代表性的信号组包括：AXI-Lite 的 `AW/W/B/AR/R` 五个通道、顶层 DMA 主口的 `AR/R/AW/W/B` 握手、核心内部 `ms` 与 `cs` 状态、`dma_rd_cmd_valid/ready` 与 `dma_wr_cmd_valid/ready`、`row_l` 和 `row_acc` 的局部更新，以及 `done` 与 `done_sticky` 的置位时刻。在当前验证流程中，虽然报告未附图形界面截图，但仿真环境已经允许通过 Verilator 导出波形并对这些关键信号进行逐拍排查。工程经验表明，绝大多数顶层级功能问题最终都能在这些信号组上被定位到明确的阶段边界。


## 5.4 0324 跨分支验证矩阵汇总

相比 0310 版本主要关注 baseline 单线，本次验证已经扩展成“主线 + bonus 线 + 推理线”的三层结构。

### 5.4.1 baseline 与系统扩展线

## 6. UVM 验证——模块功能和完整性测试

### 6.1 UVM 验证结构

UVM 体系目前尚未正式落地，但设计边界已经足够清晰。若进入下一阶段实现，建议将验证平台拆分为 AXI-Lite agent、AXI4 memory agent、寄存器模型、scoreboard、coverage collector 与虚拟序列六个主要部分。AXI-Lite agent 负责寄存器配置与轮询完成，AXI4 memory agent 则负责行为级存储阵列与突发事务。寄存器模型应覆盖当前 `CTRL/STATUS/CFG/BASE/STRIDE/SCALE/PERF` 全部窗口，并支持 `done-sticky` 的写 1 清行为。scoreboard 一方面对比写回的 O 矩阵，另一方面核对 DMA 事务条数和性能计数器口径。虚拟序列则负责组织短序列、全序列、causal/non-causal、错误注入、背靠背任务和长时间稳定性测试等场景。

从结构上看，现有 cocotb 验证已经为 UVM 搭建提供了相当完整的参考：内存模型可以映射到 AXI agent，现有 Python 参考可以迁移为 DPI-C 或离线黄金模型，寄存器访问路径则可以直接转化为 reg model 序列。因此，UVM 的工程量主要体现在把当前脚本化验证重构成类层次清晰、覆盖率可统计、随机约束可扩展的体系，而不是从零开始重建全部行为语义。

### 6.2 UVM 验证结果

截至本报告写作时，UVM 还未启动编码，因此暂无覆盖率统计、回归通过率或约束随机结果可汇报。这一节保留为后续阶段的规划接口。考虑到当前 baseline 功能、周期与精度已经具备稳定基础，下一阶段若进入更强的 SoC 集成和 bonus 功能开发，UVM 平台将成为验证复杂数据流、异常事务和系统互联边界条件的自然下一步。

## 7. 算法实现架构建模

### 7.1 周期精确的 CModel 建立

`cmodel/` 目录中的 C++ 工程承担两类工作：第一类是精度对照，第二类是吞吐与周期建模。其文件组织为 `attention_math.cpp`、`attention_kernels.cpp`、`attention_experiment.cpp`、`attention_lib.cpp` 和公共头文件 `attention_core.hpp`。其中，数学文件实现 fixed-point 算术与近似函数，内核文件实现 attention 计算流程，实验文件实现多种模式扫描、阶段误差分解和 compute-only 架构模型，而库文件则把这些功能组织为可执行工具。

该 CModel 的重要价值并不只是“再写一份软件版 attention”，而是在于它提供了严格对齐 RTL 结构的多种模式。例如 `rtl_strict` 模式沿用 PWL exp、NR reciprocal 和 fixed-point 位移链路；`rtl_real_exp`、`rtl_real_exp_float_norm` 则逐步替换局部算子，用于判断误差究竟来自哪里；`run_stage_decomp` 能对各个算子阶段分别做 MAE、MaxAE 和 RMSE 统计；`run_compute_cycle_model` 则能够在不真正写出 RTL 的前提下，对不同 lane 数、row 并行数和是否引入 NoC 的架构做周期估算。

### 7.2 精度/吞吐量建模及优化

精度建模部分的关键结论前文已经讨论：`acc` 是主导误差源，而不是 `exp` 本身。吞吐量建模部分则给出了另一个很重要的系统性判断。以 `docs/data/20260304_compute_cycle_models_s256d64.csv` 为代表的结果显示，当采用 `fixed_flow_l32_norm8_row2` 时，compute-only 周期约为 `100,608`；若将 row 并行进一步扩大到 4，则可下降到 `51,328`；而引入简单 NoC 后，虽然功能上更灵活，但附加的分发与同步开销会使总周期反而回升。因此，对于当前问题规模和当前设计阶段，固定指令流并行优先于引入额外网络结构，是一个更合理的工程决策。

### 7.3 测试结果

为了便于汇总，表 7-1 列出 CModel 中最具代表性的几组数据。

| 数据类别 | 代表结果 | 结论 |
|---|---|---|
| 阶段误差分解 `small-int + causal` | `acc` MAE=`135.58`，`norm` MAE=`1.865` | 误差主导来自累计与归一化 |
| 阶段误差分解 `gaussian + causal` | `acc` MAE=`464.11`，`norm` MAE=`33.44` | 高动态输入进一步放大累计误差 |
| 方案对比 `small-int + causal` | `acc_float_qout` / `acc_float_real_exp_qout` 可达标 | 证明累计精度是关键方向 |
| 计算周期模型 `fixed_flow_l32_norm8_row2` | `100608 cycles` | 说明当前 RTL 仍有进一步结构优化空间 |
| 计算周期模型 `simple_noc_l32_norm8_row4` | `71808 cycles` | NoC 并非当前规模下的必要条件 |

这些结果有两个直接意义。其一，CModel 不是与 RTL 相互独立的辅助代码，而是架构决策的重要支撑工具。其二，当前主线之所以能够在不牺牲正确性的前提下把周期降到十几万级，并不是凭经验试错，而是因为 CModel 已经提前揭示了哪些方向会有效、哪些方向虽然看起来高级但收益有限。

## 7.6 与 RTL 对齐的下一步

基于当前建模结论，RTL 对齐建议是：

1. 保持 mode14 作为 golden-like 对照；
2. 针对 mode15/17 热点层位（如 layer22/23, head1/8~13）导出 `m/l/acc/norm` 同名观测；
3. 做 merge 参数联合扫描（chunk、rounding、PV shift、round bias），按“首分歧 token 位置”排序，而非按单一 MAE 排序。

该路径比继续堆叠局部 guard 更有概率收敛到可替代 fixed 路线。
## 8. IP 核接入大模型推理

### 8.1 模型与推理框架

关于 LLM 接入，本项目已经完成较为系统的可行性分析。总体思路是在 C/C++ 推理框架中拦截 attention 模块调用，把原本由 CPU 完成的 SDPA 运算替换为 RTL IP 或其 Verilator/DPI-C 封装接口。理想情况下，软件侧只需要完成三件事：第一，把进入 attention 的浮点张量量化为 Q8.8；第二，把量化后的 Q/K/V 放入一段 DMA 可见内存；第三，启动 IP 并在完成后把 O 结果从 Q8.8 恢复成浮点再接回后续网络层。

需要指出的是，若完全不修改当前 RTL 主线，则模型选择必须考虑 `head_dim` 与上下文长度的兼容性。当前 IP 以 `D=64` 为默认参数，因此更直接匹配的是 `head_dim=64` 的模型或经过裁剪后的实验模型。若仍坚持沿大纲中最初提到的 `Qwen2.5-0.6B` 继续推进，则必须先确认该模型的 `head_dim` 是否与当前 IP 对齐；若不对齐，就需要将硬件扩展到 `D=128`，或者在软件侧做明确的模型裁剪与验证说明。从现有调研结论看，短期更稳妥的方案是优先选择 `head_dim=64` 的小模型或做受控实验模型，以降低接入阶段的不确定性。

### 8.2 针对 IP 核的推理引擎指令流优化

一旦把 attention 核从纯软件函数替换为硬件外设或其仿真模型，推理引擎层面的编排就变得重要起来。当前 IP 天然支持 tile 化，因此软件侧最直接的优化是让 `run.c` 或等价推理框架把 Q/K/V 的地址组织成与 IP tile 边界一致的布局，减少边界打包和额外拷贝。若未来要支持长于 `S=256` 的上下文，则更需要在推理框架层实现外层 block 调度，把一个长序列拆成多个 `256` 长度的 block，并结合外部存储层次或 scratchpad 做双缓冲搬运。

但需要注意，若要对大于 `256` 的上下文做严格等价的 FlashAttention block merge，IP 需要暴露中间的 $m$ 和 $l$ 状态，或者支持“续算模式”。如果只输出最终归一化后的 O，而不输出 block 级统计状态，那么多个 block 的结果无法在软件层无损合并。因此，当前推理引擎优化可以分成两个层次。第一个层次是不修改 RTL、仅在 `S\le 256` 的范围内做端到端联合仿真；第二个层次是为了支持更长序列，在 IP 协议层增加中间状态可见性，使软件得以正确完成 block merge。当前项目已经完成第一个层次的方案论证，第二个层次则属于 bonus 与系统扩展方向。

### 8.3 实测结果对比

`inference/native` 已经保留了一组本机 Q8.8 attention 替换实验结果，本轮未再重复长耗时跑批，而是把现有结果统一收集到 [docs/report_0310/report/logs/native](docs/report_0310/report/logs/native)。其中可直接引用的文件包括性能日志 [docs/report_0310/report/logs/native/perf.log](docs/report_0310/report/logs/native/perf.log)、trace [docs/report_0310/report/logs/native/trace.log](docs/report_0310/report/logs/native/trace.log)、吞吐汇总 [docs/report_0310/report/logs/native/q8_8_perf_results.csv](docs/report_0310/report/logs/native/q8_8_perf_results.csv) 与文本对比 [docs/report_0310/report/logs/native/q8_8_text_results.csv](docs/report_0310/report/logs/native/q8_8_text_results.csv)。

从文本一致性看，当前 CSV 共记录 `10` 组 prompt，其中 Q8.8 输出与 FP32 输出“完全一致”的只有 `2` 组，按严格字符串口径的 match rate 为 `20%`，统计摘要已单独存放在 [docs/report_0310/report/logs/native/native_metrics_summary.txt](docs/report_0310/report/logs/native/native_metrics_summary.txt)。这说明：一方面，Q8.8 attention 路径已经能够稳定跑通完整推理流程；另一方面，若以最终生成文本逐字一致作为标准，当前定点替换仍会带来明显语义漂移，因此后续对接 RTL 时必须把“是否能跑”与“文本是否严格保持”分开讨论。

从吞吐数据看，`10` 组样本上的平均结果为：FP32 路径 `QKV=7.969 GMAC/s`、`ATTN=1.936 GMAC/s`、`Pipeline=14.833 GMAC/s`、`ATTN_Time_%=13.840%`；Q8.8 路径则为 `QKV=8.243 GMAC/s`、`ATTN=5.582 GMAC/s`、`Pipeline=17.366 GMAC/s`、`ATTN_Time_%=5.440%`。虽然这些数字仍然混合了软件框架与本机 CPU 行为，但它已经说明当前 attention 替换后，热点占比确实从“明显 attention 主导”下降为“attention 不再是主导瓶颈”，这为后续用 DPI-C / RTL 核进一步替换 `flash_attn.c` 提供了现实依据。

具体到单条日志，[docs/report_0310/report/logs/native/perf.log](docs/report_0310/report/logs/native/perf.log) 记录了一次以 “Introduce the history of the Apple company.” 为 prompt 的本机运行。该运行成功完成了模型加载与文本生成，但回答内容明显偏保守、且未真正围绕苹果公司历史展开，这与上面的文本匹配率结论是一致的：当前 native Q8.8 路径已经能证明“算子替换可行”，但尚不能把其输出质量直接视为最终可交付的大模型推理质量。

### 8.4 结合 trace 的数据流分析与优化讨论

[docs/report_0310/report/logs/native/trace.log](docs/report_0310/report/logs/native/trace.log) 给出了 attention 替换在模型推理中的实际数据流展开。以 `pos=0` 的首 token 为例，每层都先执行 `Input RMSNorm`、`Q_proj/K_proj/V_proj` 与 `RoPE`，随后进入“FlashAttention Module Equivalent”阶段。trace 明确表明：当前模型的 attention 输入在每层表现为 `Q [14, 64]`、`K_cache [1, 2, 64]`、`V_cache [1, 2, 64]`，即共有 `14` 个 query head、每个 head 的 `head_dim=64`，而在序列初始阶段每个 head 只需要对极短的 K/V cache 做点积、softmax 与加权求和。

这个 trace 对硬件接入有三个直接启示。第一，当前 IP 的 `D=64` 与 trace 中的单头维度是对齐的，因此最小可行接入不必先扩维到 `128`，而是可以先围绕“单 head、head_dim=64、逐 head 调用”的方式完成 DPI-C 验证。第二，真正需要软件—硬件协同处理的是 head 维与层维的外层循环；对单次核调用而言，硬件只需负责某一 head 的 `QK^T + online softmax + PV`，而不需要吞掉整个 transformer layer。第三，decode 初期 K/V cache 很短，attention 计算量并不大，此时若直接调用 RTL 仿真核，调度、量化、内存拷贝和 DPI 交互开销很可能高于纯计算开销，因此应该优先在 prefill 或较长 decode 上下文中验证收益。

据此，后续优化建议可归纳为四点。其一，先把 `inference/native/flash_attn.c` 中单 head attention 调用封装成稳定接口，再以 DPI-C 替换其中的 `QK/softmax/PV` 核心，避免一开始就尝试把整层全部搬到 RTL。其二，优先复用当前 `trace.log` 中已经出现的 `head_dim=64` 场景，把硬件核视为“每 head 一次调用”的加速器，而不是要求硬件立即支持全部 `14` 个 head 并行。其三，在 RTL 侧应继续优先吸收 `fa_qk_dotprod_slice_pipe/exp_h` 与 `fa_online_softmax_ctx/exp_d` 这类已经完成频率验证的结构，因为它们恰好对应 trace 中最核心的两段计算。其四，若未来要覆盖更长序列，就必须把 block merge 所需的中间 `m/l` 状态或等效统计信息通过接口暴露出来，否则软件无法在多 block 场景下正确合并 attention 结果。


## 8.5 0324 接入状态：DPI 与 CModel 双后端并行

本阶段推理接入的本质变化是：attention 后端已经从单一软件路径扩展为可切换后端体系。

- `FLASH_ATTN_BACKEND=sw`
- `FLASH_ATTN_BACKEND=dpi`
- `FLASH_ATTN_BACKEND=cmodel`

并且 `inference/dpi/` 已形成 C API + Verilator wrapper + AXI-Lite/队列提交骨架，为后续真实 RTL 联调提供了稳定接口层。

## 8.6 DPI 现状与瓶颈量化

### 8.6.1 速度量级

当前 DPI 长跑样本显示：

- `prefill tok/s ≈ 0.0238`
- `decode tok/s ≈ 0.0232`

按 prefill 30 token 估算，首个 decode token 约需：

$$
30 / 0.0238 \approx 1260s \approx 21\text{分钟}.
$$

这与非 DPI 软件路径（几十 tok/s）存在数量级差距，说明当前瓶颈主要在仿真执行本体，而非单纯日志开关。

### 8.6.2 可读性问题

DPI 路径在 decode 早期出现 `token=72030 (/API)` 重复采样，形成模式坍缩。当前已通过三类证据定位：

1. top-k 直接对照（SW vs DPI）；
2. 层/头热力图（`layer23`、`head1/8~13` 热点明显）；
3. 最后激活统计（DPI `maxabs` 明显抬升）。

结论：问题已从“现象级”收敛到“logits 分布级”。

### 8.6.3 热点修复实验结果

热点回填（hotfix）能明显缓解 `/API` 坍缩，证明“晚层 attention 输出失配”是主链路；但该方案属于工程缓解，不是根因修复。

## 8.7 CModel 后端的阶段成果

### 8.7.1 可读性恢复

mode14 修复后，cmodel 在 chat/role 两类样本下均实现可读输出并与 sw 主干对齐。

### 8.7.2 速度对比

按 20260320 回归摘要，cmodel 在 chat 场景的平均吞吐处于可用区间：

- mode14: `avg_prefill≈23.933 tok/s`, `avg_decode≈16.649 tok/s`
- mode15+ks: `avg_prefill≈28.298 tok/s`, `avg_decode≈18.319 tok/s`（但质量不稳定）
- mode17+ks: `avg_prefill≈25.309 tok/s`, `avg_decode≈14.198 tok/s`

因此当前最合理的工程定位是：

1. cmodel 先作为稳定参考；
2. fixed 路线继续追质量，不以短期 tok/s 优势替代质量门槛。

## 8.8 从“可跑通”到“可交付”仍缺的三件事

1. DPI 需要从仿真级跑通转为质量稳定，先解决 decode 分布坍缩；
2. mode15/17 需要跨过 role prompt 稳定门槛，才能替代 mode14；
3. 推理框架需形成统一 benchmark 协议（同 prompt 集、同温度/采样、同统计窗口）以避免跨日志口径漂移。

这三件事完成后，IP 接入才可从“技术可行”进入“结果可交付”。
## 9. Bonus 功能实现

虽然本报告主体仍以 baseline 为中心，但当前工程中实际上已经包含若干具有 bonus 性质的能力。第一，perf counters 不仅满足调试需要，也为后续系统级性能感知与软件侧调度提供了硬件事件基础。第二，K/V 双缓冲预取与主线控制空拍压缩，使当前设计不再只是“功能正确的串行原型”，而是具备了真实吞吐优化特征。第三，QK 点积的多轮实验已经从浅层归并推进到乘法首拍和全流水加法树，为进一步逼近高频提供了结构模板。第四，围绕长上下文支持、block merge、DPI-C 联合仿真和 LLM 接入的方案分析，也已把 bonus 扩展的技术边界梳理得较为清楚。

## 10. 逻辑综合与物理实现

### 10.1 具体方案

当前综合与时序分析采用两阶段策略。前期使用 Yosys 进行逻辑综合，并通过 iEDA 完成基于 icsprout55 的 pre-P\&R 静态时序分析，主要目标是定位中前端的结构瓶颈，而不是给出最终流片级物理结果。后期若项目进入更完整的实现阶段，则再迁移到 Cadence 工具链做完整后端流程，包括 floorplan、placement、CTS、routing、功耗分析和版图签核。

这种策略的合理性在于，当前项目仍处于架构快速迭代期。对于 QK、Online Softmax、Normalization 等模块，决定频率上限的往往是“这一拍做了什么组合逻辑”，而不是“标准单元摆在芯片上的具体位置”。因此先用综合和 STA 快速识别最长路径、面积量级和结构性趋势，再决定是否继续拆拍或重构 datapath，是成本最低、信息量最高的做法。

### 10.2 版图结果与面积分析

当前尚无完整 Cadence 版图结果，因此面积分析仍以综合报告中的 cell area 为主。尽管如此，这些数据已经足以揭示各热点模块的相对规模。举例而言，`fa_online_softmax_ctx/exp_d` 的面积约为 `27216.28`，说明 softmax leaf 本身虽然时序敏感，但绝对面积并不高；`fa_o_normalize_block_pipe/exp_d` 的面积约为 `238672.84`，说明 64bit 归一化链路会带来较大面积负担；QK 点积实验 `exp_g` 与 `exp_h` 的面积分别约为 `272855.24` 和 `286906.48`，则表明高宽度并行乘加树是当前最主要的面积热点之一。倒数模块 `fa_recip_nr_q16_16/exp_c` 的面积约为 `60594`，在达到 500MHz 收敛的同时面积增量仍然可接受。需要额外说明的是：当前主线把 `ctx` 以按维复制的方式接回 core，因此单实例 `27216.28` 只能作为 leaf 级数据参考，不能直接当作当前 softmax 子图总面积来理解。

这些数据有一个直接推论。若未来需要进一步压缩面积，单靠在线 softmax 或倒数模块的局部优化意义有限，因为它们的绝对面积并不构成系统主导项；真正需要做结构权衡的是 QK 和归一化等高位宽、高并行路径。与此同时，若只从“面积—频率收益比”角度看，Online Softmax 是目前最值得继续保留和吸收独立实验成果的模块，因为它已经证明可以以相对温和的面积代价换来非常显著的频率提升。

首先看 QK。`exp_f/g/h` 已经证明“乘法首拍 + 全流水二叉树”是正确方向，且 `exp_h` 把最差端点收缩到 `mult*_r`，说明当前瓶颈已从宽加法树转移到**输入总线驱动乘法器阵列**与**单乘法器叶级路径**。因此下一轮最值得做的实验，不应再回到 `exp_e` 那类局部乘加块细修，而应围绕以下三类：

1. **输入扇出继续收敛的 `exp_i` 类实验**：在 `exp_h` 的输入预寄存基础上，继续做输入寄存复制、按 `16+16` 子阵列分组、局部 bank 化布线友好组织，目标不是改变 `32-lane` 与 `II=1`，而是进一步降低“输入寄存到 32 个乘法器”的单拍扇出压力。
2. **乘法叶级本体优化的 `exp_j` 类实验**：既然关键路径已经稳定落到 `mult*_r`，下一步应尝试 Booth/部分积型乘法 RTL、或把 `16×16` 乘法明确重写成更物理友好的两级部分积与 CSA 结构，验证是否能把 `442.5MHz` 再往上推近 500MHz。
3. **带 tag 的流式回收原型**：独立模块已经是长流水，真正限制系统表现的是当前 core 没有把这条流水隐藏起来。因此应做一个带 `qpair/chunk` tag 的 QK slice 原型，让 `fa_attention_core` 可以连续发射多个 score-pair，再按 valid/tag 回收部分和。这类实验本身不一定改变 leaf STA，但对系统周期至关重要。

其次看 Norm。`exp_d` 通过高低半字部分积，把频率从约 `264MHz` 提升到 `360.8MHz`，说明该路径仍有结构空间，但它和 QK 不同：Norm 的主问题不是单一超宽扇出，而是**64bit 累计量 × Q16.16 倒数**后在同一路径上完成重组、舍入与饱和。因此下一轮实验建议集中在：

1. **更细粒度部分积 + carry-save 累加**：把当前 `pp_lo/pp_hi` 再细分为更规整的部分积树，并将最终 CPA 尽量后移，避免在单拍内同时完成过长的乘法重组。
2. **符号/绝对值/饱和路径解耦**：将 sign handling、rounding 和 saturation 明确拆到独立末级，验证当前关键端点是否其实卡在“乘积重组 + 饱和判断”的混合逻辑上。
3. **系统级 overlap 友好版本**：对 Norm 而言，未必一定要把 leaf 本身硬推到 500MHz 才有价值。若能把倒数请求更早发起、把 normalize chunk 与写回重叠，系统收益可能大于继续单独深挖 leaf STA。因此建议增加一类“保持 `exp_d` 叶结构、但改变 core 发射节奏”的系统实验。

综合来看，QK 更适合继续沿“叶级继续压关键路径 + core 做流式 tag 回收”双线推进；Norm 则更适合做“适度继续拆 leaf + 更强调系统 overlap”的组合策略。若只按优先级排序，下一步仍应先做 QK，再做 Norm。

#### 10.3.3 功耗分析

当前流程尚未形成完整的向量驱动功耗报告，因此本节只能给出定性分析而不提供签核级数值。一般而言，QK 点积模块由于具有大量并行乘法器和较宽寄存器阵列，是最可能同时成为面积与功耗热点的单元。归一化模块虽然频率较低，但 64bit 数据路径同样会带来不低的切换活动。Online Softmax 模块的面积和切换范围都相对较小，因此在总功耗中的占比预计不会像其时序重要性那样突出。待后续引入更稳定的门级网表与活动文件后，可再补充 VCD/SAIF 驱动的动态功耗分析与静态泄漏分析。

### 10.4 DRC \& LVS 验证

基于 Cadence 的完整后端尚未开展，因此目前没有可报告的 DRC 与 LVS 结果。现阶段使用 Yosys+iEDA 的目的主要是进行中前端结构收敛，而不是替代完整签核流程。后续若项目进入版图阶段，应在统一工艺库和约束环境下补齐版图生成、DRC、LVS、IR drop 和功耗完整报告。

### 10.5 总结

基于 icsprout55 的当前工作已经足够支持一个明确判断：项目的中前端热点和优化方向已被较清晰地定位。倒数与 Online Softmax 路径已经证明能够通过适当流水化达到或超过 500MHz；Normalization 有改善但优先级次之；QK 路径在本轮通过全流水乘法—加法树重构后已经被显著推进到 400MHz 以上，但仍是距离 500MHz 最近却也最难完全闭合的关键瓶颈。基于 Cadence 的完整物理实现尚未启动，但这并不妨碍当前基于 pre-P\&R 的结果对主线架构演进产生直接指导价值。

### 10.6 自评：`syn/` 覆盖完整性与自顶向下 PPA 估算

本小节仅用于自评，不作为正式报告对外展示内容。与前一版报告相比，本轮最大的变化不是“又多做了几个实验”，而是把真正已经被主线实例化的实验结构整理回了当前 RTL 命名体系：`fa_qk_dotprod_slice` 与 `fa_o_normalize_block` 现在已经分别对应 `exp_h` 与 `exp_d`；online softmax 也已经从 archived `pair` 切回 `ctx` 家族；`fa_dma_reader`、`fa_dma_writer` 与 `fa_perf_counters` 也已经补齐当前主线的直接 STA 结果。因此，`syn/` 对当前有效 leaf RTL 的覆盖已经明显强于上一版审计时的状态。

其次，从主线实例化关系看，当前 `fa_attention_ip_top` 直接例化 `1` 个 `fa_axi_lite_regs`、`1` 个 `fa_perf_counters`、`1` 个 `fa_dma_reader`、`1` 个 `fa_dma_writer` 与 `1` 个 `fa_attention_core`；`fa_attention_core` 内部再直接例化 `1` 个 `fa_qk_dotprod_slice`、`ROW_PAR=2` 个 `fa_mul_sat_q8_8`、`ROW_PAR×D=2D=128` 个 `fa_online_softmax_ctx`、`1` 个 `fa_recip_nr_q16_16` 与 `1` 个 `fa_o_normalize_block`。这里必须强调：`2D=128` 个 `ctx` 实例是本轮为了把 `ctx/exp_d` 功能恢复到主线而采用的**直接复制接法**，它不是最终 PPA 口径下希望长期保留的系统结构。

为了得到可用的 top-down 粗估，本报告继续采用“逻辑功能块 × 当前最佳候选模块面积”的保守方法，对**未来真正调度闭环后的主线**做一个结构下界估计，而不是把当前临时 `128×ctx` 接法直接乘进面积。参与估算的单模块面积分别取：`fa_axi_lite_regs=4399.64`，`fa_mul_sat_q8_8=4469.36`，`fa_recip_nr_q16_16(exp_c)=60594.24`，`fa_online_softmax_ctx(exp_d)=27216.28`，`fa_o_normalize_block(exp_d)=238672.84`，`fa_qk_dotprod_slice(exp_h)=286906.48`。按 `1×AXI-Lite + 2×mul_sat + 1×recip + 1×softmax + 1×normalize + 1×QK` 相加，可得到一个“面向未来合理主线结构、只覆盖主要已知计算块”的面积下界：

$$
4399.64 + 2\times 4469.36 + 60594 + 27216.28 + 238672.84 + 286906.48 = 626727.96.
$$

这个 `626727.96` 只能视为**核心已知块的面积下界**，因为它还没有计入 `fa_attention_core` 本身的控制逻辑、`fa_dma_reader`、`fa_dma_writer`、`fa_perf_counters`、顶层 glue logic，以及更重要的片上 buffer / 寄存阵列在完整顶层中的真实物理代价。换言之，如果未来把 `exp_h + exp_d + exp_d + exp_c` 这组最佳候选真正集成进主线，那么完整顶层的面积只会比这个数字更高，不会更低。

从时序角度看，这个自评揭示了一个更清晰的现实：当前主线最关键的“已吸收优化结构”已经从实验态转成了正式 RTL，而且 `QK` 与 softmax 的 system-level overlap 也已经兑现到当前 `main` 的实测周期上。具体来说，当前主线 full-run 已读回 `cycles=85928`、`cs_dp_run_cycles=66560`、`cs_softmax_prep_cycles=32768`；这说明问题已经不再是“高频候选模块是否被 core 以正确节奏使用”，因为这一点已经在当前主线中基本解决。因而后续若要把自评真正做扎实，优先级应转向：第一，补跑 `fa_attention_core` 与 `fa_attention_ip_top` 的直接综合，并重新核对 cycles / PPA；第二，针对当前 128 个 `ctx` 叶实例的面积与布线代价做更系统的 top-down 审计；第三，再把长序列、padding、multi-head 与 task queue 等 bonus 方向工程化落地。


## 10.7 0324 PPA 阶段结论（跨分支）

0310 的 PPA 结论主要针对 Q8.8 主线 leaf；0324 需要补充“哪些分支已进入可比 PPA 阶段，哪些仍是功能原型阶段”。

### 10.7.1 Q8.8 主线（可比阶段）

Q8.8 主线仍是当前唯一具备较完整系统口径的 PPA 参考：

1. 周期、误差、DMA、perf counters 都已闭环；
2. leaf STA 已有多轮结果；
3. 具备明确的系统瓶颈解释。

因此，若需要对外提供“当前 IP 的可信 PPA 数字”，仍应以该线为主。

### 10.7.2 Bonus 分支（非同等级 PPA）

- `exp/padding-mask-s512`：系统功能闭环成熟，但尚缺与 baseline 同深度的综合对照矩阵；
- `exp/bonus2-mha`：周期线性可解释，但并行化前提下的面积/时序收益尚未展开；
- `exp/bonus9-task-queue`：控制面扩展明显，PPA 影响主要在寄存器与控制逻辑，不在算术热路径；
- `exp/bonus1-bf16` 与 `exp/int8-fp8-bootstrap`：当前重点仍在算法/结构可运行性，尚未进入与主线同口径的工艺级比较。

结论：目前不能把低精度分支的“局部模块可跑”直接外推为主线等价 PPA 结论。

## 10.8 吞吐、带宽与频点的统一工程口径

为了跨分支比较，建议后续固定输出以下四项：

1. `cycles`（统一问题规模）
2. `GOPS/GHz`（算术吞吐）
3. `bytes/cycle`（带宽压力）
4. `bus_util`（相对理论总线利用率）

以 baseline 为例：

- `cycles=85928`
- `GOPS/GHz=195.247`
- `bytes/cycle=6.864`

以 `S=512` 为例：

- `cycles=307024`
- `GOPS/GHz=218.580`
- `bytes/cycle=7.26`（按 top/IP 数据）

该口径能同时体现“算得快不快”和“搬得重不重”，比单看 cycles 更有解释力。

## 10.9 面向 500MHz 的下一阶段建议（系统视角）

在 0310 版中，500MHz 讨论主要集中在 leaf；0324 阶段建议把目标拆成双层：

1. leaf 层：继续压 QK/Norm 关键端点；
2. system 层：避免把 leaf 频率收益被调度气泡和数据搬运抵消。

重点动作：

1. 对 `fa_attention_core` 和 `fa_attention_ip_top` 补跑直接综合，形成 top-down 时序证据；
2. 量化 queue/multi-head/s512 分支对控制逻辑面积和关键路径的影响；
3. 对 `valid_len` 场景补充 DMA 裁剪实验，观察 bytes/cycle 改善幅度。

若不补这三项，下一轮 PPA 仍会停留在“leaf 很强，但系统收益不可量化”的阶段。

## 10.10 0324 小结

当前 PPA 可信度排序：

1. Q8.8 baseline 主线：最高；
2. `S=512/valid_len/multihead/queue` 系统扩展：中等（功能强，PPA 对照待补）；
3. BF16/FP16 与 INT8/FP8：原型验证为主，PPA 结论暂不对外外推。

这一定义有助于避免在报告中把“研究原型性能”误写成“可交付 IP 性能”。

> **禁止显式存储完整注意力矩阵**

这一要求已经完成，而且是当前 RTL 架构的核心前提。`fa_attention_core` 中只保存 `q_buf[TQ][D]`、双 bank `k_buf/v_buf[TK][D]`、按 query row 维护的 `row_m[TQ]`、`row_l[TQ]`、`row_acc[TQ][D]`，以及最终的 `o_buf[TQ][D]`。整个设计中都不存在 `score[S][S]` 或任何等价的完整注意力矩阵缓存。也就是说，对每个新得到的 score，设计会立刻做缩放、online softmax 状态更新和 PV 累加，而不是先把一整行或整个 `S\times S` 分数矩阵写到片上再统一处理。

从数据流角度看，这一点和 FlashAttention 的原始动机一致：当前默认参数下，若显式缓存 `256\times256` 个 score，即使用 16bit 表示，也需要约 `128KB` 级别片上存储；而当前主线把片上主要存储压缩到 Q/K/V tile buffer 与 row context 上，主存储量约为 `56KB` 级别。换言之，本设计不是“没有做 attention matrix buffer 只是巧合”，而是**从存储组织一开始就排除了这条路线**。

> **必须使用在线（online）softmax**

这一要求已经完成。算法公式层面，主线始终按 online softmax 的递推更新 `m/l/acc`：当新 score 到来时，只基于上一拍的 `m/l/acc` 与当前 `(score, value)` 做状态推进。当前版本中，softmax 路径已切回 `fa_online_softmax_ctx` 家族；在 `fa_attention_core` 内部，当前不仅保留了按 lane 复制的 `ctx/exp_d` 叶模块，还通过 `SOFTMAX_CTXS=4`、batch 化 row-pair 调度与 tag 化回收把它真正纳入流式系统调度中。

功能验证上，当前重新回归后，`fa_online_softmax_ctx` 单模块 cocotb 通过，`fa_attention_core` 通过，`fa_attention_ip_top` 也再次通过。这说明 online softmax 不只是“算法文档里写了”，而是已经在当前 RTL 与顶层系统回归中闭环。与此同时，本轮新建文档 [docs/20260310_online_softmax_ctx_pair_base2_comparison.md](docs/20260310_online_softmax_ctx_pair_base2_comparison.md) 已专门把 `ctx/pair/base2` 的实现差异与数据关系梳理清楚，避免后续再混淆“当前主线结构”和“历史实验候选”。

> **必须分块（tiling）处理 K/V**

这一要求已经完成。主线默认参数固定为 `TQ=32`、`TK=64`，因此 `SEQ_LEN=256` 会被拆成 `8` 个 Q tiles 和 `4` 个 K/V tiles。具体实现上，主状态机 `ms` 先读入一个 `Q tile`，随后对全部 `K/V tiles` 做内层遍历；每处理一个 `K tile` / `V tile`，就在 `S_COMPUTE` 中把 score、softmax 与 PV 累加流式完成。这样既限制了片上 buffer 规模，又保证了 K/V 以 tile 为单位被重复搬运和计算。

选择 `TQ=32`、`TK=64` 的原因，也已经在 RTL 与理论分析里被量化：`Q tile` 为 `4KB`，`K tile` 或 `V tile` 各为 `8KB`，与当前 `128bit` 总线、每 beat `8` 个 Q8.8 元素的搬运粒度是匹配的。顶层 full-run perf 读回的 `DMA_RD_CMD_COUNT=136`、`DMA_RD_BEAT_COUNT=34816`、`DMA_WR_CMD_COUNT=8`、`DMA_WR_BEAT_COUNT=2048` 也与这套 tile 组织高度一致，说明 tiling 不是停留在结构图上的概念，而是已经在系统层真实发生。

> **输入输出必须采用 Q8.8 定点格式，并保证内部有足够累计精度**

这一要求已经完成。`Q/K/V/O` 都采用 Q8.8；QK 点积结果先在 Q16.16 域内累计，再通过 40bit 中间和送入缩放；row 级累计接口 `row_acc` 仍保留为 64bit；倒数模块使用 Q16.16。当前 streamed `ctx` 主线内部的 softmax leaf 使用 32bit `l/acc` 标量状态，随后由 core 写回 64bit `row_acc` 接口，并在 normalize 入口补齐当前主线所需的尺度对齐，因此整个数值链路已经在当前 `main` 上重新闭合。

验证层面，这条数值路径已经在 core/top cocotb 中被 fixed-point 参考和 FP32 参考同时审计。当前主线在修正 `acc -> normalize` 尺度口径后，顶层 full-run 再次读回：RTL 相对 fixed-q8.8 参考 `mae_lsb=0`、`max_err_lsb=0`，相对 FP32 参考 `mae=0.002499`、`max_err=0.006583`，说明当前 `main` 已重新满足赛题精度门限，并且 fixed-point 参考也已与当前 RTL 主线对齐。

> **必须提供 AXI-Lite 控制接口**

这一要求已经完成。`fa_axi_lite_regs` 提供 `CTRL/STATUS/CFG/Q_BASE/K_BASE/V_BASE/O_BASE/STRIDE_BYTES/SCALE/NEG_LARGE/CYCLES/PERF_*` 等寄存器窗口。顶层寄存器回归已覆盖：

1. 默认寄存器值；
2. `CTRL` 启动脉冲；
3. `STATUS` 中 busy / done-sticky / error 语义；
4. 基地址与 stride 配置；
5. perf counters 的读回窗口。

这意味着 host 侧已经可以把本 IP 作为标准的“配置—启动—轮询完成—读结果/读统计”设备来使用。

> **必须提供 AXI4 Master DMA 数据接口**

这一要求已经完成。`fa_dma_reader` 负责从外部内存搬运 Q/K/V tile，`fa_dma_writer` 负责把 O tile 写回外部内存。主线核心通过 `dma_rd_cmd_*` / `dma_wr_cmd_*` 只下发逻辑命令，而不直接操纵 AXI 五通道细节，这使 tile 调度与总线协议保持了清晰边界。

验证上，单模块 DMA 测试已经覆盖 burst、错误返回、长命令拆分等基本场景；顶层 full-run 中又进一步把命令数与 beat 数与行为级内存模型统计交叉校验。当前 full-run 再次读回的 `rd_cmd=136`、`rd_beat=34816`、`wr_cmd=8`、`wr_beat=2048` 与内存模型观测一致，说明 DMA 不仅“能搬”，而且其统计口径也可信。

> **必须形成完整的端到端 attention 计算闭环**

这一要求已经完成。当前主线顶层 `fa_attention_ip_top` 已经把寄存器配置、DMA 读写、tile 调度、QK 点积、online softmax、normalize 和写回全部连通。本轮在把 online softmax 切回 `ctx` 后，又重新完成了三层回归：

1. `fa_online_softmax_ctx` 单模块 PASS；
2. `fa_attention_core` PASS；
3. `fa_attention_ip_top` PASS。

因此，当前结构变化没有破坏主线功能闭环，这也是本轮先做恢复、再谈调度优化的前提。

> **性能指标完成情况**

在功能项上，以上要求都已经完成；在性能项上，当前 `main` 也已经形成统一口径。

当前顶层 full-run perf 读回为：`cycles=85928`、`busy=85928`、`cs_dp_run_cycles=66560`、`cs_score_done_cycles=32768`、`cs_softmax_prep_cycles=32768`。其中：

1. `QK` 的 `8` 拍流水延迟已不再对每个 score-pair 重复支付，而是按 batch 支付；
2. `ctx` 的 `4-context` 交错能力已被当前主线调度真正利用；
3. `score retire`、`softmax issue` 与 `QK issue` 已发生重叠；
4. 最终总周期显著低于 baseline 要求的 `<300k cycles`。

因此，当前项目在性能层面的结论已经从“高频 leaf 能工作，但 system 仍未闭环”，转变为：

> **当前唯一活动主线 `main` 已经完成周期与精度双闭环，下一步工作的重点应从“主线达标”转向“bonus 扩展能力、分支管理与更完整 PPA 收敛”。**

## 11.4 当前最重要的“已知事实”

1. baseline 核心指标稳定：`85928 cycles` 与既有精度口径保持不变。
2. `S=512` top/IP 闭环已成立，但周期约 `307024`，不应与 baseline 目标混写。
3. `Q6.10/Q4.12` 当前属于外部格式桥接，不代表内部全链路多精度。
4. MHA 顺序版已展示良好线性缩放，但并行收益仍待架构重构。
5. task queue 已完成 true FIFO 形态与异常语义，具备进一步系统化条件。
6. mode14 已成为推理稳定参考；mode15/17 仍在“可读性改进但未替代”阶段。
7. BF16/FP16 与 INT8/FP8 分支均有实质进展，但仍属并行研究线，暂不并入 baseline 口径。
