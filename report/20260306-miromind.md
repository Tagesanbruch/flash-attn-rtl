# 任务 A：系统级吞吐指标与“先估算再改 RTL”的方法论

## 1. 适合当前项目的 system-level 指标体系

在你已经明确“500MHz 只是观察点”的前提下，可以直接采用一组与 FlashAttention 算法强相关、又便于 RTL 前期粗算的指标体系：

1. **端到端单次 SDPA 时延**

\[
\text{Latency}_{SDPA} = \frac{\text{cycles}_{SDPA}}{f_{clk}}
\]

2. **端到端 SDPA 吞吐**

\[
\text{Throughput}_{SDPA} = \frac{f_{clk}}{\text{cycles}_{SDPA}}
\]

3. **算力利用率（MAC 利用度）**

FlashAttention 单头 S=256, d=64，精确 MAC 数：

- QKᵀ：\(S^2\cdot d = 4{,}194{,}304\) MAC  
- PV：同样 4,194,304 MAC  
- 合计：8,388,608 MAC

如果当前并行 MAC lane 数为 `P`（例如 32），则平均利用率：

\[
U_{MAC} = \frac{8{,}388{,}608}{P \cdot \text{cycles}_{SDPA}}
\]

这个指标可以用来判断“算子流水加深后是否有效被利用”：一旦 cycles 明显涨、但 U_MAC 反而下降，就属于典型“伪优化”。

4. **面积效率**

\[
\text{AreaEff} = \frac{\text{Throughput}_{SDPA}}{\text{Area}}
\]

在 2M gates 约束下，任何“多给两倍 MAC、吞吐只升一点点”的改动都可以被这个指标筛掉。

5. **I/O 效率**

\[
\text{BytesPerSDPA} = \text{总 RD/WR Bytes}
\]

结合 \(\text{Throughput}_{SDPA}\) 可以看每秒 DRAM 需求是否在接口能力范围内；一旦算子流水加深导致 K/V 重读增加，就会明显恶化这个值。

> 建议在工程上把 **`Throughput_{SDPA}`, `U_MAC`, `AreaEff`, `BytesPerSDPA`** 四个量列成一个表，每次改架构之前先做估算。

---

## 2. 哪些结构最容易出现“局部 Fmax 变好，系统反而变慢”

结合 SystolicAttention 的分析框架和你当前 pair-wise FSM 的组织方式，可以明确以下几类高风险结构：

1. **串行 pair-wise FSM + 深流水算子**

- 当前 `fa_attention_core` 中对 `(i,j)` pair 的逐点处理，如果每一个 pair 都要等 `fa_exp_pwl`、`fa_mul_sat` 的全流水完成再进入下一个 pair，那么：
  - 局部 Fmax 可以从 400MHz 抬到 600MHz；
  - 但 **每个 pair 生效间隔从 1cycle 变成 Ncycle**（N=流水深度），总 cycles 按 N 倍膨胀。
- 这在 SystolicAttention 中被明确避免：他们把 softmax 和 matmul 全部吸进 systolic array 内部，通过流式数据流和行级/列级复用，把算子 pipeline latency 变成“空间移动”，而不是“时间等待”[1]。

2. **online softmax 纯串行、没有多行交错**

- 当前 online softmax 递推：

\[
l_i = l_{i-1}\cdot e^{m_{i-1}-m_i} + e^{x_i-m_i}
\]

如果流水深度从 1 加到 4，但仍要求 `i` 依赖 `i-1` 的输出（同一行、同一上下文），等价于把 critical path拆散却放大循环体长度。
- Softermax 显示了一个典型反例：他们通过在线归一化和 base-2 形式，把“更新 max / renorm”做成移位和累加，可在流水化的同时仍保持 **II≈1**[2]。

3. **exp / reciprocal / mul 分散在不同模块，缺乏融合**

- “exp 模块 → mul 模块 → add 模块”的单链式组织，会将所有子单元的组合延迟串在一条 critical path 上。
- ExpMul 的做法是直接提供一个 `ExpMul(x, v) ≈ e^x * v` 的融合算子，把 log 近似和 exponent shift 合并，**一方面减少模块数量，另一方面避免多级握手等待**[3]。

## 3. “先估算再动 RTL”的轻量建模方法

结合你现在的 S=256, d=64，一次 attention 的 **理论最佳 cycles 下界**（理想 MAC 利用率=100%）：

\[
\text{cycles}_{ideal} = \frac{8{,}388{,}608}{P}
\]

例如 P=32 → 约 262,144 cycles。你现有 148,656 cycles，说明已经通过在线 softmax 与 tiling 融合，显著低于“朴素双 matmul”估算。

要在加流水前评估影响，可以在工程脚本中加上一套简单的 **stage 级时序-周期模型**：

1. 对每个算子维护 4 个参数：

- \(L_{op}\)：组合延迟（ns）
- \(D_{pipe}\)：流水深度（级数）
- \(II_{op}\)：启动间隔（目前多为 1）
- \(N_{use}\)：在一行 / 一次 SDPA 内被调用次数

2. 对给定目标周期 \(T_{clk}\)（例如 2ns 对应 500MHz），检查：

- 若 \(L_{op} \le T_{clk}\)：该算子在当前频率下可 1 级实现，D_pipe 视为 1。
- 若 \(L_{op} > T_{clk}\)：需要增加 \(D_{pipe} = \lceil L_{op} / T_{clk}\rceil\) 级。
- 如果调度不变、pair-wise 等待，则 **总 cycles 惩罚**大约为：

\[
\Delta \text{cycles}_{op} \approx N_{use}\cdot (D_{pipe}-1)  
\]

3. 如果调度采用 **行级或多行交错**，则可引入一个“可隐藏比例” \(\alpha \in [0,1]\)：

\[
\Delta \text{cycles}_{effective} \approx (1-\alpha)\cdot \Delta \text{cycles}_{op}
\]

- 纯串行 FSM：\(\alpha \approx 0\)
- 完全行级 overlap（如：行 i 做 PV，行 i+1 做 QK+softmax）：\(\alpha\) 可以接近 1

这一套估算可以写成 Python/Excel 脚本，把你关心的 3 个模块 `fa_mul_sat_q8_8`、`fa_exp_pwl_8seg`、`reciprocal` 的 Fmax / 深度 / N_use 填进去，在动 RTL 前先看：
- 如果为了从 400MHz 推到 600MHz，需要 D_pipe=3，但在现有调度下 \(\Delta cycles\) 导致 `f_clk/cycles` 实际 **下降**，则这个改动直接否决。

## 4. 优化优先级建议（Task A）

综合文献经验与你当前 baseline 数据，推荐的优先序：

1. **先改调度 / 微架构（行级 overlap、online softmax 结构）**
   - 不动算子逻辑，先把 pair-wise FSM 改成 **row-level pipeline**：  
     - 行 r：做 PV  
     - 行 r+1：做 QK + 在线 softmax  
   - 这一点在 SystolicAttention 和 FlashAttention-4 中都被证明是系统级提升的关键[1][3]。
2. **在调度具备隐藏能力之后，再加深关键算子的流水**
   - 例如让 `fa_exp` 从 1 级变 3 级，但通过行内/行间重叠，把 II 保持在 1。
3. **最后再考虑增加算子数量（更多 MAC lane、并行 exp 单元）**
   - 这一步主要受面积与带宽约束，一般在前三项优化空间吃完后才值得动。

# 任务 B：online softmax 递推的流水化 / 交错化方案

## 1. 最值得参考的 3–5 类结构

### 结构 1：行顶 CMP Row + in-array online softmax（SystolicAttention 风格）

- **核心思想**：在阵列顶部加一行比较单元（CMP row），在 QKᵀ 生成 score 的同时：
  - 实时计算当前行的 `rowmax`
  - 计算 `S - rowmax` 并送入下游 exp 路径
- softmax 所需的 `max`、`exp`、`rowsum` 全部在阵列内部以“流式”方式完成，去掉外部串行 online softmax 单元[1]。
- 反馈链（`m/l/acc`）不再是集中式寄存器 + 复杂组合逻辑，而是“按列分布”的小状态机，大幅缩短关键路径。

### 结构 2：Softermax base-2 online normalization

- **核心思想**：[2]
  - 把 softmax 的指数 base 从 e 换成 2：\(e^x \to 2^{x'}\)
  - 用整数 max 保证 `OldMax - NewMax` 是整数
  - renorm 因子变成 `2^{OldMax - NewMax}`，可以用 **移位器** 实现，而非乘法
- online 递推类似：

\[
\begin{aligned}
m_i &= \max(m_{i-1}, x_i) \\
l_i &= 2^{m_{i-1}-m_i} \cdot l_{i-1} + 2^{x_i-m_i}
\end{aligned}
\]

- 因为 max 差是整数，`2^{m_{i-1}-m_i}` 是纯移位，管线可做得很深而不影响 II=1。

### 结构 3：行级多上下文（multi-row）交错

- 每一条 online softmax pipeline 不只服务“一个 query 行”，而是维护若干个 **context slot**（例如 4 个行）：
  - cycle 0：slot0 的 i=0  
  - cycle 1：slot1 的 i=0  
  - cycle 2：slot2 的 i=0  
  - cycle 3：slot3 的 i=0  
  - cycle 4：slot0 的 i=1  
- 这样即便一个 pipeline 内部有 3–4 级 latency，也可以通过 4-way interleave 把 II 压到 1，相当于把数据相关性隐藏在不同上下文之间。

### 结构 4：ExpMul 驱动的 online update

- FlashAttention-2/4 提出的 ExpMul 算子，把 `e^{Δm} * v` 融合成单个硬件路径[3]：
  - `ExpMul(Δm, v)` 直接用近似 log2/shift 执行，无需独立 exp 与 mul。
- 把 online softmax 的递推：

\[
acc_i = acc_{i-1}\cdot e^{m_{i-1}-m_i} + e^{x_i-m_i}\cdot v_i
\]

  改写为两次 ExpMul：

\[
acc_i = \text{ExpMul}(m_{i-1}-m_i, acc_{i-1}) + \text{ExpMul}(x_i-m_i, v_i)
\]

- 在 RTL 上，反馈链只需等待 ExpMul 输出，而 ExpMul 自身可以高度流水。

## 2. 各类结构对当前项目的改造代价与系统影响

用简表总结（定性）：

| 结构 | 对现有 RTL 改造量 | 时序潜力 | cycles 变化 | 吞吐影响 | 误差风险 |
|------|------------------|----------|------------|----------|----------|
| CMP Row + in-array softmax | 大（需改 array＋控制） | 高（消掉集中式 recurrence） | 轻微增加/持平 | 显著↑（QK/softmax/PV 融合） | 极低（已有浮点实证）[1] |
| Softermax base-2 online norm | 中（softmax 路径重写） | 高（关键路径变为移位+LUT） | 基本不变 | 明显↑（不再有 max-pass） | 需重新评估 Q8.8 误差[2] |
| 多行交错 multi-context | 中（需要 context buffer + round-robin） | 中（本身不缩短路径） | 略↑（管理开销） | ↑（可隐藏 pipeline latency） | 极低 |
| ExpMul online update | 中偏大（替换 exp+mul） | 很高（单算子短路径） | 基本不变 | ↑（exp 成本变小，可增加并行度） | 取决于对近似 log2 精度控制[3] |

从“系统级吞吐 / 实现复杂度”权衡：

- 若你更愿意逐步演进，而不是一口气上完整 systolic array，**Softermax 风格在线归一化 + 适度行级交错** 是当前 RTL 上最现实的切入点：
  - 不需要改整个 compute fabric，只是把 online softmax 单元改写成 “base-2 + shift renorm”；
  - 把原本长的 `m/l/acc` 组合链拆成 2–3 级小操作（max、差值、移位、加法），整体时序可从 189MHz 拉到 300MHz+，在 55nm 下是合理目标。

## 3. 推荐优先尝试的方案（Task B）

1. **优先方案 1：Softermax base-2 Online Softmax（不改阵列，只改 softmax 单元）**
   - 用 base-2 形式重新实现 online softmax：
     - 从 `e^x` 改为 `2^{x'}`，并保证 `m` 用整数刻度；
     - `m_{i-1}-m_i` 只出现整数差值 → renorm 全部变成左/右移；
   - 将当前 `fa_exp_pwl_8seg_q1_15` 换成一套小片上 LPW（4 段或 8 段） + 移位网络，延迟可压到 2–3 级，Fmax 提升到 400MHz+。
   - 对 cycles 几乎不引入额外 penalty（FSA、Softermax 的评估都显示 online 方案在循环层面可以做到 II≈1）。

2. **优先方案 2：在线 softmax + 行级双行交错**
   - 在线 softmax 改造完成后，在调度上让：
     - 行 r 的 PV 与 行 r+1 的 QK+softmax 同时运行；
   - 这样可以用“另一行”来隐藏当前行 online softmax 的 pipeline latency，相当于粗粒度版的 multi-context interleaving。

# 任务 C：exp / reciprocal / mul-sat 高频实现 + latency hiding

## 1. Q8.8 饱和乘法器（mul-sat）

### 可比结构 1：Booth 编码 + Wallace/Dadda 树 + 1–2 级 pipeline

- **原理**：
  - 经典 16×16 Booth 乘法器（Q8.8 对 Q8.8）产生部分积，用 Wallace/Dadda 树压缩，再做一次进位加法。
  - 饱和逻辑可以在最终加法后插入简单的 compare + mux。
- **时序**：
  - 单级实现：Fmax 通常在 300–400MHz（55nm）
  - 插入 1–2 级 pipeline 后，可轻松推到 500MHz+
- **面积**：
  - 单个乘法器约 1.5k gates，32 lane 只有 ~50k gates 量级，占 2M gates 的很小一部分。
- **对主线周期**：
  - 若仍采用 pair-wise 等待，会有明显 cycles 惩罚；
  - 若放入行/列级 systolic 型 array，则乘法 pipeline 延迟被数据流“空间移动”吃掉，cycles 几乎不变。

### 可比结构 2：Pre-saturating Multiplier（预饱和判定）

- **原理**：
  - 先以高位估算乘积是否必然溢出，若是，直接输出饱和值，不真正做全宽乘法[4]。
- **优点**：
  - 在 attention 中分布较多的极值（例如较大的 score）情况下，部分运算可简化为比较+选择，降低平均延迟。
- **缺点**：
  - 控制路径更复杂，对 Q8.8 这种相对窄位宽收益有限。

**建议**：在你当前位宽和门数预算下，直接用 Booth+Wallace + 1~2 级 pipeline 即可，不必上 pre-saturating 技术。

---

## 2. exp(x) 的高频实现

结合文献和现有软硬件实践，可以列出 3 类适合 Q8.8 的实现：

### 结构 1：8 段 PWL（当前已有）+ 更深流水 / 更好段划分

- **现状**：你已经有 `fa_exp_pwl_8seg_q1_15`，isolated 下可到 677MHz。
- **优化方向**：
  - 保持 8 段，但：
    - 把 LUT 存放在近邻寄存器中，减少寻址延迟；
    - 把“段选择 + 线性插值”拆成两级 pipeline；
  - 从系统角度，关键在于 **配合行级 overlap** 隐藏这 2–3cycle latency。

### 结构 2：Base-2 exp2 + fractional LPW（参考 SystolicAttention + Softermax）

- **原理**：
  - 把 \(e^x\) 写成 \(2^{x / \ln2}\)，即先做一个系数缩放，再调用 `exp2`。
  - 对 `exp2(z)`，令 `z = z_i + z_f`，其中 `z_i` 整数部分、`z_f` fractional，在 `z_f∈[-1,0]` 上做 8 段线性插值：
    - `exp2(z) ≈ 2^{z_i} * (slope_k * z_f + intercept_k)`[1][2]
- **优势**：
  - 2^{z_i} 只影响浮点/定点的指数位，非常适合用移位实现；
  - fractional LPW 只需小 LUT + 一次 16-bit 乘法，critical path 很短。
- **对你项目的好处**：
  - 可自然接入 Softermax 风格在线 softmax；
  - 和 ExpMul/reciprocal 的 log2 近似共用一套 LUT，整体面积下降。

### 结构 3：一阶级数 / 多项式 + 混合字长

- 有文献给出基于有限项级数 + mixed-precision 的 exp 实现，可约 30% area 降低 + 50% 能耗降低[5]。
- 但对你这种偏小规模、Q8.8 的定点实现而言，收益不如 base-2 + LPW 直观。

**推荐**：把当前 8 段 PWL 改成 **base-2 exp2 + fractional LPW**：
- 方便和 Softermax/ExpMul 的 log2 流水线统一；
- 更易于插多级 pipeline，以 2–3 cycle 延迟换 500MHz+ Fmax。

## 3. reciprocal 1/x 的实现

在 softmax 中 reciprocal 主要出现于：
- `1/Z`（行和的倒数）；
- 或 LSE Norm 阶段的 normalize。

特点是：**调用次数极少**（每行 1 次），完全可以接受多 cycle latency，只要不阻塞主线即可。

### 结构 1：LUT + 单次 Newton-Raphson（NR）

- **步骤**：
  1. 规范化 x，使其位于 [0.5, 1)；
  2. 查小 LUT 得到初值 y0（低精度）；
  3. 执行一次 NR：`y1 = y0 * (2 - x*y0)`；
- 对 Q8.8 而言，一次 NR 就足以把误差降到 1e-3 级别，在 softmax 中完全可接受。
- **面积**：一小块 1k~2k gates 级 LUT + 两次 16-bit 乘法 + 少量加法器。

### 结构 2：Goldschmidt

- 多次迭代，以 `x * (2 - x * p)` 形式不断优化倒数。
- 对小位宽来说，与 NR 相比收益不明显，且控制路径更复杂。

**建议**：用 LUT + 一次 NR 即可，把 reciprocal 逻辑挂在 **行级或 tile 级控制路径上**，只在 PV 开始前处理一遍，该 latency 完全可以用其他行的 QK/softmax 计算来隐藏。

---

## 4. 系统层面的 latency hiding 策略

所有高频算子（mul-sat, exp, reciprocal）的额外 pipeline latency，必须通过 **调度/微架构** 隐藏，而不是在 FSM 里原地等待：

1. **行级 double-buffering**
   - 同时维护两个 row context：
     - row r：正在进行 PV（用到之前算好的 P[i,j]、1/Z 等）；
     - row r+1：正在进行 QKᵀ + online softmax（产生 P[i+1,j] 和其 Z）。
   - reciprocal 可以在 row r 的 softmax 结束后、PV 开始前的“空闲行”中计算；exp 可以在 QKᵀ 流水内并行计算。

2. **算子与阵列绑定**
   - 把 `mul-sat` 视为阵列中 PE 的一部分，而不是独立模块；
   - 把 `exp PWL` 与 `QKᵀ`/`PV` 的 MAC 单元对齐，让一行数据在同一条数据通路上“顺流而下”，避免在时序上形成串行瓶颈。

# 任务 D：在不显著增 cycles 的前提下降低 top 级面积

## 1. 哪些 buffer 最值得 SRAM 宏化

结合 S=256, d=64, Q8.8（16bit），单头单 batch，几块主要 buffer 体量大致为：

- Q / K / V：256×64×2B ≈ 32KB 各一份；
- O：同为 32KB；
- row_acc / softmax 中间：每行 256 元素，约 0.5KB 级别。

在 55nm 下，32KB 级别的 REG-file 面积和功耗都很可观，优先级建议：

1. **最高优先：k_buf / v_buf SRAM 宏化**
   - 访问模式：统一按 key index j 扫描全部 Q 行；
   - 适合做成 **多 bank SRAM**：
     - 比如 4×8KB bank，每个 bank 支持多个 lane 并行读；
   - 宏化后：  
     - 面积大幅下降（对比等效 flop 阵列）；  
     - 方便做 K/V 复用（Task E）——但这已超出本问题范围。

2. **次优先：q_buf SRAM 宏化（或较窄 RF + SRAM 混合）**
   - 访问模式：一般一行 Q 常驻，用于与若干 K block 做 dot product；
   - 可以采用：小 RF 保留当前行（64×16bit×DP_LANES），其余行放在单端口 SRAM 中逐步换入。

3. **row_acc / o_buf**
   - row_acc 容量很小，做在 flop/MBFF 更灵活；
   - o_buf 宏化为 SRAM 有意义，但访问模式比 Q/K/V 更写多读少，**可优先考虑单端口 SRAM + write-only streaming**。

---

## 2. TQ/TK/ROW_PAR/DP_LANES 调参方向

目标是在面积下降的同时保持 `<300k cycles`，且为算子更深流水留下隐藏空间。

1. **TQ / TK（行/列 tile 大小）**
   - 当前 S=256，可以考虑：
     - TQ = 8 或 16（每次处理 8/16 行 Q）
     - TK = 16 或 32（每次加载 16/32 列 K/V）
   - 经验上（参考 Flat / SystolicAttention[1]）：
     - 稍大一点的 TK 有助于提高 K/V reuse，减少外存 traffic；
     - 但 TQ 过大时，row_acc / softmax 的状态保持时间变长，会加剧 online softmax 的反馈链压力。
   - 对你当前规模，**TQ=8, TK=16~32** 是比较稳健的起点。

2. **ROW_PAR（行级并行度）**
   - 若将 ROW_PAR 提高（一次处理多行），
     - 单次 SDPA 的 cycles 可以下降；
     - 但 Q/K/V buffer 带宽和阵列面积要成比例增加。
   - 在 2M gates 预算下，更合理的路线是：
     - 保持小 ROW_PAR（甚至=1），
     - 利用高 Fmax + 行级 overlap 提高吞吐。

3. **DP_LANES（每行 dot-product lanes）**
   - 目前经验值是 32 lanes。  
   - 根据前面 MAC utilization 分析，32 lanes 已足够让理论 cycles 下界 ≈ 262k，你已经做到了 148k，这说明算法级融合已相当充分。
   - 除非 SRAM 宏化带来了大量面积结余，否则暂不建议大幅增加 DP_LANES。

---

## 3. 是否有机会同时降面积且维持 `<300k cycles`

结合前面调度与在线 softmax 的改造建议，可以有一个比较现实的目标：

1. **只通过 top 级缓存 SRAM 宏化**：
   - 把 Q/K/V/O 从 flop 阵列改成单/双端口 SRAM 宏；
   - 保持算子与调度不变，则 cycles 几乎不受影响，Fmax 有可能小幅提升（布线压力下降）。

2. **进一步引入多 bank K/V SRAM + 适度调参 (TQ/TK)**
   - K/V 一旦有较好的 bank 组织，可减少端口冲突、减少 stall；
   - 加上合适的 tiling，可以把 K/V 重读次数减少，甚至略微 **降低 cycles**（减少等待外存的 bubble）。

因此，在“算子逻辑不大改动”的前提下：
- **面积显著下降（Q/K/V/O 宏化）**是现实的；
- cycles 保持在 150k~200k 区间是完全有可能的，只要不同时抬高 ROW_PAR / DP_LANES 造成过大带宽压力。

---

## 4. 这些变化对 `f_clk / cycles` 的净效应

1. **SRAM 宏化**：
   - 减少布线长度与寄存器数，有利于时钟树与时序收敛；
   - 若 Fmax 能从如 399MHz 稳定到 450MHz+，在 cycles 基本不变的条件下，`f_clk/cycles` 明显提升。

2. **K/V 多 bank + 合理 tiling**：
   - 降低 DRAM 等待带来的周期浪费；
   - 在单次 SDPA cycles 保持 <200k 的同时，内核利用率提高，`f_clk/cycles` 进一步提升。

3. **风险**：
   - SRAM 宏的接入方式若不谨慎，可能在 top 级引入新的长组合路径（地址生成 / 多路选择），抵消时序收益；
   - 需要在综合/布局早期就做“block-level STA”，而不是等到 full chip 再发现问题。

# 总体落地路线建议（聚焦 A/B/C/D）

结合以上各项，推荐的工程推进顺序（也是给后续 deep-research-agent 的“执行路线图”）：

1. **Task B 先行：online softmax 结构重构**
   - 引入 **base-2 + shift renorm** 的 Softermax 风格 online softmax；
   - 将当前 189MHz 的 recurrence 关键路径拆散成多级小操作，目标是 300MHz+。
   - 同时在调度上，引入 **行级双行交错**（row r 做 PV，row r+1 做 QK+softmax）。

2. **Task C 同步：算子高频实现，但始终绑定在系统级调度下评估**
   - 把 `fa_exp_pwl` 改为 base-2 exp2 + fractional LPW；
   - `fa_mul_sat_q8_8` 使用 Booth+Wallace+1~2 级 pipeline；
   - reciprocal 用 LUT+一次 NR，只在每行末尾调用，隐藏在行间 overlap 里。

3. **Task D：top 级存储层次与 SRAM 宏化**
   - 优先宏化 K/V/Q/O 四类大 buffer，并设计合适的 K/V bank 结构与 TQ/TK；
   - 评估在宏化和少量调参后 cycles 是否仍 <200k；
   - 若 area 有富余，可适当提高 DP_LANES 或增加一条在线 softmax pipeline 做 multi-context interleaving。

4. **Task A：建立统一的 system-level 评估脚本**
   - 开发一个小工具，输入：
     - 各算子 Fmax / pipeline depth / 调用次数；
     - 调度模式（串行、行级 overlap、多上下文交错）；
   - 输出：
     - 估算的 `cycles_{SDPA}`, `U_MAC`, `Throughput_{SDPA}`, `AreaEff`, `BytesPerSDPA`；
   - 所有新方案在 RTL 实施前先过这一关，避免“局部 600MHz、全局更慢”的伪优化。

通过上述路线，后续 deep-research-agent 可以围绕 AB(C)D 四个方向分别深入，但在一套统一的 **`f_clk / cycles` + 利用率 + 面积** 框架下评估，确保所有优化都是真正面向端到端吞吐的，而不是孤立的模块拉频。
