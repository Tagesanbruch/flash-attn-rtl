下面直接给出基于现有工程（已拆分 datapath）的**下一阶段可落地微架构方案总结**，并围绕 5 个具体问题给出 3 个候选微架构、影响评估、实施顺序与 RTL 级建议。

---

## 一、3 个最适合当前工程的候选微架构

### 方案 A：保守增量版 —— base‑2 + 2‑context online softmax + QK 2 级流水

**核心思想**

在完全保留当前顶层架构和 3 个子模块边界的前提下，只做三件事：

1. `fa_qk_dotprod_slice`：把 QK 点积从组合树改为 **2 级流水 MAC 树**；
2. `fa_online_softmax_pair`：把自然底 `exp` 换成 **base‑2 exp2**，并增加 **2‑context 行级交错**，隐藏 `exp / rescale / acc` 的多周期延迟；
3. `fa_o_normalize_block`：在归一化后加一个很小的 **row FIFO**，与 DMA 写回做 row‑level overlap，并把 **reciprocal 提前**到整行 softmax 结束时发起。

**适用原因**

- Q8.8、ROW_PAR=2、D=64：单行长度 256，不长不短，用 2 个 context 就足以把 2–3 级流水的 `exp` 延迟完全隐藏，不需要一上来做 4 或 8 context；
- 你当前 MAE≈0.0025，留有足够的精度裕量，base‑2 + LUT 的误差在 Q8.8 下完全可控[1][2]；
- RTL 层面改动集中在现有三个子模块内部，接口几乎不变，最多多几个 ready/valid 信号，**最利于复用现有 cocotb 回归**。

---

### 方案 B：进阶优化版 —— base‑2 + 4‑context + 单级 ExpMul 融合

在 A 的基础上，进一步：

1. 将 `fa_online_softmax_pair` 的行级上下文从 2 个扩展到 **4 个 context**，实现 4‑way multi‑row interleave；
2. 引入 **单级 ExpMul**，先只融合 `exp(diff_old) * acc_old` 这一路，把“exp + 乘法”变成单个 2–3 级 pipeline 算子。

**适用原因**

- 4 个 context 可以完全吃掉 3 级甚至 4 级流水的延迟，允许你把 `exp`/ExpMul 做得更深（提 Fmax）而不拉周期；
- 单级 ExpMul 只替换 online softmax 里的“旧 acc 重标定”路径，不动 `exp(diff_new) * v`，数据路径简单，验证成本远低于“一口气把两路都融合”[3]。

---

### 方案 C：激进重构版 —— 小型 systolic / reduction block + 内嵌 ExpMul

保留现有顶层接口与 AXI DMA，但把 `fa_qk_dotprod_slice + fa_online_softmax_pair` 合并为一个 **小型 systolic / reduction block**：

- 比如 4×8 或 8×4 的 “Q·K + online softmax” block，每个 PE 包含：
  - 1 个 16 bit MAC（Q8.8），2–3 级 pipeline；
  - 1 个简化的 base‑2 exp/ExpMul 单元（配合上游 max 计算）。
- 行级 softmax 的 `max / sumexp / acc` 在阵列顶部或边界集中做 reduction，阵列内部只负责本 tile 的局部累加（类似 SystolicAttention/FSA 的“顶行 max 行 + 行内规约”[4]）。

**适用原因**

- 在 S=256、D=64 的小规模场景，上一个级别的 systolic 并不会“大材小用”，反而可以让 QK / softmax / PV 三段强耦合流水，显著提高 MAC 利用率；
- 适合你如果后续确实想把 attention IP 做成“可复用 IP 内核”，而不是只针对这个题目调一版。

## 二、三个方案对 f_clk / cycles / area / 精度 / 验证复杂度的影响

下表是基于当前 148,656 cycles、MAE≈0.0025 的工程，做的定性+粗量化评估（相对当前 baseline）：

| 方案 | 预期 f_clk 变化 | 预期 cycles 变化 | 面积变化 | 精度风险 | 验证复杂度 |
|------|----------------|------------------|----------|----------|------------|
| A：base‑2 + 2‑context + QK 2‑stage | 从 ~350–400 MHz → **450–500 MHz**（softmax & QK 都不再是长组合链） | 从 ~148k → **130–140k**（2‑context 隐藏 2–3 级流水延迟） | + ~5%（context 寄存器 + pipeline FF + 小 LUT） | 很低：MAE 可能涨到 ~0.003–0.004，远低于 0.03 要求 | 低：接口基本不变，主要在单元级验证 base‑2 exp |
| B：base‑2 + 4‑context + 单级 ExpMul | f_clk 可进一步推到 **500–600 MHz**（ExpMul 是 2–3 级短 pipeline） | cycles ≈ **115–130k**（更深流水完全被 4‑context 吃掉） | + ~8–10%（更多 context 状态 + ExpMul 核心） | 中等偏低：ExpMul 的近似误差会额外引入 ~1e‑3 量级误差，但总 MAE 仍远低于 0.03[3] | 中：需要为 ExpMul 单独构建 golden model，对 online softmax 的数值对齐做更多 corner case 验证 |
| C：小 systolic + 内嵌 ExpMul | f_clk 目标 **600 MHz+**（整条路径高度流水） | cycles 有机会压到 **~100k** 甚至更低（QK/softmax/PV 真正 tile‑级融合） | + ~20–30%（阵列结构 + 边界缓冲） | 取决于实现，理论上可与 A/B 相当，但需要完整 bit‑level 验证 | 高：需要重写大量控制与数据流，cocotb 框架可复用，但 case 要重写一轮 |

结合端侧 SoC、面积约束和你**已经有的一个健康 baseline**，更现实的路径是 **优先 A → B，C 留作长期目标/下一代 IP**。

## 三、围绕 5 个问题的针对性建议

### 1. online softmax：如何流水化 / 交错化？

**(1) multi‑context / multi‑row 结构**

- 在 Q8.8、ROW_PAR=2、D=64 情况下，**2 个 context 是首选**：
  - 每行 256 个 scores，对在线 softmax 来说是一条长度适中但不算很长的链；
  - 2 context 即可将 2–3 cycle 的 `exp + rescale + acc` pipeline 延迟完全交错隐藏；
  - 硬件代价非常小：为每个 context 维护 `m_ctx` 和 `l_ctx`（以及必要时的 `acc_ctx`，如果你保持当前“每步更新 acc”的写法）。

- 当你引入 **更深的 ExpMul**（3–4 stage pipeline）或者为了更激进的提频，把 `exp` 做到 3–4 级流水时，可以再升级到 **4 context**。经验上，`context_count >= pipeline_depth` 即可保证 II≈1。

**(2) 如何隐藏 exp/rescale/acc latency？**

把 online softmax 逻辑拆成几个硬件 stage，并用 context 交错确保 pipeline 未被 data dependency 阻断：

- Stage S0：从 QK 读取 `s_i`，更新行内 max 值 `m_i = max(m_{i-1}, s_i)`；
- Stage S1：计算 `diff = s_i - m_i`，送入 base‑2 exp2 LUT，1 级流水；
- Stage S2：对上一拍返回的 `exp(diff)` 做：
  - `l_i = l_{i-1} * exp(m_{i-1} - m_i) + exp(diff)`；
  - `acc_i = acc_{i-1} * exp(m_{i-1} - m_i) + exp(diff) * v_i`（若采用 pair‑wise 累加）；

对于单 context，会因为 `l_i` 依赖 `l_{i-1}` 造成 data hazard。2‑context 的做法是：

- cycle 0：处理 context0 的 `i=0`；
- cycle 1：处理 context1 的 `i=0`；
- cycle 2：context0 的 `i=1`（此时 context0 的流水已经“绕回来了”）；
- …

这样，**每个 context 的 “真实循环间隔” 等于 pipeline 深度**，但全局视角依然是 1 score/cycle 的吞吐。

**(3) base‑2 online softmax 的好处**

Softermax 和后续 base‑2 softmax 论文给出了硬件友好的变形[1][2]：

- 把 softmax 写成 `2^{x'}` 型，`x'` 的整数部分可直接用移位处理，fractional 部分用小 LUT + 线性插值；
- `m_{i-1}-m_i` 变成一个小整数，多数情况下是 0 或 -1，`2^{m_{i-1}-m_i}` 完全是移位操作，对 Q8.8 来说近似成简单右移即可；
- 整个在线 softmax 的“重标定因子”从“乘 + exp”退化为“移位 + 加法”，关键路径非常短，天然适合做 2–3 级流水。

在现有 Q8.8 pipeline 下，你可以把 exp/rescale 路径整体简化为：

- `diff_q = clip(s_i - m_i, [-8, 0])`；
- `exp2_f = LUT(diff_q[fractional])`；  
- `scale = 1 << (diff_q[integer])`；  
- `e = exp2_f * scale`（一个 16 bit 乘法）；

然后用 context 交错把这 2–3 级流水隐藏掉。

### 2. QK engine：从组合树到高频流水

**(1) 是否值得做 2–3 级 pipeline？**

在你目前的规模和时序数据下，答案是 **值得做 2 级，3 级视工艺和目标频率再定**：

- 16×16 Q8.8 乘法 + 64 项加法树在 55 nm 下，如果全组合，很难稳定在 500 MHz 以上；
- 加 1 级 pipeline（2 级总），通常可把这条路径拉到 ~600 MHz 左右；
- 多加第 3 级 pipeline 时收益会迅速递减，并且需要更复杂的交错调度（反而增加实现风险）。

**(2) 如何把额外 latency 隐藏掉？**

关键点是：**QK 树本身已经按 D=64 分 chunk（TQ/TK 分块），本来就不是“1 分数/1 周期”模式**，只要 QK 的输出节拍不变（仍然是每若干 cycle 出 1 个 score），多 1 级 pipeline 基本不会增加总 cycles。  
具体做法：

- 在 `fa_qk_dotprod_slice` 内部：
  - 把乘法和部分加法树算在第 1 级 pipeline；
  - 把最终累加和归一化（可能还有 shift）放在第 2 级；
- 对上游 FSM 而言，**score 仍然每 `D / (#lanes)` cycle 出 1 个**，不需要在状态机里“多等待 1 拍”；
- 和 softmax 的交互通过 `valid` 信号（或简单的“延迟 1 cycle 的 ready”）来实现，不影响总体 schedule。

**(3) 有没有更合适的小 systolic / reduction 树？**

在当前工程中，我更建议：

- 不立刻重构为完整 2D systolic 阵列，而是在 `fa_qk_dotprod_slice` 内部，把 32 lane MAC 的 adder tree 做成 **小型 reduction tree + 局部寄存器**：
  - 比如 4 级：32→16→8→4→1，每级之间插 1 级小寄存器；
  - 每个 leaf lane 仍然是“一行中某个维度的一个乘加”，无需改变外部协议；
- 这样可以让 QK 引擎 **在 RTL 级仍然看起来像“32 个独立 MAC”，但物理上具有 systolic 的 timing 特性**，对综合/STA 极其友好。

真正的小型 systolic 阵列（例如 4×8 block）更适合作为后续“架构级升级”的一部分（对应上面的方案 C），而不是当前这代 IP 的小步演进。

---

### 3. 是否要从自然底 exp 改为 base‑2 online softmax？

结合 Softermax、base‑2 softmax 论文以及 FlashAttention‑3/4 中对 exp 单元的处理[1][2][4]，对 Q8.8 来说：

- **更适合**：  
  - Q8.8 整数位只有 8 bit，softmax 输入通常在 [-8, 8] 的范围内，`x / ln2` 的范围也在一个有限区间内，用 base‑2 形式更易界定 LUT 范围与缩放因子；
  - base‑2 的指数位/移位逻辑与硬件自然契合，适合做成“短 critical path + 多级流水”，非常利于提 Fmax。

- **面积影响**：  
  - 自然底 PWL：需要一套系数 LUT + 乘法 + 加法；  
  - base‑2：系数 LUT 缩小（只对应 fractional 部分），integer 部分直接进移位器，**乘法次数可以减少 1 次**，整体 LUT + 乘法面积可减 ~30%。

- **控制复杂度**：  
  - 从控制/状态机看，本质都是“拿一个 diff 喂给 exp 核心，等结果回来再更新 max/sumexp”；
  - base‑2 引入的逻辑主要是 `integer/fractional` 拆分，但可封装在 exp 核心内部，对上层控制几乎无感。

**小步演进建议**

1. **第一步**：保留现有 online softmax 公式，只把 `fa_exp_pwl_8seg_q1_15` 换成 base‑2 版本：
   - 接口不变：`in_diff` → `out_exp_q1_15`；
   - 内部实现改为 base‑2 LUT + shift；
   - 用现有 cocotb 向量比较“替换前后”的 MAE。

2. **第二步**：在 online softmax 内部，把“旧 max 与新 max 的差值”显式整数化，重写 rescale 逻辑为“移位 + 加法”（即 Softermax 的在线归一化变形）[1]。

3. **第三步**：如果这两步验证通过，再考虑把 exp 与 mul 合并成 ExpMul，继续收缩非线性单元面积与时序。

### 4. ExpMul 融合：是否值得引入、从哪条路径先改？

ExpMul 的基本形式是：`ExpMul(x, v) = e^x * v`，论文给出了可以显著减少 exp 和 mul 面积/功耗的硬件结构[3][4]。  
在你当前 online softmax 递推里有两处典型调用：

1. `exp(diff_old) * acc_old` —— 重缩放旧行的累积结果；
2. `exp(diff_new) * v` —— 本步权重乘以 v 向量。

**优先建议：先替换 ① 路径**

- ① 的特点：
  - 标量 × 标量（或少量通道），频率不高；
  - 精度敏感度略低（累积误差可被后续归一化一定程度平滑）；
  - 只与在线 softmax 内部状态相关，对外最后结果影响相对间接。

- ② 的特点：
  - 向量级（D=64）乘法，占用大量 MAC 资源；
  - 直接影响最终 Out=P·V 的数值；
  - 如果立即替换，验证成本较高。

因此，**首选路径是用 ExpMul 替换 `exp(diff_old) * acc_old`**：

- 把 online softmax 的“旧 acc 重标定”从：

  ```verilog
  e_old = exp(diff_old);
  acc_i = acc_old * e_old + ...;
  ```

  改成：

  ```verilog
  acc_scaled = expmul(diff_old, acc_old);
  acc_i      = acc_scaled + ...;
  ```

- 接口定义：

  ```verilog
  module fa_expmul_q8_8 (
      input  logic        clk,
      input  logic        en,
      input  logic [15:0] diff_q8_8,   // m_{i-1} - m_i
      input  logic [15:0] val_q8_8,    // acc_{i-1}
      output logic [15:0] out_q8_8,    // scaled acc
      output logic        out_valid
  );
  ```

- pipeline 深度建议 2–3 级，并用 2 或 4 context 把 latency 隐藏。

**整体收益**

- **面积**：减少独立 `exp` + `mul` 实例数量（尤其是如果你原本为每个 acc 都准备了单独乘法器），拉低整体非线性逻辑面积；
- **Fmax**：ExpMul 内部可以专门针对“diff 范围有限 + Q8.8”优化，critical path 通常比“通用 exp + 通用 mul”短；
- **验证复杂度**：集中在 ExpMul 单元本身，你可以写一个 Python golden model（使用高精度 FP32 先转为 Q8.8）做比对；对整个 attention 的误差影响可用已有 cocotb 顶层测试评估。

第二阶段若需要更大收益，再考虑用 ExpMul 替换 `exp(diff_new) * v` 那一路，但那已经是方案 B/C 的范畴。

### 5. normalize / reciprocal / writeback 的 overlap

你目前 `fa_o_normalize_block` 的典型顺序大致为：

1. 等待 online softmax 给出整行 `sumexp`；
2. 求 `1 / sumexp`（reciprocal）；
3. 遍历行内 acc，逐个乘以 reciprocal 得到最终 P·V 或 O；
4. 把结果写回 DMA。

这是一个天然“串行 4 阶段”的流程，容易在尾巴阶段造成 DMA 写空转。

**可落地 micro‑architecture 建议**

1. **reciprocal 前移**  
   - 在线 softmax 一行结束时，你已经拿到了 `sumexp`，此时可以立刻把它送进 `reciprocal` 单元（LUT+1 次 NR 或 Goldschmidt 单步都足够[5]），其 latency 完全可以被“下一行 QK + softmax”覆盖；
   - 接口层面，只需要在 `fa_online_softmax_pair` 增加一个 `row_done` + `sumexp_out` 信号，驱动 `fa_o_normalize_block` 内部的 reciprocal。

2. **normalize 与 writeback row‑level overlap**  
   - 在 `fa_o_normalize_block` 内部增加一个小的 row FIFO（深度可以是 1 行，16 bit × D=64），流程改成：
     - 一边从 acc RAM 读出一行数据、乘以 reciprocal、写入 FIFO；
     - FIFO 一侧用 streaming 形式喂给 AXI DMA 写接口；
   - 这样只要 AXI DMA 不背压，**归一化和写回实际上是重叠的**。对于 S=256 的小规模 attention 来说，这可以把“normalize+writeback”阶段的可见尾巴缩短到接近 normalize 单纯计算时间。

3. **与已有验证框架的耦合**

- 顶层 AXI DMA 接口不变，只是写操作开始得更早，写 burst 的排布与之前一致；
- cocotb 框架中主要观测的是“完整 SDPA 结束后的结果矩阵”，对中间写回时序并无强依赖，因此可以直接复用；
- 若担心有写乱序风险，可以在 DMA wrapper 中加一个 `row_idx` 信号，确保 FIFO → DMA 的写序与逻辑行序完全一致。

## 四、推荐实施顺序（工程视角）

1. **阶段 1：方案 A（风险最低的性能收益）**
   - `fa_qk_dotprod_slice`：加入 1 级 pipeline；
   - `fa_exp`：改为 base‑2，并做 1–2 级 pipeline；
   - `fa_online_softmax_pair`：引入 2 context 行级交错（multi‑row interleave）；
   - `fa_o_normalize_block`：增加 row FIFO，实现 normalize/writeback overlap；
   - 目标：**Fmax → 450–500 MHz，cycles 降至 ~130–140k，保证 MAE 仍在 0.005 以内**。

2. **阶段 2：在 A 稳定之后，实现部分 ExpMul（方案 B 的前半步）**
   - 实现单级 ExpMul 并替换 `exp(diff_old) * acc_old`；
   - 增加 regression，重点比对 softmax 行级的归一化数值；
   - 观察 cycles 与 Fmax 真实变化，决定是否进一步开 4 context。

3. **阶段 3：如果还有性能/能效压力，再考虑 4 context + 双 ExpMul 或小 systolic block（方案 B/C 全量）**

## 五、“最小可验证原型”建议

为了最大化复用现有 cocotb 回归，建议按下面的“最小增量”路径来做原型：

1. **原型 0（sanity check）**  
   - 只把 `fa_qk_dotprod_slice` 加 1 级 pipeline（2 级 MAC），不动 softmax 和 normalize；
   - 验证：cycles 几乎不变，MAE 完全一致；Fmax 有明显提升。

2. **原型 1：base‑2 exp 核 + 2‑context softmax**  
   - 在 `fa_online_softmax_pair` 里换成 base‑2 exp LUT + 2 context，保持接口不变：
     - 输入仍然是 QK 输出 score 流；
     - 输出仍然是行级 acc 更新结果；
   - 使用现有 cocotb 向量，比较：
     - MAE/MaxAE 是否仍远小于题目要求；
     - 总 cycles 是否无明显增加。

3. **原型 2：reciprocal 前移 + row FIFO 写回 overlap**  
   - 把 reciprocal 单元放到 softmax 行结束时触发；
   - 在 normalize block 内加入 1 行 FIFO，但保持 DMA 总写入大小和顺序不变；
   - 验证：读写数据量一致，结果矩阵一致，cycles 略有改善。

4. **原型 3：单级 ExpMul（只替换 `exp(diff_old) * acc_old`）**  
   - 在 `fa_online_softmax_pair` 内加 ExpMul 单元；
   - 做更严格的随机向量测试（多行、多 batch 等），确认数值一致性；
   - 若 MAE 仍稳定在 ≪0.03，则可以推广到更多路径。

以上每个原型都可以单独打 tag、跑全套 cocotb 回归，并在 CI 中保持“任意一个原型失败即回退”的策略，使工程向前推进同时维持稳定性。
