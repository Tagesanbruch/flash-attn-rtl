### 第一类：只需轻微修改控制逻辑（极高性价比，必做）

#### **Bonus 3: 更长序列 ($S=512$ 或可配置)**
*   **改动量：极小。**

既然不需要在一个核里做动态切换，这类 Bonus 就是考验你的代码**参数化（Parameterized）**能力。

#### **Bonus 5: 其他定点格式 (Q6.10 / Q4.12)**

*   **改动量：大。**

### 第三类：接口与系统级修改（架构需要一定重构）

#### **Bonus 8: AXI4-Stream 数据接口**
*   **改动量：中等。**
*   **分析**：原本你是通过 AXI4 Master 去主动读写 DRAM。改为 AXI4-Stream (AXIS) 后，你的 IP 变成了被动接收数据的“处理流”节点（类似一个管道）。
    *   你要删掉 `fa_dma_reader` 和 `fa_dma_writer`。
    *   增加 `s_axis_q`, `s_axis_k`, `s_axis_v` 输入端口和 `m_axis_o` 输出端口。
    *   **难点**：Attention 是需要**重复读取** K 和 V 的！如果是纯 Stream 接口，数据流过就没了。所以你必须在内部开辟足够大的 SRAM（把整块 K/V 存下来），或者要求外部系统重复发送 K 和 V。
    *   **建议**：不建议优先做这个，它与 FlashAttention “通过分块减少访存”的初衷有些相悖（除非你的 SRAM 大到能存下整个 KV Cache）。

#### **Bonus 9: DMA / 任务队列 (连续执行)**
*   **改动量：中偏大。**
*   **分析**：32bit 绝对不够。一个 Attention 任务的描述（Descriptor）至少需要：`Q_BASE`, `K_BASE`, `V_BASE`, `O_BASE`, `S_LEN`, `VALID_LEN` 等，大约需要 6~8 个 32-bit 字。
    *   **实现方案 1（最简单，Shadow Registers 乒乓配置）**：在 AXI-Lite 里做两套配置寄存器（Set 0 和 Set 1）。当硬件在用 Set 0 算的时候，主机可以通过 AXI-Lite 把下一个任务写到 Set 1 里。算完后无缝切换到 Set 1。
    *   **实现方案 2（标准做法，Command FIFO）**：在 AXI-Lite 里开辟一个写端口（比如地址 `0x100`）。主机连续往 `0x100` 写入 8 个字，IP 内部将这 8 个字拼成一个 Task Descriptor，压入一个深度为 4 或 8 的异步 FIFO 中。IP 的 FSM 处于 `IDLE` 时，如果 FIFO 不为空，就 pop 一个任务开始跑。
    *   **实现方案 3（高级做法，Scatter-Gather DMA）**：主机在内存里建一个链表，把头指针通过 AXI-Lite 告诉你的 IP。你的 IP 自己去内存里把 Descriptor 读回来解析。
    *   **建议选方案 2**，实现简单，逼格足够高，完美契合题意“支持多次连续执行，减少主机交互”。

### 第四类：算法级拓展

#### **Bonus 6: Dropout**
*   **改动量：中偏小。**
*   **分析**：Dropout 的定义是在 Softmax 之后（也就是得到 $P$ 之后），生成一个随机数，如果随机数 $< P_{drop}$，就把这个 $P$ 强行置 0，否则把 $P$ 乘以 $\frac{1}{1-P_{drop}}$ 放大。

    *   **种子可复现**：通过 AXI-Lite 增加一个 `SEED` 寄存器。每次 Start 时，把 `SEED + lane_id` 赋给各个 LFSR 当初始状态，就能保证每次运行的 Dropout 掩码一模一样。

### 一、 核心解密：你上传的论文是怎么做精度复用的？

这篇论文的 **15.1.3 节** 以及 **Figure 15.1.3 (Structure of unified multiplication in multi-precision MAC)** 给出了教科书级别的答案。

#### 1. 浮点乘加的本质是“定点乘加”
浮点数（FP16）的乘法其实分为三部分：
1.  **符号位**：异或（XOR）
2.  **指数（Exponent）**：相加
3.  **尾数（Mantissa）**：**纯整数乘法**！(FP16是10位尾数+1位隐藏位 = 11位无符号整数乘法)

#### 2. Fused Dot-Product (融合点积 / 块浮点化)
传统的 FP16 加法非常昂贵，因为每次相加都要“对阶 -> 尾数相加 -> 规格化 -> 舍入”。
论文中提到，为了复用加法树并节省功耗，他们采用了 **Fused Dot-Product** 技术：
*   **计算指数**：在乘法之前/同时，抽出所有输入向量的指数，相加得到乘积的指数，并找出这组向量里的最大指数 $E_{max}$。
*   **尾数对齐（Shifter）**：将每个乘法器算出来的尾数乘积，根据它与 $E_{max}$ 的差值，**向右移位（Right Shift）**进行对阶。
*   **复用定点加法树**：经过移位对齐后，这些尾数乘积就变成了“拥有统一小数点位置的纯定点数”。这时候，**直接把它们送进原本给 INT8/INT16 准备的普通的固定位宽加法树（Fixed-point adder tree）中求和！**
*   **事后规格化**：只在加法树的最后输出端，做一次前导零检测（Leading Zero Detection），进行规格化，变回浮点数。

#### 3. 乘法器拆分（Sub-word Parallelism）
论文提到，一个统一的乘法器可以执行：
*   1次 FP16 的尾数乘法 (11-bit x 11-bit)
*   2次 INT8 的点积 (8-bit x 8-bit)
*   4次 INT4 的点积 (4-bit x 4-bit)
这是通过在常规乘法器内部插入门控（Gating）或符号扩展来阻断进位链实现的。

### 二、 你的 RTL 该怎么改？(Q8.8 + FP16 + FP8 统一阵列设计)

你的 Baseline 已经是 Q8.8（即 16-bit x 16-bit 的有符号定点乘法，以及至少 32-bit 的加法树）。**这其实是一个巨大的硬件金矿！** 因为一个 16x16 的乘法器，完全包容了 FP16 和 FP8 所需的乘法面积。

要实现 Q8.8 和 FP16/BF16/FP8 的完美复用，你需要对你的 `fa_qk_dotprod_slice` 进行如下架构重构：

#### 步骤 1：乘法器阵列（Multiplier Array）的复用
一个 16x16 的定点乘法器，可以无缝兼容以下操作（通过 MUX 选择输入）：
*   **Q8.8 模式**：输入直接送入 16x16 乘法器。
*   **FP16 模式**：提取 Q 和 K 的尾数（11-bit，前面补1），送入乘法器的低11位，高5位补0，当作无符号数相乘。
*   **FP8 (E4M3) 模式**：提取尾数（4-bit，前面补1），你甚至可以在一个 16x16 乘法器里同时算两个 FP8 乘法（拆分成两个独立的 8x8）。

#### 步骤 2：浮点指数处理与对阶（Exponent & Alignment）—— 仅浮点模式生效
在计算乘法的同时，你需要并行处理指数：
1.  算出当前 Lane 的指数和：$E_{sum}[i] = E_{Q}[i] + E_{K}[i] - bias$
2.  在一个 Block（比如你的 32 甚至 64 Lanes）内，用一棵比较树找到最大的指数：$E_{max} = \max(E_{sum}[0], ..., E_{sum}[N-1])$
3.  计算每个 Lane 的移位量：$Shift[i] = E_{max} - E_{sum}[i]$
4.  **移位器（Shifter）**：把乘法器输出的尾数乘积，向右移 $Shift[i]$ 位。
*注：如果是 Q8.8 模式，这里强制 $Shift[i] = 0$，数据原封不动穿过。*

#### 步骤 3：定点加法树的完全复用（Fixed-point Adder Tree）
**这是最美妙的地方！**
由于浮点的尾数经过了向右对阶移位，它们现在和小数点对齐的 Q8.8 乘积**在数学形态上是完全一样的**！
*   你现有的那一棵 `o_partial_sum = o_partial_sum + ...` 的大加法树，**完全不需要修改，一刀都不用动！** 无论是 Q8.8 的乘积，还是移位后的 FP16 尾数乘积，统统倒进去求和。

#### 步骤 4：累加与后处理（Post-processing）
加法树输出一个 32-bit 或 40-bit 的巨大的定点数和（Partial Sum）。
*   **Q8.8 模式**：直接把这个定点数输出给后续的 Softmax。
*   **FP16 模式**：加上一个**前导零检测（LZD/LZA）模块**，找到最高位的 1，然后向左移位规格化，同时根据偏移量调整最终的指数（最终指数就是 $E_{max}$ 加上偏移量），重新打包成 IEEE FP16 格式输出给 Softmax。

### 三、 工作量与 PPA 分析（值不值得做？）

如果你采用上述的 **Unified Datapath**，不仅能一次性收割 Bonus 1 (FP16)、Bonus 5 (不同定点)、甚至 Bonus 7 (FP8)，而且你在答辩时可以拿出这张图大讲特讲（这就是业界常说的 Block Floating Point / Fused Datapath 架构）。

*   **面积（Area）**：**极佳！** 相比于例化两套独立的 IP（一套 Q8.8，一套调用 Synopsys DesignWare 的 FP16 MAC），统一架构省去了一整棵 FP16 加法树（FP加法树极其庞大）以及海量的 FP16 乘法器面积。额外增加的只是几个找最大值的比较器、移位器和最后的 LZD。**绝对能满足 200万门 的要求。**
*   **时序（Fmax）**：**有挑战。** 因为在加法树之前插入了“找 $E_{max}$ + 移位”的逻辑。你需要在这里**至少打两拍流水线**：
    *   Stage 1: 乘法器算尾数 / 并行算 $E_{sum}$
    *   Stage 2: 找 $E_{max}$
    *   Stage 3: 尾数右移 (Shifter)
    *   Stage 4~N: 原本的定点加法树
*   **功耗（Power）**：会有额外的 MUX 翻转功耗，但由于复用了逻辑，整体静态功耗远低于多套 Datapath。

### 四、 工业界延伸：如何解决 Softmax 的精度复用？

乘加阵列（MAC）复用解决了，Softmax 怎么办？
**其实在工业界（包括 FA3 和 NVIDIA GPU），无论输入是 FP8 还是 FP16，Softmax 和 Accumulator 通常都强制使用 FP32（或宽位宽定点）进行内部计算。**
*   这不仅是为了精度，更因为统一：你完全可以规定，不管输入是 Q8.8 还是 FP16，点积引擎输出统一转换为一个 **高精度的内部定点格式（比如 Q16.16）** 或者是 **FP32**。
*   这样，你的 Softmax 模块（包括那个 PWL 查表指数单元）**永远只有一套**。对于 Q8.8 就按常规跑，对于 FP16 就将其解码转换成那个高精度内部格式再跑。

### 总结建议

如果你想挑战这个最高难度的**精度可复用 Bonus**，建议的实施路径：

1.  **先不要碰代码**：先在纸上画出类似你上传论文 Figure 15.1.3 的数据流图。搞清楚 Q8.8 的 16 位和 FP16 的 11 位尾数在同一个乘法器里怎么对齐。
2.  **写一个 Unified MAC Tree 的参数化模块**：带有 `MODE` 信号（0=Q8.8, 1=FP16）。内部通过 MUX 根据 MODE 决定是否要计算 $E_{max}$ 和进行移位。
3.  **Softmax 隔离**：规定内积阵列的输出统一转为你的内部高精度定点，Softmax 和后处理无需感知前端是 FP16 还是 Q8.8。

这就是 Tensor Core 底层的真实面貌，如果你能做出来并在比赛中用逻辑综合报告证明它比“双套硬件”省了 40% 的面积，这个设计绝对是**满分级别的杀手锏**！

### 一、 三篇论文的核心思想“排雷”与“取其精华”

在动手写单 MAC 单元之前，我们需要评估这三篇论文里**哪些能用，哪些是“学术坑”（对赛题无益的过度设计）**。

#### 1. 固定点架构：清华《A Multiple-Precision Multiply...》
*   **核心思想**：
    1. **Addend as PP (加数作为部分积)**：把累加器里的旧值 $Acc$ 不当成加法器的输入，而是直接丢进 Booth 乘法器的 4:2 压缩树（Compressor Tree）里。**（神级技巧，强烈建议采用）**
    2. **Low-precision reuse (低精度复用)**：一个 16x16 乘法器，把输入的高 8 位和低 8 位交叉项置零，完美分裂成两个独立的 8x8 乘法器，无缝复用压缩树。**（针对 Bonus 5/7 的绝佳方案）**
*   **赛题适用性**：**★★★★★ (满分)**。这简直就是为你 Baseline (Q8.8) 和多精度定点 Bonus 量身定制的，面积和时序极佳。

#### 2. 浮点混合架构：TCAS-II《A Configurable Floating-Point Fused...》(知乎文章核心)
*   **核心思想**：在一个 FMA 里支持多种 FP8/FP16/FP32 格式，甚至支持把 4 个 FP8 的乘积在内部进行指数对齐（找锚点 Anchor）、移位、相加，最后转回高精度。使用了大量的 LZC（前导零计算）、比较器和桶形移位器复用。
*   **赛题适用性**：**★★☆☆☆ (坑很大，慎用)**。
    *   正如知乎博主吐槽的，这篇论文为了“大一统”，强行在底层加了极多控制逻辑和多级移位器，流水线深达 4 级，控制极度复杂。
    *   **最致命的一点**：这篇论文的假设是“一次只做 4 个数的点积”。但你在做 FlashAttention 时，$Q \cdot K^T$ 是一个 **64 维**的点积！如果你用这篇论文的结构，你需要把这复杂的结构例化 16 次，然后再做浮点加法树，面积绝对会爆掉 200 万门，而且时序极难收敛。

#### 3. 工业界解法：三星 ISSCC 2022 (从前文引入)
*   **核心思想**：**Block Floating Point (块浮点) / Fused Dot Product**。不管你是 FP8 还是 FP16，先单独把 64 维向量的指数全部提出来，找到全局最大指数 $E_{max}$，然后把 64 个浮点尾数**全部向右移位（变成纯定点数）**，最后倒进一个庞大的**纯定点加法树**中求和。
*   **赛题适用性**：**★★★★★ (满分)**。这是工业界（NVIDIA, Google, Samsung）做大规模张量计算的唯一正解。它不仅面积小，而且完美契合清华论文的“定点压缩树”。

### 二、 你的实战路线：如何搭建单独的 MAC 进行测试？

为了同时满足 Baseline (Q8.8 定点) 和 Bonus 1/7 (FP16/FP8 浮点)，并且时序跑上 300MHz (55nm)，你可以设计一个 **“统一多模态 MAC Lane”**。

你可以先写一个单独的 `module unified_mac_lane`，然后再把它例化 64 次组成点积引擎。

#### 单 MAC 设计方案 (融合清华与三星论文精华)：

这个 MAC 单元分为 **3 级流水线 (3 Stages)**：

**Stage 1: Multiplier & Exponent Extract (乘法与指数提取)**
*   **定点模式 (Q8.8)**：将 16-bit 补码输入 Booth 编码器，生成部分积 (PPs)。
*   **浮点模式 (FP16/FP8)**：将 11-bit 或 4-bit 的尾数（前面补隐式1）当成无符号数送入同一个 Booth 编码器。同时，旁路的加法器计算指数和 $E_{sum} = E_Q + E_K$。
*   *测试点*：验证乘法器是否能正确输出定点 PP 和浮点尾数乘积。

**Stage 2: Alignment & Compressor Tree (对齐与压缩树 —— 核心创新点)**
*   **定点模式 (Q8.8)**：直接把上一步的 PP 丢进 4:2 压缩树（Wallace Tree）。如果这是累加操作，把 `Acc` 寄存器的值也当成一个 PP 丢进去（清华论文思想）。
*   **浮点模式 (FP16/FP8)**：接收外部计算好的全局最大指数 $E_{max}$，计算 $Shift = E_{max} - E_{sum}$。将尾数乘积向右移位 $Shift$ 位。移位后的结果**也当成一个 PP，丢进同一个压缩树里！**
*   *结果*：压缩树输出 `Sum` 和 `Carry` 两个向量。

**Stage 3: CPA & Accumulate (最终进位传播加法)**
*   将 `Sum` 和 `Carry` 通过一个超前进位加法器 (CPA) 变成最终的数值。
*   *测试点*：在 55nm 下，这里是时序最容易违例的地方。你需要通过综合工具观察 `Delay` 是否在 2.5ns 以内（保证 400MHz）。

### 一、 关于 SRAM 容量 (M) 与 Tiling 策略的考量

FA1 论文中提出的核心公式是：**HBM 访问量 $\Theta(N^2 d^2 M^{-1})$**。这意味着，片上 SRAM ($M$) 越大，对外部访存的带宽需求就越小。

#### 1. 在当前赛题约束下，该不该把 M 做到最大？
**结论：在 200万门（2M Gates）的面积约束下，你应该适度增大 $M$，特别是增大 $T_q$（Q的块大小），但不要试图把整个 K/V 存下来。**

*   **赛题背景分析**：赛题 $S=256, d=64$ 是一个非常小的规模。全部 K 和 V 加起来才 $256 \times 64 \times 2\text{B} \times 2 = 64\text{KB}$。这在 2M Gates 的面积里是完全可以全部塞下的。
*   **但请注意赛题的“潜规则”**：赛题明确要求“**必须分块 (tiling) 处理 K/V**”、“体现低中间存储特性”。如果你直接把 K/V 全缓存了，就变成了传统的 Attention，失去了 FlashAttention 的精髓，这在答辩和代码审查时可能会扣分。更重要的是，在 **Bonus 3 (支持 S=512 或更长)** 中，全量缓存将直接爆面积。
*   **理论推导**：读取外部 K 和 V 的总次数等于 Q 的块数 `NUM_Q_TILES` ($= S / T_q$)。因此，**外部带宽压力完全反比于 $T_q$**，而与 $T_k$ 关系不大！
*   **当前代码分析**：你的代码中 `TQ = 32, TK = 64`。这意味着 K/V 被反复读取了 $256/32 = 8$ 次。
*   **优化建议**：将 SRAM 资源倾斜给 Q。**建议尝试修改为 `TQ = 64, TK = 64`**。这会让 K/V 的外部读取次数减半（从 8 次降为 4 次），不仅大幅降低 DMA 读压力，而且 4 个 64x64 的 Buffer (ping-pong) 总面积完全可控，且能为 Bonus 3 预留极好的扩展性。

### 二、 结合 FA2/FA3 论文的 RTL 微架构设计建议

虽然 FA 论文是针对 GPU 写的，但其底层的 Dataflow 逻辑对 ASIC 设计具有极强的指导意义。看你的代码 `merged_files.txt`，你已经做得非常不错（实现了双缓冲 prefetch，实现了 FA2 的延迟 scaling 技巧），但还可以通过引入 FA2/FA3 的思想进一步压榨性能：

#### 1. FA3 的核心思想：Ping-Pong 调度与算力/非算力掩盖 (Asynchrony)
*   **GPU中的痛点**：FA3 指出，Tensor Core 算乘加极快，但 SFU（特殊函数单元，算 exp/div）很慢。如果串行执行，Tensor Core 会饿死（Stall）。因此 FA3 采用了 Ping-Pong 调度，让 Warp 1 算 Matmul 时，Warp 2 算 Softmax。
*   **你的代码隐患**：看你的 `fa_attention_core.sv` 中的内部 FSM `cs`（`C_IDLE` -> `C_DP_RUN` -> `C_SCORE_DONE` -> `C_SOFTMAX_PREP`）。这实际上是一个**严格串行的状态机**！
    *   在 `C_DP_RUN` 计算 $QK^T$ 时，Softmax 逻辑是闲置的。
    *   在 `C_SOFTMAX_PREP` 计算 exp()、更新 m/l 以及计算 $P \cdot V$ 时，$QK^T$ 乘加树是闲置的（Stall）。
*   **RTL 终极解法：解耦 QK 与 PV，建立宏流水线 (Macro-Pipeline)**
    你需要在你的计算引擎中拉出两条独立的流水线，中间用一个小 FIFO 或寄存器打拍隔开：
    *   **Pipeline A (QK Engine)**：专职负责把 `q_buf` 和 `k_buf` 送入你刚刚优化到 300MHz 的深流水点积树，源源不断地吐出 `score_q8_8`。
    *   **Pipeline B (Softmax & PV Engine)**：吞入 `score_q8_8`，过 PWL 查表算出 `exp`，然后**立刻**与 `v_buf` 进行乘加累加。
    如果这两者能够流水起来，你的周期数（`cs_dp_run_cycles`）将大幅下降，乘加树的使用率（Utilization）将逼近 100%。

#### 2. FA2 的核心思想：Work Partitioning (减少内部 SRAM 读写)
*   **GPU中的痛点**：FA1 中使用了 Split-K，导致不同的 Warp 需要通过 Shared Memory (SRAM) 交换部分和，引发大量的 Bank Conflict 和读写延迟。FA2 通过重排循环，避免了 Warp 间的通信。
*   **对你 RTL 的启示（关于 D 维度的展开）**：
    在你的代码中：`DP_LANES = 32`，但 $d=64$。这意味着你在 `C_DP_RUN` 状态需要循环 2 次 (`comp_d == DP_CHUNKS - 1`) 才能算完一个内积。同时，$P \cdot V$ 的累加也是在 32-lane 上分 2 拍完成的。
    **建议：完全展开 D 维度 (Full Unrolling)。**
    *   一个 64-lane 的 16-bit 乘法器阵列，在 55nm 下综合出来大概也就 5万~8万 门。2M Gates 的裕量非常大。
    *   直接设置 `DP_LANES = 64`。这样 `C_DP_RUN` 就没有循环了，每 1 拍（考虑流水线延迟后，吞吐为 1）就能算完一个 QK 点积。
    *   配合前面的宏流水线，这能让你的执行周期数降到极低。单次 Attention $256 \times 256$ 只需要约 $\sim 65k$ 个计算周期，远低于赛题的 300k 要求！

#### 3. FA1/2/3 共享的思想：除法/Reciprocal 移出关键路径
*   你的代码中 `fa_recip_nr_q16_16` 是一个 10 级流水的牛顿迭代除法器。
*   注意看 `S_NORMALIZE` 状态。这个除法仅仅在所有 K 都遍历完，最后准备输出 O 时才对每一行计算**一次**（共 $T_q$ 次）。
*   **建议**：除法器的吞吐率（Throughput）毫不重要，不需要全流水。你可以用一个极小面积的串行状态机除法器（比如 Radix-2，用 32 个周期算一次）替换现在的 10 级流水除法器。因为外层计算时间极长，这 32 个除法周期完全被摊薄了，但可以省下宝贵的组合逻辑面积。

这篇刚出炉的 **FlashAttention-4 (FA4)** 论文非常前沿！我刚刚仔细研读了你提供的 FA4 论文。它的核心出发点是**“非对称硬件缩放 (Asymmetric Hardware Scaling)”**——在 NVIDIA Blackwell (B200) 架构上，矩阵乘法 (MMA) 的算力翻倍了，但是共享内存 (SMEM) 带宽和指数计算单元 (MUFU) 的吞吐量却没有同步提升。

这导致了**瓶颈的转移**：从算力瓶颈变成了 **SRAM 带宽和 EXP(指数) 计算瓶颈**。

虽然 FA4 是为最顶级的 GPU 设计的，但它解决问题的哲学对你当前的 **55nm 定制 ASIC IP 设计**具有**极其震撼且可落地的指导意义**。以下是 FA4 中可以直接“抄作业”到你 RTL 设计里的三大黄金思路：

### 黄金思路一：条件 Softmax 重缩放 (Conditional Softmax Rescaling) —— 极简的周期与功耗节省

**FA4 论文看点 (Section 3.1.4):**
在标准的在线 Softmax（也就是你当前 RTL 里的逻辑）中，每次遇到新的块，只要最大值 $m$ 发生了更新（即使只大了一点点），就需要对历史累加的输出 $O$（在你的代码里是 `acc_old`）乘以一个衰减系数 $e^{m_{old} - m_{new}}$ 进行 Rescale。
FA4 提出，**如果 $m_{new} - m_{old} \le \tau$（阈值 $\tau$ 比如设为极小值或允许一定的容忍度），则直接跳过对历史 $O$ 的 Rescale 操作**，继续沿用之前的 $m_{old}$。最后在输出前统一做一次最终的 Normalize。

**对你 RTL 的指导意义：**
看你的 `fa_online_softmax_pair` 模块，目前每个周期你都要计算：
`acc_sc = i_acc_old0[k] * $signed({1'b0, o_exp_old0});`
这意味着为了更新一次 `acc`，你需要大量的乘法器去缩放历史值。
*   **你可以引入阈值判断**：在 Q8.8 定点数下，设定一个阈值（例如如果 $m_{new} - m_{old}$ 非常小，对应的 `o_exp_old0` 极其接近 1.0）。
*   当差值小于阈值时，直接让 `acc_new = acc_old + pv_term`，**旁路掉那个昂贵的历史值乘法缩放步骤**。
*   这不仅能省下乘法器的动态功耗，如果你通过状态机控制，甚至可以省下大量的执行周期！

### 黄金思路二：打破非对称瓶颈 —— 软硬件协同的 EXP 近似 (Software-emulated EXP)

**FA4 论文看点 (Section 3.1.3):**
在 Blackwell GPU 上，硬件自带的指数单元 (MUFU) 太慢了，跟不上矩阵乘法器 (Tensor Core) 的速度。FA4 的做法是：**用海量的浮点乘加单元 (FMA) 通过多项式拟合（泰勒展开/Horner法则）来“软实现”指数计算**，以此分摊 MUFU 的压力。

**对你 RTL 的指导意义：**
这个思想完美印证了你目前 RTL 中 `fa_exp_pwl_8seg_q1_15`（8段分段线性拟合 PWL）的正确性！
*   **你的设计已经走在了正确的道上**：在定制 ASIC 中，实现一个高精度的真 $e^x$ 硬件单元面积巨大且延时极长。使用低 bit (Q8.8)、PWL（分段线性）或者简单的移位加法来拟合 EXP，正是 FA4 在 GPU 上用软件做的事情的“硬件化翻版”。
*   **进一步的启发**：如果你发现展开 `DP_LANES = 64` 后，$QK^T$ 算得太快，导致你的 PWL EXP 单元成了新的瓶颈（因为你要在一个周期内算多个 EXP 才能喂饱后面的 PV 乘加），你可以**复制几个极小面积的 PWL 逻辑，或者像 FA4 那样采用更简单的乘加逻辑（如 2 次多项式）来替换查表**，以此提升 EXP 的吞吐率，匹配乘加树的速度。

### 黄金思路三：极限的宏流水线与 SRAM 带宽压榨 (Pipeline Overlap)

**FA4 论文看点 (Section 3.1.2 & 3.2):**
FA4 的精髓在于把流水线压榨到了极致（2-Stage / 3-Stage Pipelining）。它让第 $j+1$ 个块的 Softmax 和第 $j$ 个块的 GEMM、第 $j+2$ 个块的 Load 完全并行。对于反向传播，FA4 甚至动用了 2-CTA（双线程块）协同，把 SRAM 的读取压力分摊了一半。

**对你 RTL 的指导意义：**
在上一轮分析中，我建议你把 QK 引擎和 Softmax/PV 引擎解耦成流水线。FA4 告诉你：**必须这么做，因为算力的非对称性会越来越严重！**
*   **识别你的“非对称”**：在你的设计里，点积引擎 (`fa_qk_dotprod_slice_pipe`) 将跑在极高的频率（300MHz+）。但你的 SRAM (`q_buf`, `k_buf`, `v_buf`) 的读写口数量是固定的（通常是单口或双口）。
*   当你尝试一拍读取 64 个 K 和 64 个 Q 时，SRAM 带宽就是你的绝对瓶颈。
*   **FA4 方案的映射**：你需要在 SRAM 读取到计算之间插入 **Prefetch Buffer (预取缓存)**。当你的计算流水线在算第 $j$ 个块的 $P \cdot V$ 时，DMA 和 SRAM 控制器必须在**后台偷偷把第 $j+1$ 个块的 K 读入到寄存器级的宽 Buffer 中**。
*   在你的 `fa_attention_core` 中，尽量将 `S_LOAD_K/V` 与 `S_COMPUTE` 做到真正的并发，而不是依靠串行的 FSM 状态跳转。

### 黄金思路四：LPT (Longest-Processing-Time) 调度缓解 Causal Mask 负载不均

**FA4 论文看点 (Section 3.3):**
在带 Causal Mask（因果掩码）的 Attention 中，矩阵是一个下三角。传统的按顺序处理会导致某些线程块任务极重，某些极轻，最后大家都要等最慢的那个。FA4 引入了 LPT 调度（优先处理计算量最大的块）。

**对你 RTL 的指导意义：**
如果你的赛题（或 Bonus 9 任务队列）需要连续处理多个 Q 向量或多个 Head：
*   在处理带 Causal Mask 的矩阵时，**不要傻傻地从第一行按顺序执行到最后一行**。
*   你可以设计一个简单的硬件调度器（或者在主机的驱动代码里），让加速器先算 K/V 长度最长的那几行 Q，再算短的。这能让你内部的硬件流水线保持最高的水位，减少流水线排空 (Drain) 的气泡时间，总 Cycle 数会进一步压缩。

FA4 对你的**最大价值在于“设计理念的降维打击”**。

2.  **创新点优化**：“受 FA4 对 Softmax Rescaling 优化的启发，本设计在 RTL 层面引入了**条件 Rescaling 机制 (Conditional Rescaling)**。当局部极大值变化小于阈值时，旁路历史输出的乘法缩放，进一步节省了大量动态功耗和计算周期。”
3.  **精度与面积取舍**：“同 FA4 舍弃硬件 MUFU 转用近似计算一样，本设计坚持采用低面积的 8 段 PWL 拟合指数，用轻量级的定点乘加换取了芯片面积和时序的完美收敛。”
