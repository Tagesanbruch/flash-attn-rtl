下面是基于前面所有调研与分析，面向你当前 FlashAttention 风格 RTL IP 的**下一阶段架构演进方案总结**。整体立场是：在已经有一个「S=256 单 head Q8.8、周期/精度都闭环」的 baseline 上，优先选**高展示价值、低侵入、验证成本可控**的路线。

---

## 一、四个方向的总体优先级排序

结合收益、改动面、风险与验证成本，推荐的优先级为：

1. **方向 A：从单 head 扩展到标准 multi-head attention（最高优先）**
2. **方向 B：从“一次配置一个任务”扩展到“连续任务队列”（第二优先）**
3. **方向 D：在现有 Q8.8 基础上试点更低精度（首选 INT8）**
4. **方向 C：新增 AXI4-Stream 数据平面（适合作为中长期演进）**

原因概括：

- A、B **不动主 datapath**，聚焦在控制与地址生成，改动集中又高可见度，最适合比赛/演示型工程的「V2 能力」；
- D 涉及 dot-product、online softmax 等核心数值路径，需要重新做大规模数值回归，适合作为有空档期时的「研究分支」；
- C 改动顶层数据通路与协议，影响整套验证环境，除非你明确要对接流式 SoC 环境，否则优先度可以靠后。

下面按方向展开。

---

## 二、方向 A：单 head → 标准 multi-head attention（MHA）

### 2.1 收益与风险

**收益**

- 从“单 head IP”升级为“标准 MHA IP”，对评审/展示非常直观；
- 不改内核算法与位宽，**复用现有 Q8.8 datapath 和 online softmax**；
- 多 head 串行执行时，不会上 PPA 大雷区，只多一点控制与 row context 存储；
- 后续若你要研究 GQA/MLA，MHA 是必要前置。

**风险**

- 在线 softmax 的 row context（max / sumexp / acc）要引入 head 维度索引，设计/验证上要非常小心，避免 head 间串扰；
- Q/K/V/O 的地址生成要支持「base + head_stride * head_idx」，容易出 off-by-one/对齐错误，但问题集中、好定位。

### 2.2 预计改动面

1. **AXI-Lite 寄存器扩展**

   建议增加一小组「head 级别」寄存器：

   - `NUM_HEAD`：uint3/uint4，支持 1/2/4/8 head；
   - `HEAD_Q_BASE`, `HEAD_K_BASE`, `HEAD_V_BASE`, `HEAD_O_BASE`：head0 的基地址；
   - `HEAD_STRIDE_Q/K/V/O`：每个 head 间的地址步长（单位字节或元素）；

   内部通过：

   ```verilog
   q_base = HEAD_Q_BASE + head_idx * HEAD_STRIDE_Q;
   // k, v, o 类似
   ```

2. **head loop 控制**

   在当前 top-level 的「单次 attention 调用」外围，加一个 head 维度的外层循环：

   ```verilog
   for (head_idx = 0; head_idx < NUM_HEAD; head_idx++) {
       // 1) 装载当前 head 的 Q/K/V/O base & stride
       // 2) 触发现有 fa_attention_core 跑完整一遍 S=256 attention
   }
   ```

   `fa_attention_core` 的内部 FSM 与 datapath 不需要知道有多少 head，只需要把 DMA base 地址与 valid_len 这些配置换成当前 head 的那一份。

3. **row context / buffer 复用**

   - 由于你当前是**单 batch、单序列**，MHA 的每个 head 的 Q/K/V 是独立矩阵，注意力结果也独立；
   - 行级在线 softmax 的 `max/sumexp/acc` **可以按 head 串行复用一套寄存器**，因为在 head loop 里，一个 head 完全结束后才会进入下一个 head；
   - 因此第一阶段不需要为每个 head 单独开一整套 row_context，只需在 head 之间清零 row context 即可。

   只有当你未来支持 **head-level 并行（多 head 同时跑）** 时，才需要为每个并行 head 各自一份 row context。

4. **buffer 复用**

   - 片上 Q/K/V buffer 可以按 head 重用同一块 SRAM，只是 base 地址不同；
   - AXI DMA 按 head 顺序从外存拉取对应 head 的 Q/K/V，完全符合现在 tile-based 访问模式。

5. **验证方案**

   - cocotb 中增加一个多 head test：
     - 在 Python 侧构造一个 `[num_head, S, D]` 的 FP32 golden；
     - 分别对每个 head 调用你的单头 FP32 模型，得到 `O_head[h]`；
     - 与 RTL 多 head 输出按 head 维度一一比对；
   - 覆盖点：
     - 不同 head 的 base/stride 组合；
     - NUM_HEAD=1/2/4/8 的边界；
     - 在 valid_len/padding 的场景下多 head 是否一致。

### 2.3 为什么第一阶段不要直接做 GQA / MLA

- **GQA** 需要多个 head 共享 K/V，而 query 子空间不同，这会让现有的 tile-based Q/K/V 缓冲与 DMA 调度逻辑**重写一遍**；
- **MLA** 更进一步，head 不再是一对一的 Q/K/V，而是 latent 结构映射，完全超出当前 datapath/softmax 的简单复用范畴；
- 你当前 baseline 已经“精细调到 S=256 单 head 的 FlashAttention + online softmax”，第一步在这一基线外面包一层标准 MHA，**既能展示功能，也避免对内核做大手术**；GQA/MLA 更适合在 MHA 稳定之后单独开一条研究分支。

### 2.4 最小可落地版本定义（方向 A）

- `NUM_HEAD` 支持 1/2/4（先不做 8）；
- head 之间**完全串行执行**，无 head 间并行；
- 行级 row context 完全复用一套寄存器，head 间切换时清零；
- Q/K/V/O 基地址通过 `base + head_stride * head_idx` 计算；
- 所有 cocotb case 在 NUM_HEAD=1 时行为保持与现在完全一致。

## 三、方向 B：一次配置 → 连续任务队列

### 3.1 形态选择

你列的三种选择中，按“保留 AXI-Lite、最小侵入”的优先级：

1. **shadow register / ping-pong register bank**（首选，最小可落地版本）
2. **memory-resident descriptor queue**（中期目标）
3. **instruction-fetch/decode 风格控制器**（过于重型，不建议本项目采用）

### 3.2 Shadow register 方案

**核心思想**：维护两套寄存器 bank（A/B），当前任务用 A；软件可以在内核跑 A 时写 B，A 完成后硬件自动切换到 B 并启动下一任务。

**收益**

- 对 AXI-Lite 的协议**几乎无改动**，只是增加 bank_sel；
- 软件模式与原来「写配置→写start→轮询done」几乎相同，只多一个“下一任务配置提前下发”的能力；
- 验证简单，可直接在原有单任务回归上套一层 for-loop。

**关键实现点**

1. AXI-Lite 配置寄存器改为二维：

   ```verilog
   reg [31:0] cfg_reg_bank[2][N]; // N 为原有寄存器数量
   reg        active_bank;        // 0 or 1
   ```

2. CPU 在写寄存器时需带上目标 bank id（通过高位地址或单独控制位）；

3. 内核启任务时读 `cfg_reg_bank[active_bank]`；

4. 当前任务 done 后，如果发现另一 bank 的 `TASK_VALID` 已置位，则：

   - 切换 active_bank；
   - 自动拉起下一次任务；
   - 如果没有有效任务，则保持 idle，等待软件触发。

5. 中断与错误：

   - 对外仍暴露“TASK_DONE”、“TASK_ERROR”；
   - 可以增加一个“CURRENT_BANK” 只读寄存器，方便软件知道当前在跑哪一个 bank 的任务。

### 3.3 Descriptor queue 方案（第二阶段）

在 shadow register 稳定后，可以升级为小型 **memory-resident descriptor queue**（4~8 深度）：

- 每个 descriptor 结构类比一次寄存器配置；
- CPU 将 descriptor 写到一段 SRAM（或通过 AXI-Lite 写到小 FIFO）；
- 控制器从 queue 中弹出 descriptor，装载到内部寄存器，启动内核；
- 任务结束后，自动弹下一个 descriptor。

这一步的好处是：更接近 DPU/NNP 里的标准“任务队列”范式，适合展示「端侧 SoC 自主调度」能力，但改动与验证都要大一截，不适合作为下一步首选。

### 3.4 与现有 DMA 流程的衔接

无论 shadow register 还是 descriptor queue，**DMA 的行为都不必改变**：

- 每个任务仍然是一对 Q/K/V/O 基地址 + stride + seq_len / valid_len 的组合；
- 内核对 DMA 控制器的命令序列不变，只是多跑几次；
- 确保任务切换时，上一任务的 DMA 已完全结束（可用 `dma_done` 信号与 attention_core_done 一起作为“任务完成”条件）。

### 3.5 最小可落地版本定义（方向 B）

- 仅实现 **双 bank shadow register**，队列深度=2；
- 任务切换逻辑为：当前任务 done 且另一 bank 的 `TASK_VALID==1` 时自动切换并启动；
- 不依赖任何新 DMA 特性，仍用原有 burst 模式；
- cocotb 增加一个“连跑两次”的 case，验证两次任务输出都正确且顺序无误。

## 四、方向 C：AXI4-Stream 数据平面

### 4.1 架构影响范围

如果把数据平面改成 AXI4-Stream（保持 AXI-Lite 控制）：

- 必须重构的模块：
  - 顶层 DMA 控制逻辑；
  - Q/K/V/O buffer 入口（原先由 DMA 驱动地址，现在由 stream 驱动 valid/ready）；
  - tile 边界管理（原本由地址与 tile counter 决定，现在要由 stream 帧/side‑band 信号决定）。

- 可以复用的模块：
  - `fa_qk_dotprod_slice`、`fa_online_softmax_pair`、`fa_o_normalize_block` 以及内部 SRAM 组织；
  - online softmax 递推和 row context 组织。

### 4.2 Wrapper vs 深度重构

**强烈建议**：第一阶段只做 **AXI4-Stream wrapper 顶层**，而不直接重写内核：

- wrapper 内部自己实例化一个 AXI DMA Adapter（参考 Xilinx AXI Stream Accelerator Adapter 思路）[1]：
  - Stream In → 写入本地 SRAM → 通过内部 AXI4 对接现有 DMA 版 core；
  - Core 输出 → 通过内部 AXI4 写回 SRAM → 再通过 Stream Out 输出。
- 对 `fa_attention_core` 完全无修改，只是把当前“真实外存”抽象为 wrapper 内的「本地 SRAM」。

这样可以：

- 利用现有 cocotb/DRAM 模型不变的优势；
- 渐进式验证 stream adapter 本身的协议正确性（backpressure、TLAST、frame 边界等）。

### 4.3 Backpressure / 帧边界 / tile 边界

对于 tile-based FlashAttention IP，stream 版需要考虑：

- **Backpressure**：当内部 tile 未处理完时，需要拉低 `tready` 阻止上游继续推数据；
- **帧边界**：
  - 可约定一条 stream 输入包含一整个 `[S, D]` Q 或 K 或 V 矩阵；
  - S=256 或 512 可通过 TLAST 分隔不同序列。
- **tile 边界**：
  - wrapper 内部仍按 TQ/TK 切 tile，把流式数据缓存在 tile buffer 中；
  - tile 满后再触发一次「tile-level」计算。

### 4.4 最小可落地版本定义（方向 C）

- 新增一个 `attention_stream_top` 模块：
  - 上游/下游是 AXI4-Stream；
  - 内部通过小型 SRAM + 简单 DMA 适配器对接现有 `attention_axi_dma_top`。
- 先只支持 S=256 单 head，无任务队列/多精度；
- 验证上仍以「写 Q/K/V 到虚拟 DRAM → wrapper → core → 读 Out」为主，不直接上真实流输入。

## 五、方向 D：从 Q8.8 扩展到其他数值格式

### 5.1 哪些模块真的会被影响

在 attention 栈里，被数值格式牵一发动全身的模块主要是：

1. **dot-product 与累加器**
   - Q/K、P/V 的乘加路径；
   - 积的位宽、累加位宽、饱和逻辑、舍入逻辑都要重审。

2. **online softmax**
   - `x_i`、`m_i`、`l_i`、`acc_i` 的数值范围和精度；
   - exp 近似的输入/输出位宽；
   - renorm 因子的缩放范围（防溢出/下溢）。

3. **max / sum / reciprocal / normalize**
   - 行内 max 的比较精度；
   - sumexp 的动态范围；
   - reciprocal 与归一化时舍入误差。

4. **output cast**
   - 内部高精度累加结果截断/舍入到输出格式（如 INT8、FP8）的策略；
   - 是否需要 per-channel scale/metedata。

5. **scaling metadata**
   - 若采用 FP8/INT8，将不可避免地引入 per-tile / per-head / per-tensor 的 scale；
   - 这些 scale 的存储、更新与应用会引入新的元数据路径。

### 5.2 首选路线：INT8 作为第一阶段试点

从「最小可落地升级」的视角看，在 BF16/FP16/INT8/FP8 中，**INT8 最适合当前 fixed-point IP 做第一阶段升级**：

- **架构兼容性**（从高到低）：INT8 ≈ Q8.8 > FP16 ≈ BF16 > FP8
  - INT8 和现有 Q8.8 都是整数乘加，修改主要在缩放与截断；
  - FP16/BF16 需要浮点乘加器与浮点 softmax 路径，几乎是另一个 IP；
  - FP8 需要复杂的 scale/metedata 管线，反而是最难的一条。

- **实现代价**（从低到高）：INT8 < FP8 < FP16 ≈ BF16
  - INT8：8×8→16 或 32 位累加，门数和功耗都有优势；
  - FP8/FP16/BF16：需要浮点算子（乘、加、exp、div），对 55nm ASIC 来说成本很高。

- **验证复杂度**（从低到高）：INT8 < FP16 ≈ BF16 < FP8
  - INT8：主误差来自量化和截断，可用「FP32 → 量化 → INT8 softmax → 反量化」做系统 Golden；
  - FP8：既要验证浮点，又要验证 per‑tile scale 元数据，验证空间巨大。

- **吞吐/面积收益潜力**：
  - INT8：MAC/带宽都减半，理论上面积/功耗收益立竿见影；
  - FP8：收益更大，但实现/验证代价远超当前工程阶段需要。

综合下来，**建议第一阶段如果做多精度，就锁定 INT8**。

### 5.3 INT8 路线的「最小可落地版本」

1. 外部接口新增一个 `PRECISION_MODE`：

   - 0：Q8.8（现状）  
   - 1：INT8（新模式，内部 datapath 改变）

2. Q/K/V 输入为 INT8（有单独 scale，例如 per-tensor scale），内部做：

   ```text
   q_int8 * k_int8 → 16/32 bit 累加（定点）
   ```

   累加位宽至少 20~24 bit 以避免溢出。

3. online softmax 可以有两种策略：

   - **策略 1**：内部仍在 Q8.8 域工作：
     - 把 dot-product 结果先归一化成 Q8.8，再进入现有 online softmax；
     - 优点是 softmax 全路径不重写，改动集中在 dot-product 输出的缩放器。
   - **策略 2**：softmax 全路径也切换到更窄位宽的 INT/fixed 域：
     - 会进一步省面积，但需要额外数值评估。

   第一阶段建议采用策略 1。

4. 输出 cast：

   - 内部保持 Q8.8 或更高位宽精度；
   - 根据 `PRECISION_MODE` 决定最后 cast 成 Q8.8 / INT8 / 外部 Q6.10 / Q4.12。

5. 验证：

   - 在 cocotb 中增设一个「FP32 → 量化为 INT8 → RTL → 反量化为 FP32」的 golden 流程；
   - 对比整体 MAE/MaxAE 是否仍在可容忍范围（例如 MAE < 0.03）。

### 5.4 从 FlashAttention-3/4 借鉴的思想（抽象到 RTL/IP 层）

不谈 CUDA 细节，只抽象对你有帮助的几点：

1. **coarse-grain overlap**：
   - 把 non-matmul 工作（exp、softmax、normalization、reciprocal）尽可能与 QK/PV 的大块 matmul 重叠（你现在 online softmax 已经在做，但可以在多 head、多任务时做得更 aggressive）。

2. **将非矩阵计算隐藏到调度中**：
   - 例如：在 head r 做 PV 的同时，对 head r+1 做 QK + online softmax；
   - 在任务 n 的写回阶段预取任务 n+1 的 Q/K/V；
   - 这些思想和你在任务 B 的队列化、本地 multi-head loop 是天然契合的。

3. **低精度计算与块缩放/metadata 联动**：
   - 若将来走 FP8/INT8 路线，可借鉴 FA3/4 中的「块级 scale」思路，把 scale/元数据当作旁路通道与计算块一起流动；
   - 在 RTL 中会表现为：每个 tile/head 附带一个缩放寄存器，dot-product 和 softmax 里都使用该缩放因子进行归一化/反量化。

## 六、综合推荐路线与里程碑规划

### 6.1 推荐优先实施的 1–2 条路线

**首选路线 1：方向 A（标准 multi-head）**

- 原因：
  - 对外功能提升最直观：从“单头 IP” → “标准 MHA IP”；
  - 不动 datapath，主要加 head loop 与地址生成，风险低；
  - 可完全复用现有 cocotb 环境，只需扩展少量测试用例。

**首选路线 2：方向 B（shadow register 任务队列）**

- 原因：
  - 与方向 A 高度互补：A 扩展 head 维度，B 扩展 time 维度（多任务）；
  - 可以展示「IP 自主连续处理多个 Attention 调用」的系统级能力；
  - 通过双 bank shadow register 可以在较短开发周期内实现第一个可演示版本。

### 6.2 建议的分支 / 里程碑组织方式

```text
main
 ├─ feature-mha              # 方向 A，多头支持
 │   ├─ milestone-a1         # head_outer_loop + NUM_HEAD=1/2/4
 │   └─ milestone-a2         # 加强验证 + 与 valid_len/512 联动
 ├─ feature-taskqueue        # 方向 B，shadow register 任务队列
 │   ├─ milestone-b1         # 双 bank shadow register
 │   └─ milestone-b2         # 小深度 descriptor FIFO（可选）
 ├─ research-int8            # 方向 D 的 INT8 试点，暂不 merge 主线
 └─ research-axi-stream      # 方向 C 的 AXI4-Stream wrapper，研究性分支
```

- `feature-mha` 与 `feature-taskqueue` 拟合你当前“比赛型工程”的最近目标；
- `research-*` 两条分支可以在资源允许时推进，但不宜马上拖进主线，以免影响已稳定的周期/精度红线。

## 七、建议重点阅读的参考对象（带目的说明）

1. **Hardware Accelerator for Multi-Head Attention and Position-Wise Feed-Forward in the Transformer**（Lu et al., 2020）  
   - 用来参考：MHA 的 head-level 循环组织、Q/K/V/O buffer 在多 head 下的复用方式，以及 softmax 多 head 调度模式。

2. **SystolicAttention: Fusing FlashAttention within a Single Systolic Array**[1]  
   - 用来参考：如何在一个统一阵列里融合 QK / softmax / PV，并用行级/块级 overlap 隐藏非 matmul 运算的 latency，你可以抽象出 head/tile 调度层面的思路。

3. **Online Softmax to FlashAttention — and Why it Matters**[2]  
   - 用来参考：在线 softmax 的数值稳定性与实现细节，如何把 max/sumexp 的递推做成适合流水化的形式，对你未来做 INT8/FP8 softmax 有借鉴价值。

4. **Low‑Cost FlashAttention with Fused Exponential and Multiplication (ExpMul)**[3]  
   - 用来参考：如何把 `exp` 与 `mul` 融合成一个短流水算子，从而既省面积又利于高频，未来你在 INT8 或混合精度上引入 ExpMul 是自然延伸。

5. **AttenPU: An Area Efficient Attention Processor with Reconfigurable FP8 Units**[4]  
   - 用来参考：FP8 的 reconfigurable 协议、scale/metadata 通路和 softmax 实现方式，为你中长期若要支持 FP8 提供结构思路。

6. **Efficient FPGA Implementation of Softmax Function for DNN**[5]
